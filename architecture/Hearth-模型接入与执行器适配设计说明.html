Hearth OS · 模型接入与执行器适配设计说明 ​

本文只依据项目源码整理（apps/server/src 下模型与执行器相关文件，以及 packages/codex-executor、packages/deepseek-executor），未参考 docs/ 与 README.md；文中不列举任何具体代码，括号内的文件名仅用于定位核对。 整理日期：2026-11-13

本文边界（避免与本套其它说明重复）

已讲过的内容在哪份文档本文的处理
一句话该派给哪个执行器、能力白名单、回退顺序意图识别路由与执行器自动选择那篇讲「选谁」，本文讲「接上之后怎么跑」，不重复选路逻辑
调度器如何消费执行结果、如何重试接管Hearth-任务执行调度器设计说明不展开
上下文与交接包如何跨执行器延续hearth-os-上下文管理设计不展开
工具审批与权限模式判定审批机制说明只讲参数差异，不重讲审批机制

本文只讲：四家大模型协议怎么被折叠成一个客户端，七种执行器怎么被折叠成一个接口，以及配置、安装、健康探测是怎么托住它们的。

0. 一句话总览 ​

这是两层适配：下层把四种 LLM 协议折成统一的补全/流式/列模型与流式工具调用；上层把七种执行器折成「能不能跑、跑一次、接着跑」三个动作。旁边一圈注册表、设置、安装器、健康缓存，只回答三个后勤问题：配置从哪来、进程怎么起、算不算活着。

1. 先定性：三个容易误解的地方 ​

误解代码里的实际做法
以为每个模型厂商写一套客户端只有四种「线协议」客户端，厂商差异靠基础地址、模型名与密钥配置表达
以为七种执行器有七套适配代码只有四个适配器类，其中外部 CLI 那一类被复用覆盖四种执行器
以为健康探测就是发个请求看 200缓存分两套时长；真正探测要求模型回复里包含一段约定的回显文本

2. 下层：四协议统一客户端 ​

支持的线协议是 OpenAI 聊天补全、OpenAI Responses、Anthropic 消息、Gemini 四种。对外只暴露三个入口：一次性补全、流式补全、列出可用模型。共同底层负责解析 SSE 帧、容错 JSON 与统一错误对象。

项默认值 / 规则
重试总共 3 次尝试，间隔从 400 毫秒翻倍；只对超时、限流与网关类状态码重试
一次性补全超时60 秒
流式超时180 秒
列模型超时30 秒

流式工具调用按协议分别实现，各自解析增量文本、推理片段、用量统计与「进行中的工具调用片段」。若模型给出的工具参数是无效 JSON，不会抛错终止，而是包成一个「非法参数」标记交回上层处理——宁可让 Agent 看到并自我修正，也不要整轮崩掉。

3. 模型档案、预设与绑定 ​

模型档案存在应用设置里，字段包含协议、基础地址、模型名、密钥等；聊天链路用一个固定的设置键记住「当前用哪份档案」。厂商预设覆盖国内外主流服务与自定义端点，默认上下文窗口 12.8 万 token、单次输出上限 8 千 token。聊天模型被视为「已配置」的门槛是三项齐全：基础地址、模型名、密钥。

执行器与协议之间有一张硬白名单，这是最容易忽略的约束：

执行器允许的协议
原生执行器四种全支持
Codex仅 OpenAI Responses
其余五个外部执行器三种（聊天补全 / Responses / Anthropic 消息），都不支持 Gemini

绑定时若协议不在白名单内会直接报错。也就是说 Gemini 协议只有原生执行器能用。另外，指向本机或私网地址的自建端点不走统一模型管理，避免把本地服务当成云厂商档案。

Codex 的档案还会生成一份 TOML 配置并注入专用环境变量；解析配置时会区分密钥来自进程环境、Windows 用户环境变量还是完全缺失，并对 Windows 用户环境变量做短暂缓存。

4. 上层：统一执行器接口 ​

接口只有四个要素：标识、是否支持续跑、能否运行、执行一次；支持续跑的再补一个「接着跑」。七种执行器标识为：原生、Codex、DeepSeek Harness、Hermes、Qoder、WorkBuddy、Kimi。其中前三个被归为「一等执行器」，其余四个为外部执行器。

一次执行的结论统一为五种：完成、等待补充、失败、取消、预算耗尽。调度器只看这五种，不关心背后是哪个 CLI。

四类适配器：

适配器覆盖的执行器特点
原生原生走本项目的 Agent 运行时与统一模型客户端
CodexCodex走官方 SDK，读本地配置档
DeepSeek HarnessDeepSeek Harness走厂商 SDK，写供应商补丁配置
外部通用Hermes / Qoder / WorkBuddy / Kimi拼命令行参数或直接调 SDK，解析流式 JSON 输出

5. 外部执行器是怎么被拉起来的 ​

启动来源有五种：内建、用户配置、托管安装、全局探测、显式路径。解析顺序是「用户配置 → 托管 → 探测 → 路径」，只有未显式关闭探测时才去扫全局安装。

启动形态有四类：内建代码、直接命令、Node 脚本、SDK 异步迭代。几个值得注意的差异：

  • 多数 CLI 用「打印模式 + 流式 JSON 输出」启动，参数里带轮数与预算限制。
  • 「完全权限」模式在各家并不统一：有的加一个免确认开关，有的加另一个名字的开关，有的通过 SDK 的权限模式参数表达；其中一个执行器的参数里未见对应开关。
  • 取消进程在 Windows 用任务树强杀，在非 Windows 用进程组信号，避免留下孙进程。
  • 临时提示词文件用完会清理，但清理失败被静默吞掉（提供进程在 Windows 上常占用目录），因此临时目录可能残留。

Qoder 走 SDK 的异步迭代，权限模式在「放宽」与「仅接受编辑」两档之间切换；Hermes 单独有一层流解析与「需要审批 / 启动失败」两类专属错误。

6. 安装、健康与就绪 ​

环节规则
托管安装只托管三个外部 SDK 包，版本固定；单次安装超时 15 分钟，日志最多保留 8 千字符，结果写进安装记录文件
设置安装方式分托管 / 已有 / 探测，鉴权方式分本地 / 令牌 / 环境变量；默认审批模式为「必要时」
健康缓存通用缓存 30 秒，「已验证」缓存 24 小时；版本探测 6 秒超时，真实探测 60 秒超时并要求约定回显文本
Hermes 额外探测另有 30 秒缓存，探测版本 4 秒超时；会从若干候选主目录里找配置与鉴权文件
就绪检查只判三个一等执行器：Codex 必须有密钥，DeepSeek Harness 不接受 Gemini 协议

「健康」与「就绪」是两件事：前者回答进程能不能起来，后者回答配置够不够跑。

7. 两个 SDK 包的性格差异 ​

Codex 包DeepSeek Harness 包
配置来源解析主目录下的 TOML 配置档由本项目写供应商补丁配置并注入专用密钥变量
运行姿态工作区可写、不询问审批、关闭联网搜索上下文窗口 13 万 token、输出上限 3.2 万；权限分「完全访问」与「工作区可写」两档
运行中提问支持不支持：提问回调固定按「已取消」返回

最后一行影响很大：DeepSeek Harness 在执行过程中若想问用户，请求会被当成取消，落到调度器的等待补充或失败路径。这不是 bug，是该执行器当前的能力边界。

8. 设置迁移与目录 ​

旧的模型与执行器设置是两个 JSON 文件，启动时会被迁入主库，迁移记录带固定编号；原文件备份到备份目录下的独立子目录，文件名带时间戳。模型迁移失败时会回滚注册表快照。执行器主目录下按执行器再分 Codex 与 DeepSeek Harness 两个家目录。

9. 只读代码才会发现的事实 ​

  1. Gemini 协议只有原生执行器可用；Codex 只认 OpenAI Responses。
  2. 「重试 3 次」是总尝试次数，且只对指定状态码生效，流式调用也走同一套重试。
  3. 健康探测的成功判据是一段约定的回显文本，不是 HTTP 200。
  4. 外部执行器的「完全权限」开关名字各不相同，没有统一抽象。
  5. 临时目录清理失败会被吞掉，Windows 上可能残留。
  6. DeepSeek Harness 的提问回调恒为取消，设计中就不支持运行中交互。

10. 与其它模块的分界 ​

方向内容
输入应用设置与遗留 JSON、模型设置、并发配置、运行预算与权限、工作区路径
输出模型档案与绑定、流式增量与用量、执行结论、健康与就绪视图、供调度器判断重试的失败信息
不讲选哪个执行器（意图路由）、调度与重试（执行调度器）、工具与循环（Agent 运行时）、提示词（上下文）
