SYSTEM DESIGN

总体架构与数据流 ​

七个平面如何协作，状态如何流动，系统如何从最小产品长成完整 Agent OS。

北极星架构 ​

text
用户 / CLI / Web / Mobile / IM
            ↓
     Experience Plane
     任务卡 · 审批 · 产物 · 接管
            ↓
      Personal Gateway
   身份 · 渠道 · 设备 · 注意力入口
            ↓
       Control Plane
  触发 · 策略 · Mandate · 调度 · Watchdog
            ↓

            ↓

   Memory OS      Evolution OS

所有事实进入 Event Log；所有外部副作用经过 outbox、幂等键和 Receipt；所有界面状态都是投影，不是事实源。

七个平面 ​

平面责任不承担
Experience Plane任务卡、审批、产物、接管、通知直接执行业务逻辑或写数据库
Personal Gateway身份、渠道归一化、设备注册、注意力入口长任务推理
Control Plane意图、触发、策略、Mandate、调度、Watchdog持有长期凭据
Durable Harness任务图、路由、预算、重试、lease、恢复绕过策略执行外部动作
Executor LayerNative、Codex、Connector、Browser、GUI、Document/Data、Human 的统一协议自行扩大权限或修改 Policy
Execution Gateway工作区、Sandbox、浏览器、GUI、网络、Credential Broker决定“该不该做”
Memory / Evolution个人上下文、记忆、技能、评估、晋升和回滚成为事实源

Event Log 贯穿所有平面，是状态、审计、恢复和 UI 的源头。

一次任务的完整数据流 ​

  1. 用户或 Source 产生事件。
  2. Gateway 归一化 Event，去重并记录来源。
  3. Control Plane 判断：忽略 / 观察 / 建议 / 创建 Task。
  4. Policy 与 Mandate 检查范围、风险、预算和审批要求。
  5. Token Router 选择最小可行模型和执行层级。
  6. Context Compiler 构建 Task Pack。
  7. Harness 创建 Ticket、Assignment 和 outbox 记录。
  8. Executor 在受限环境执行，持续产生 WorkerEvent。
  9. Execution Gateway 通过 Broker 完成获批副作用。
  10. 产物、Receipt、失败和人工操作写入 Event Log。
  11. 验证器决定完成、重试、换执行器或转人工。
  12. Memory 写入候选记忆；Evolution 收集轨迹。
  13. UI 从投影生成任务卡、通知和产物视图。

部署形态 ​

形态组成目标
Localhearth CLI + hearthd + SQLite + Docker第一阶段和 dogfood
Hybrid本地状态与设备能力 + 云端模型/沙箱资源不足或远程执行
Self-hosted Server常驻 Gateway + 多设备 agentd + 可选远程 Sandbox长期在线和多设备

第一阶段不引入微服务。单进程、单写者、SQLite 足以支撑早期。模块边界靠接口、schema 和测试保证，而不是先拆网络服务。

启动形态 ​

text
hearthd
  ├─ local gateway / IPC / web API
  ├─ scheduler / watcher / trigger
  ├─ task queue / event log / outbox
  ├─ token router / context compiler / budget governor
  ├─ executor supervisor
  ├─ device registry / capability catalog / lease manager
  ├─ execution gateway / sandbox manager
  ├─ watchdog / health / backup
  └─ pairing / event sync / device revocation

必须考虑开机自启、终端关闭后继续运行、休眠唤醒、网络中断、认证过期、执行器崩溃、版本升级、资源回收、手机断开和重新配对。

架构演进 ​

Hearth 不在第一天实现最终架构图上的全部模块。架构随产品增量逐步长出来，但核心不变量保持：

产品形态架构增量继续保持不变
Stage 0 可点击原型Web 原型、UI 数据契约、模拟投影任务卡优先、状态诚实、一个主动作
Stage 1 本地 MVP单进程 hearthd、SQLite WAL、Event Log、Codex、基础审批与产物事实源、恢复、验证、副作用回执
Stage 2 日常操作员Connector、Browser、Document/Data、Context Compiler、Memory v0最小权限、来源、幂等、Token 预算
Stage 3 桌面操作员设备 agentd、GUI Executor、接管与桌面隔离单写者、审计、审批、失败恢复
Stage 4 主动个人 AgentTrigger、注意力预算、手机 PWA、推送与配对低打扰、可撤销、主动模式可暂停
Stage 5 记忆与进化 OSMemory OS、Evolution OS、技能评估与回滚provenance、遗忘、权限交集、可回滚
Stage 6 Personal Agent OS v1.0多设备同步、离线队列、迁移、长期运行与配额一个逻辑 Agent、事件一致、设备可撤销

架构可以分阶段扩展，但产品形态不能分阶段补课。 每个阶段都必须有与其架构复杂度匹配的完整用户路径。

本章结论 ​

架构的价值不是模块数量，而是让“任务、授权、执行、证据和恢复”沿同一条可审计链路流动。Stage 0 先定义契约，Stage 1 用最小真实链路实现它，之后逐步扩展平面，不改变事实源和权限边界。
