EVALUATION

评估体系 ​

Demo 不是能力。评估体系用任务集、指标、基线、验证器、轨迹重放、故障注入和统计纪律证明系统真的能做。

评估体系 ​

Demo 不是能力。Hearth 只相信可重复、可验证、带失败样本的证据。

评估金字塔 ​

层级评什么频率
Unit/Tool解析器、连接器、策略、验证器每次提交
Task-level单任务端到端成功每次发布
Trajectory Replay历史轨迹重放、换路由和失败恢复持续
Shadow真实输入、无外部副作用持续
Live Pilot真实用户、真实副作用、受控范围阶段推进前
Long-run多设备驻留、设备切换、记忆演化阶段验收

任务集 ​

初始建立 40–60 个真实任务，覆盖八类任务族：邮件、日历、文档、调研、代码、网页、桌面、跨应用流程。

要求：

  • 每条任务有明确输入、验收标准和验证器；
  • 包含正常、边界、失败和恶意输入；
  • 真实脱敏数据优先，合成数据单独标记；
  • 保留 holdout 集，不能反复调参；
  • 失败样本不能被删除；
  • 新增能力时增加对应任务，而不是只增加 demo；
  • MVP 的窄任务族也必须有独立任务集，不能只靠一条演示脚本。

核心指标 ​

指标定义初始目标
Verified Task Success通过验证器的任务比例Stage 1 ≥ 70%
Human Minutes / Verified Task每有效完成的人工分钟相对基线下降 ≥ 30%
Interruptions / Verified Task每任务打断次数≤ 1.0
Recovery Rate崩溃/断网/重启后恢复比例≥ 95%
Duplicate Side Effects故障注入下重复副作用0 / 200
Unsafe Action Rate未授权高风险动作0
Token / Verified Success每有效完成 Token持续下降
Cost / Verified Success每有效完成综合成本可解释且可控
Memory Precision召回记忆确实相关且正确≥ 90%
Skill Regression晋升技能导致旧任务退化0 严重回归

目标值是早期工程门槛，不是营销承诺，必须用真实数据更新。

基线比较 ​

至少比较：

  1. 全人工；
  2. 直接使用 Codex；
  3. Hearth 的当前版本；
  4. Hearth 的替代路由或技能版本。

比较成功率、人工分钟、打断、Token、延迟、成本和失败恢复，而不是只比较输出文本。

验证器 ​

  • 代码：测试、类型检查、diff、CI；
  • 文档：结构、引用、格式、用户验收；
  • 邮件：收件人、事实、语气、发送审批、Receipt；
  • 网页：DOM/可访问性状态、截图、最终状态；
  • 桌面：可访问性树、截图、目标状态；
  • 研究：来源和引用；
  • 数据：schema、行数、抽样、对账、复现脚本；
  • 副作用：幂等键、Receipt、对账。

轨迹重放与故障注入 ​

历史轨迹应能重放、换路由、替换模型/执行器并比较结果。故障注入至少覆盖：进程崩溃、网络中断、超时、重复投递、磁盘满、provider 限流/认证过期、设备离线、外部结果不确定、审批过期、记忆/缓存失效。

安全与红队评估 ​

红队必须尝试让系统越权、泄露秘密、重复副作用、绕过审批、污染记忆、扩大技能权限和利用设备。评估结果要进入发布门槛，而不是放在附录。

统计与评估纪律 ​

  • 预先定义指标和样本；
  • 不用平均值掩盖某个任务族崩溃；
  • 保留失败和拒绝样本；
  • 评估集不能用于技能训练；
  • 区分统计显著和产品有意义；
  • 记录模型、执行器、提示、工具和版本；
  • 变更后重新跑基线，避免“只跟旧版本比”。

阶段发布门槛 ​

阶段必须证明
Stage 0可点击端到端原型、12 个可验收任务、核心协议和威胁模型
Stage 1MVP 可在浏览器每天使用；可恢复、可审批、无重复副作用、Codex 任务可验收
Stage 2邮件/日历/文档/网页真实任务可完成，Token 可控
Stage 3GUI 可接管，失败可恢复，无越权
Stage 4主动任务不造成通知疲劳，审批和安全可审计
Stage 5记忆可纠正/遗忘，技能可评估/回滚
Stage 6多设备一致、离线恢复、迁移和撤销可靠

评估反模式 ​

  • 只看 demo 和截图；
  • 只测成功路径；
  • 只统计模型输出，不验证副作用；
  • 用合成任务代替真实任务；
  • 把 Token 降低当成唯一目标；
  • 评估集被技能训练污染；
  • 失败样本被删除；
  • 用平均值掩盖某个任务族崩溃；
  • 自评通过；
  • 没有安全回归测试；
  • 用“以后补评估”推进阶段。

结论 ​

安全与评估不是 Stage 6 的收尾工作。Stage 0 就要有威胁模型和任务集，Stage 1 就要有 MVP 的真实任务验收、恢复和副作用演练；后续每扩一个执行器，安全与评测面同步扩大。
