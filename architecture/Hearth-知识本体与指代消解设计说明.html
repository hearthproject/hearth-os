Hearth OS · 知识本体与指代消解设计说明 ​

本文只依据项目源码整理（apps/server/src 下本体、写回、指代与只读工具相关文件，以及 packages/core/src/personal-agent.ts），未参考 docs/ 与 README.md；文中不列举任何具体代码，括号内的文件名仅用于定位核对。 整理日期：2026-11-13

本文边界（避免与本套其它说明重复）

已讲过的内容在哪份文档本文的处理
经验记忆的捕获、召回打分、巩固、遗忘Hearth-自进化机制设计说明完全不重复
记忆分层、遗忘与脱敏Hearth-存储设计说明不展开
上下文包的四车道预算、编译、渲染与按需展开hearth-os-上下文管理设计只讲「本体/记忆如何成为候选」，分道与展开交给那篇
指代澄清如何变成对话追问判定审批机制说明只讲候选打分与歧义判定

本文只讲：系统里关于「人、组织、项目、决定、承诺」的那张断言图长什么样，怎么判重、怎么处理冲突、怎么被写回、怎么把一句话里的「他」对上号。

0. 一句话总览 ​

本体不是知识图谱数据库，而是一套基于事件溯源的断言图：每条断言都带置信度、有效期与证据引用；写操作默认不静默覆盖，遇到矛盾就生成一条待办交给用户裁决。

1. 先定性：三个容易误解的地方 ​

误解代码里的实际做法
以为本体置信度沿用记忆的「低/中/高」是两套独立体系：本体用「推断 / 观察到 / 已确认 / 已失效」，记忆用低中高；只在编译上下文时做一次单向映射
以为同名实体会自动合并判重极保守：只按「名称或别名 + 同类型」命中，类型不同不合并；类型里虽有「合并到谁」字段，实际没有写入路径
以为「已失效」只是低置信它在排序里是负分，含义是「证据被遗忘后留下的陈旧断言」，比「推断」还低

2. 六类断言 ​

断言关键内容
实体稳定标识、十种类型之一、规范名称、状态、敏感度、置信度
别名别名原文与归一化形式、来源类型、置信度
关系起点、谓词（自由文本）、终点、置信度、有效期、证据、被谁取代
实体状态实体 + 键 + 值 + 置信度 + 有效期 + 来源 + 证据 + 被谁取代
决定标题、结论、理由、备选方案、由谁决定（用户 / Agent / 外部）、状态
承诺描述、到期时间、状态（未兑现 / 已履行 / 已违背 / 取消 / 过期）、对方实体、置信度

别名归一化是一串确定性处理：去首尾空白、转小写、把空白与常见连字符折成空格、合并连续空格。实体状态的值比较用的是「按键排序的递归稳定序列化」，所以对象字段顺序不同不会误判成变化。

置信度排序固定为：已确认 > 观察到 > 推断 > 已失效。它是「新断言能否盖掉旧断言」的唯一依据。

3. 判重与冲突：宁可问，也不悄悄改 ​

新建实体：先按规范名称查、再按归一化别名查，且都限定同类型。命中就补一条别名；只有当新断言置信度更高时才提升该实体的置信度并发出更新事件，否则原样返回。

记录状态：取该实体该键的有效状态（最多 20 条）：

情况处理
值相同仅当新置信度更高时合并证据与来源，不报冲突
没有有效状态直接写入
值不同，且显式要求取代，或「新为已确认且旧非已确认」让旧状态退休（写失效时间与被谁取代），再写新状态
值不同，其余情况写入一条可被立即替代的冲突状态，并生成冲突待办

冲突待办有固定去重键（实体、键、值的哈希），避免反复弹同一件事；固定给出三个选项：保留当前值、采用新值、稍后再说。它会进入注意力队列（治理见判定审批机制说明）。

关系按「起点 + 终点 + 谓词」查重，命中即返回，不更新置信度；决定与承诺也各有同题判重规则。另有「遗忘证据」操作：在证据引用里检索受影响的实体，删除证据后把仍活跃但失去支撑的实体置信度置为「已失效」。

4. 写回：六个入口，只定义「写什么」 ​

OntologyWriter 是本体与业务事件之间的桥，有六个入口：

入口写回什么
任务结果建任务实体并记状态与最新结果；关联目标、产物、所用来源，各建实体与关系
审批决定从审批目标里提取最多五个主题实体，记一条「由用户决定」的决定
对话轮次只处理用户消息：确认句（对/是的/好/记住…）写决定；含时间词与承诺动词的句子解析出到期时间后写承诺
来源条目读正文后建文档实体、记来源状态；从正文抽最多 20 个邮箱建人物实体并记「被提及于」
用户纠正以「已确认 + 允许取代」写状态，并写一条「用户纠正」决定
证据遗忘委托本体的遗忘流程

相对到期时间的解析支持 ISO 日期、明天、后天、周几、下周，默认时刻是傍晚六点。确认句写的承诺用「已确认」，普通句子用「推断」。

这个文件只定义「写什么」，具体「由哪个事件在什么时候触发」是在服务装配处用回调接线的（见Hearth-服务组装与API接入设计说明），不在本文展开。

5. 指代消解：把「他 / 这个项目」对上号 ​

候选召回：把所有活跃实体的规范名与别名汇成一张「归一化形式 → 表面写法」的表，在归一化后的输入文本里做子串匹配，按出现位置升序、表面写法长度降序排序，再用区间重叠贪心去重（长串优先，避免「张三」吃掉「张三丰」）。

打分是六个分量的加权和：

分量权重含义
别名匹配0.35精确别名满分，模糊别名约六成
时近性0.20按距今 90 天线性衰减
范围亲和0.15是否在当前作用域或同会话历史里出现过
类型相容0.15带 @ 或手机号偏人物/账号，公司团队偏组织，项目计划偏项目/主题
图邻近0.10是否与作用域实体有一跳关系
用户确认史0.05同一归一化写法过去是否被用户确认过

候选只留前三。判定为「已解析」需要同时满足两个条件：最高分不低于 0.75，且要么没有第二名、要么领先第二名至少 0.15。有候选但不满足就是「有歧义」，无候选是「无法解析」。

只有不可逆动作遇到歧义才会阻断执行；消解器本身只返回一段追问文本与候选标签，不负责把追问发出去（对话路由见判定审批文档）。

6. 五个只读工具 ​

本体被包装成五个 Agent 可调用的只读工具：查实体、查实体状态、查关系、查决定、列承诺。它们统一有参数解析、结果条数上限（50）与输出长度上限（1.6 万字符，超出给截断预览）。

几个安全细节：查实体支持稳定标识或名称/别名，多个命中会返回「实体有歧义」并列出候选而不是随便挑一个；敏感度为「秘密」的实体状态，值会被置空并标记已脱敏；查实体只返回活跃状态数与关系数，不返回明细。

7. 作为上下文候选源 ​

编译上下文时，本体会先做「查询里提到了哪些实体」的匹配（归一化名称或别名被查询包含，最多取 20 个），再对命中实体扩展出有效状态与出边关系作为额外候选；每个候选带词法、图关系、时近三个分量参与统一排序。

记忆进入候选前有严格的召回门槛：未允许召回、被污染、来源不可信、信任等级为零、敏感内容未获许可、已过期，任一命中就排除；纯词法无关且未命中实体也会被跳过。记忆与本体的关联决定图关系分量是否加一。

编译成四车道上下文包、包哈希复用、按需展开的完整机制见hearth-os-上下文管理设计，这里只说明本体与记忆这一侧的准入条件。

8. 只读代码才会发现的事实 ​

  1. 本体置信度与记忆置信度是两套体系，且「已失效」是负排序值。
  2. 判重极保守，矛盾默认生成冲突待办而不是覆盖；类型里的合并字段没有实际写入路径。
  3. 指代「已解析」是双阈值，不是单一分数门槛；只有不可逆动作才会因歧义被阻断。
  4. 五个本体工具严格只读，秘密实体的状态值被置空。
  5. 记忆关联实体时发出的事件里，关系字段用的词与类型定义允许的取值并不一致；所幸上下文编译只关心是否命中实体、不读该字段。

9. 与其它模块的分界 ​

方向内容
输入存储层的实体/关系/决定/承诺查询与事件追加、任务与审批记录、聊天消息、来源条目
