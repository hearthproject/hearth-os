# 目标、完成判定与证据

<p class="lead">聊天可以表达意图，但不能证明工作已经完成。Hearth 把目标保存为契约，把完成拆成可检查的条件，把结果写成带证据引用的报告。模型可以建议完成，只有验证器和明确的复核策略才能确认完成。</p>

## 设计目标

目标契约要同时回答四个问题：用户到底要什么、哪些事情不能做、什么条件下算完成、失败或超预算时应该停在哪里。这些问题必须在执行前固定下来，不能等模型产出结果后再倒推标准。

完成判定要优先使用确定性证据。文件存在不等于内容正确，命令返回成功不等于业务结果正确，模型说“已经完成”更不能作为唯一依据。能被检查的结构、差异、测试、查询和回执优先；无法自动判断的部分明确交给人工。

证据要能跨执行器、重启和交接保留。一次任务可能先由 Codex 修改工作区，再由原生运行时补交文档，最后由用户审批外部写入。无论执行路径怎样变化，验收条件、已取得的证据和未完成项都不能丢。

## 目标契约

一个目标至少包含以下内容：

| 字段 | 作用 |
|---|---|
| 标题与目标 | 用一句话说明用户要的结果，不用执行步骤代替目标 |
| 约束 | 必须遵守的范围、格式、来源、账户和时间限制 |
| 禁止动作 | 明确不能发送、删除、发布、付款或扩权的事项 |
| 授权来源 | 区分用户直接要求、文档规定和系统默认，避免把系统偏好当成用户授权 |
| 验收条件 | 每项都有标识、说明、验证器类型、检查内容和是否必需 |
| 证据要求 | 产物、测试输出、Git 差异、外部回执或人工复核记录 |
| 预算 | 轮次、工具调用、Token、执行时长和人工分钟上限 |
| 截止时间与停止条件 | 到什么时候停止，在哪些失败或风险信号下立即停下 |
| 复核策略 | 自动通过、风险时人工复核，或完成后必须人工确认 |
| 当前状态与下一步交接 | 目标现在处于哪个阶段，下一位执行者需要知道什么 |

目标状态包括草稿、进行中、受阻、等待用户、验证中、完成、失败和取消。状态变化是记录，不是界面上的临时标签；同一目标同一时间只有一个有效写权威。

验收条件的验证器分为命令、文件、结构校验、Git、人工和模型复核。命令和 Git 检查在受限环境中运行，不能用验证器扩大任务权限。文件检查看内容、结构和声明产物；结构校验检查格式与字段；模型复核只用于解释和补充判断，不替代确定性检查。

## 完成判定

调度器在任务准备结束时执行完成判定。判定先检查目标和验收条件是否存在，再逐项运行验证器，收集证据引用，记录缺失证据和违反的禁止动作，最后给出通过、失败、需要人工或受阻的结论。

完成报告至少要包含目标、任务、结论、验收条件结果、证据引用、缺失证据、禁止动作和检查时间。报告属于任务记录，不随执行器退出而消失。目标型任务在关闭前必须取得完成结论；没有结论时只能保持等待、验证中或受阻，不能把执行器结束当作完成。

完成判定不鼓励“补一句说明”绕过失败。缺产物时先补齐产物；命令失败时保留原始输出；证据无法确认时进入人工复核；出现禁止动作时直接失败并说明影响范围。系统不静默重试高风险动作，也不把不确定的外部结果写成成功回执。

## 预算、截止时间与停止条件

预算按有效完成计算，而不是单纯压缩 Token。轮次、工具调用、Token、时长和人工分钟分别记录；任一预算耗尽都要暂停、降级或转人工，并说明已经完成和未完成的部分。

截止时间不是定时强杀。接近截止时间时，系统应优先收敛结果、保存检查点、列出未完成项，并为用户保留继续、延长、缩小范围或取消的选择。停止条件包括预算耗尽、权限不足、风险过高、外部状态不确定、证据冲突和用户取消；触发后必须留下原因和恢复入口。

## 设计取舍

- **确定性优先。** 能运行测试、检查文件、比较 Git 差异或查询外部状态的，不交给模型自由判断。
- **模型复核有边界。** 模型可以解释证据和发现遗漏，但不能覆盖失败的命令、缺失的文件或未经确认的外部结果。
- **证据用引用而不是长文复制。** 报告保存证据位置和摘要，避免把大段日志塞进任务记录，也避免证据与原文脱节。
- **完成是状态，不是语气。** “已经完成”“应该没问题”不是结论；通过、失败、需要人工和受阻才是可追踪的结论。
- **交接保留验收上下文。** 换执行器后重新解释目标会制造漂移，交接包必须带上验收条件和已有证据。

## 当前边界

命令、文件、结构、Git、人工和模型复核已经形成代码闭环，目标预算、截止时间和停止条件也已接入调度。主观质量、审美、关系判断和真实业务影响仍需人工验收；真实长期任务、跨设备交接和真实外部回执还没有完成整体验收。
