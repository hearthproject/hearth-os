# 入口与交互

<p class="lead">Hearth 的入口不是一个无限聊天窗口，而是一个围绕任务、审批、产物和接管组织起来的操作界面。用户不需要理解内部由谁执行，只需要知道系统正在做什么、哪里需要自己，以及结果是否值得信任。</p>

## 设计目标

入口要解决的核心问题是注意力，而不是信息量。用户打开 Hearth 时，应该先看到正在运行的任务、等待自己决定的动作、最近交付的产物和需要恢复的失败，而不是一长串对话记录。

网页、命令行、手机和即时消息都可以成为入口，但它们共享同一套任务事实。用户可以在电脑上创建任务，在手机上批准，再回到网页查看产物；设备只是不同的观察和操作方式，不会产生互相对不上的状态。

通知必须克制。系统只在真正需要用户判断、授权或接管时打断，并且一次通知要说清楚发生了什么、建议怎么做、不处理会有什么后果。普通的进度变化应该留在任务页，不占用用户的时间。

移动端优先覆盖审批、查看产物、暂停和接管，不追求把桌面端的全部管理功能搬到手机上。界面还要保证键盘操作、可读对比度、屏幕阅读和弱网恢复，因为这些能力直接决定长期使用是否舒服。

## 设计取舍

任务卡优先于聊天记录。聊天适合表达意图，但长任务需要状态、截止时间、产物和失败恢复；把聊天当作唯一界面，会让用户不断向上翻找，也无法判断哪一步已经真正完成。

| 取舍 | Hearth 的选择 | 原因 |
|---|---|---|
| 主界面 | 任务卡、审批卡和产物中心 | 用户直接看到工作状态和下一步，而不是解析对话 |
| 多入口 | 统一归一化来源、身份和去重 | 同一个请求从邮件、网页或消息重复到达时只处理一次 |
| 状态来源 | 服务端记录重建界面 | 刷新、换设备和重连后仍然一致，不依赖浏览器临时状态 |
| 打断策略 | 按风险和等待时间决定 | 高风险动作尽快提醒，普通进度不制造通知疲劳 |
| 手机范围 | 审批、查看、接管和简单发起 | 手机适合短动作，复杂编辑仍留在桌面端 |
| 设备能力 | 设备注册时声明能力，不假设全部对等 | 有的设备能操作桌面软件，有的只能查看和审批 |

界面只发出命令，不直接改写任务事实。用户点击“批准”后，系统要重新检查审批是否过期、动作参数是否变化、授权范围是否仍然有效，再把结果写入记录并更新界面。这样即使两个设备同时操作，也不会出现界面显示成功但实际没有执行的情况。

失败时界面要诚实：连接中断显示离线，状态不确定显示正在核对，执行器失败显示原因和可恢复动作，不能把“还在尝试”伪装成“已经完成”。当用户选择接管时，系统先暂停自动执行，保存当前进度，再把可操作的范围交给用户。
