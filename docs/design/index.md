# 从意图到可靠任务

<p class="lead">Hearth 是一个单用户、自托管、长期驻留的个人 Agent OS。下面的内容把产品定位、关键取舍、系统架构和完成标准放在同一条叙事里：先说明为什么做，再说明怎么设计，最后说明怎样才算真的做成。</p>

## 先看结论

> **Hearth 不追求“更会聊天”，而是让个人数字劳动变得持久、可控、可验证。**

- 用户面对的是任务、审批和产物，不是 Worker、Harness 或 Token 的内部细节。
- 系统持有任务状态、权限、预算、证据和恢复路径；模型只是可替换的执行能力之一。
- 能力按阶段增长，但每个阶段都必须交付可用的纵向切片，而不是只完成一层基础设施。

## 产品定位

| 项目 | 定义 |
|---|---|
| 用户 | 一个主要用户，可能有一到三个可信协作者 |
| 部署 | 本地优先、可自托管，个人文件和凭据默认留在自己的控制范围内 |
| 工作范围 | 研究、写作、文档、邮件、日程、代码、数据、网页和桌面操作的混合工作 |
| 首个楔子 | 选择一个高频、低外部风险、可验证的任务族先跑通完整闭环 |
| 产品形态 | 以任务卡、审批、产物和通知为核心，不以无限聊天记录为核心 |
| 明确不做 | 企业多租户、公开 Agent 市场、未审批的高风险自动化、基础模型竞赛 |

### 它不是什么

- 不是另一个 Coding Agent；
- 不是只会转发提示词的 Codex 套壳；
- 不是把所有权限交给模型的黑盒；
- 不是需要用户每天维护提示词、插件和工作流的工具；
- 不是企业 IAM、组织审计和多租户平台。

## 核心取舍

| 取舍 | Hearth 的选择 | 原因 |
|---|---|---|
| 任务还是对话 | 以任务卡和完成证据为中心 | 长任务需要状态、预算、审批和恢复，聊天记录不是可靠事实源 |
| 状态放在哪里 | Event Log 作为唯一事实源，界面只做投影 | 崩溃、换设备、重放和审计都需要同一条事实链 |
| 谁来执行 | Native、Codex、Connector、Browser、GUI、Document/Data、Human 并列 | 不同任务需要不同能力、风险和 Token 成本，不能押注单一模型 |
| 自研还是集成 | 自研控制面、执行内核、记忆、验证和体验；集成模型、沙箱、浏览器和外部 API | 控制、授权、证据和恢复是产品护城河，底层能力应复用成熟实现 |
| 副作用怎么处理 | 预览、审批、幂等键、outbox 和 Receipt | 邮件、写入、分享、删除和桌面动作必须可追溯、可对账、可恢复 |
| 数据放在哪里 | 单用户、本地优先、可迁移 | 个人上下文、记忆和凭据不能默认离开用户控制 |
| 记忆和进化如何开放 | 记忆可解释、可纠正、可遗忘；技能必须评估、灰度、晋升和回滚 | 让系统积累经验，但不允许无边界自修改 |
| 如何推进交付 | 按能力门槛和纵向增量推进，不按日历承诺 | 先证明可靠，再扩大范围；每个阶段都能停留、试用和回退 |

## 一条执行链

```text
用户 / CLI / Web / Mobile / IM
            ↓
     Experience Plane       任务卡 · 审批 · 产物 · 接管
            ↓
     Personal Gateway       身份 · 渠道 · 设备 · 注意力入口
            ↓
      Control Plane         触发 · 策略 · 授权 · 调度 · 监管
            ↓
     Durable Harness        任务图 · 预算 · lease · 重试 · 恢复
            ↓
      Executor Layer        Native · Codex · Connector · Browser
                            GUI · Document/Data · Human
            ↓
    Execution Gateway       工作区 · Sandbox · 网络 · 凭据代理
            ↓
 Event Log / Artifacts / Receipts
       ↓                    ↓
  Memory OS            Evolution OS
```

任何事实都写入 Event Log；任何外部副作用都经过授权、幂等和回执；任何界面状态都从事件投影重建，而不是依赖内存中的临时对象。

## 系统由哪些部分组成

| 平面 | 主要责任 |
|---|---|
| Experience Plane | 任务卡、审批、产物、接管和通知 |
| Personal Gateway | 身份、渠道归一化、设备注册和注意力入口 |
| Control Plane | 意图判断、触发、策略、授权、调度和 Watchdog |
| Durable Harness | 任务图、路由、预算、lease、重试和恢复 |
| Executor Layer | 用统一协议承载不同执行器和人工接管 |
| Execution Gateway | 工作区、Sandbox、网络、浏览器、GUI 和 Credential Broker |
| Memory / Evolution | 个人上下文、记忆、技能、评估、晋升和回滚 |

所有平面围绕 Event Log 协作。第一阶段采用模块化单体和单写者，不提前拆微服务；边界由接口、schema、事件和测试保证。

## 任务覆盖与完成标准

Hearth 的任务范围包括沟通协作、文档内容、研究整理、代码研发、数据表格、网页 SaaS、桌面应用和个人事务。自主级别从 A0 建议、A1 受控执行、A2 授权执行到 A3 受监督自主，按任务族、来源、设备、金额和时间段分别配置。

“完成”不是模型说一句“已完成”，而是同时具备：

- 用户可见的结果和下一步；
- 持久状态、验证器和可复现证据；
- 外部副作用对应的审批、幂等键和回执；
- 失败原因、恢复入口或明确的人工接管路径。

完整任务覆盖和默认清单见[附录总览](/reference/)与[默认清单](/reference/checklists)。

## 不可妥协的边界

1. Event Log 是唯一事实源。
2. 每个状态根只有一个写权威。
3. 所有外部副作用必须有幂等键、审批或明确豁免，以及 Receipt。
4. 执行器不能直接读取长期原始凭据。
5. 每个任务必须有预算、截止时间和取消路径。
6. 记忆必须有来源、敏感度、冲突和遗忘策略。
7. 技能变化必须经过评估、灰度、晋升和回滚。
8. 每个增量都必须是完整纵向切片：用户结果、界面、持久状态、真实执行、验证和恢复同时出现。

## 当前状态

Hearth 目前处于规格与规划阶段。产品、架构、安全、评估和交付路线已经定义，可运行实现尚未开始；下一步是第一阶段：确定首个场景与真实任务，做出完整体验原型，并打通最小任务闭环。
