# 上下文压缩设计说明

本文记录 Hearth 原生执行器的上下文压缩机制、一次长任务费用问题的排查过程，以及当前的改动与未解决问题。

## 1. 概念

| 名称 | 含义 |
| --- | --- |
| 上下文窗口 | 模型一次可接收的最大输入（如 256k token） |
| maxOutputTokens | 为模型回答预留的输出空间（如 8k） |
| reserve | 从窗口中固定扣除的预留空间，用于计算压缩阈值，不随剩余空间变化 |
| buffer | 额外的安全余量（16k token），防止估算偏差导致超出 |
| 压缩阈值 | 估算输入超过该值即触发压缩：`窗口 − max(reserve, maxOutput) − buffer` |

## 2. 三层上下文

| 层级 | 作用范围 | 位置 | 触发时机 |
| --- | --- | --- | --- |
| 任务内压缩 | 同一任务运行中累积的消息 | `packages/agent-runtime/src/runtime.ts`（`compactContext`） | 每次调用模型前检查 |
| 对话层压缩 | 同一会话内多个任务之间的聊天历史 | `apps/server/src/conversation-context.ts` | 新任务开始时生成简报 |
| 微压缩 | 旧工具输出的截断 | `packages/agent-runtime/src/compaction.ts`（`microcompactMessages`） | 每轮都会运行 |

会话 = 对话框，一个会话可包含多个任务。项目包含多个会话，并共享项目记忆。

## 3. 压缩过程

压缩需要模型调用：旧消息交给模型生成摘要。压缩后，模型收到的内容为：

1. 旧消息的摘要；
2. 关键状态（待办、计划、已读文件等）重新注入；
3. 最近若干条原始消息。

压缩在模型调用之前完成，用户不需要再次提问。

## 4. 问题排查

**现象**：一个长任务跑到 22 轮，每轮都把完整历史重新发给模型，请求体从约 26k 字符涨到 157k 字符，累计输入约 208 万字符。

**定位过程**：

1. 在环境变量 `HEARTH_MODEL_DEBUG_PATH` 指定的文件中记录每次请求体，按行统计字符长度，确认历史持续累积、没有被压缩。
2. 阅读 `runtime.ts` 与 `model-settings` / `executor-settings` 中的上下文窗口策略，发现原生执行器的压缩阈值为窗口的 80%（256k 窗口下约 204,800 token）。
3. 该阈值远高于实际任务中的请求规模，因此压缩从未触发。

**结论**：阈值过高，导致长任务的每轮输入持续增长，费用随轮数快速上升。

## 5. 本次改动

- 新增运行时选项 `compactTriggerTokens`，原生执行器传入 `80_000`。
- 新增导出函数 `triggerWindowTokens`：将触发点换算为现有压缩逻辑使用的窗口参数，使阈值精确等于触发点。
  换算公式：`min(窗口, 触发点 + max(reserve, maxOutput) + 16_000)`。
- chat 对话层的压缩行为未改变。

## 6. 验证

- 单元测试 `runtime.compact-trigger.test.ts`：验证换算后阈值等于触发点，覆盖窗口上限、未配置触发点等边界情况。
- 相关运行时与原生执行器测试通过。
- 真实任务对比（初步观察，非严格对照）：
  - 修复前：一次运行涨到 157k 字符，未压缩。
  - 修复后：另一次运行在约 100k 字符时压缩，回落到约 15k 字符。
  - 两次运行的任务和起点不完全相同，累计输入约下降 45%，结论仅供参考。

## 7. 未解决问题

- **对话层阈值仍为窗口的 80%**，长对话会把大量历史带入每个新任务，需要同样的阈值调整，并审视 `taskContextBudgetTokens` 的预算。对话层阈值统计语义的修复（按有效区间计算）见 `conversation-context.md`。
- **旧工具输出的截断阈值**（8000 字符）偏大，可考虑降至约 2000 字符，保留最近 2 个工具输出的全文。
- **换算函数较绕**，更清晰的做法是让压缩函数直接接受阈值参数。
- **缺少受控对比**：需要同一任务、固定推理强度、多次运行取平均，才能给出可靠的费用数字。
- **字符与 token 的换算**：调试文件中统计的是字符数，与 token 数不完全对应，需要以 `context.usage` 中的真实输入 token 为准。
