# 数据、备份与运维

<p class="lead">Hearth 是单机控制面：任务、授权和数据都留在本机，不假设有远程节点或第二台设备替你保管状态。运维的目标不是“功能更多”，而是出问题时能看清、能回退、能停止。</p>

## 设计目标

用户应该知道数据在哪里、哪些动作会修改数据、哪些动作只是停止外部副作用。备份、恢复、维护、存储回收和诊断必须是独立入口，不能把“停止”伪装成“删除”，也不能把数据库备份说成完整迁移。

长期运行要关注资源而不是只看“没有崩溃”。内存、磁盘、缓存、日志、后台任务和临时文件都需要上限和清理规则；健康检查、异常提醒、升级和回滚要覆盖服务、数据库和桌面代理。

## 设计取舍

| 能力 | 做什么 | 不做什么 |
|---|---|---|
| 加密备份 | 用口令派生密钥，打包 SQLite 与必要元数据 | 不包含产物正文、工作区、来源正文和外部附件 |
| 恢复 | 在临时数据库执行 schema、完整性与投影校验，失败回滚 | 不撤销已经放行的外部动作 |
| 维护 | 清理过期审批、租约、桌面命令、截图、配对和临时文件 | 不删除任务、记忆或产物 |
| 存储回收 | `storage:prune` 按保留期与 pin 规则回收旧 run 与未引用工具输出 | 不删除活跃 run、未结算操作、checkpoint 引用或产物 |
| 诊断 | 导出脱敏健康快照和计数 | 不包含密钥、绝对路径和环境秘密 |
| 全局停止 | 立即停下调度器、待处理审批和桌面会话 | 不删除数据；恢复后执行器仍需手动启动 |

备份归档和口令要分开保管。忘记口令后归档无法恢复；恢复前会提示当前数据将被替换，并要求再次确认。恢复完成后执行器保持停止，避免旧任务在新数据上自动重放。

## 宿主生命周期与就绪

服务启动由 `HostKernel` 统一管理：

- **租约**：数据目录只允许一个宿主写入；`hearth.host.lock` 记录 PID 与进程创建时间，PID 复用会被判为陈旧锁。
- **阶段**：`lease → store → operations → runs → tasks → background → ready`；`/api/health` 暴露 `phase`、`step`、`readyAt`、`error` 和租约信息。
- **关闭**：`stop()` 先切到 `draining`，停止接收新任务、取消在跑 run、释放任务租约，最后释放宿主租约。
- **就绪门**：恢复完成前 `/api/ready` 返回 503，创建任务和继续对话的写路由返回 `HOST_NOT_READY`；只读健康与诊断仍可访问。

## 存储回收

`npm run storage:prune` 默认只预演并打印计划，`--apply` 才实际删除。pin 规则包括：

- 保留期内的 run；
- 活跃 run 与未结算操作；
- checkpoint 引用的 tool-results；
- 已发布产物与任务记录。

设置页的“数据”分区会显示最近一次回收路径和数量。回收不删除任务、记忆、产物正文或备份归档。

## 终态证据与清理

每个终态 run 在任务工作区输出 `run-evidence.json`，包含 task/run/usage、checkpoint 引用、恢复决策、operations/cleanup、artifacts 与 run 链。物理清理单独记账：

- 已登记 shell 进程会被真正终止，结果写回 `run_operations` 的 cleanup 状态；
- subagent/worktree/browser 等资源暂无 cleanup handler 时明确记 `failed` 并留下原因；
- 后台进程注册表在宿主启动时扫描 `running` 记录：PID + 创建时间匹配才杀进程树，否则只标 `lost`，避免误杀复用的 PID。

## 入口

所有入口都在 **设置 → 数据**：目录结构、SQLite 设置表、迁移记录、回收站、加密备份、恢复、维护、存储回收、脱敏诊断和全局停止。健康状态、任务计数和磁盘占用也在这里汇总，不再保留独立的运维页或安全页。
