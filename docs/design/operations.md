# 多设备与长期运行

<p class="lead">多设备不是把同一个网页多开几次，而是让电脑、手机和其他可信设备围绕同一个逻辑助手协作，同时处理离线、同步、撤销、备份和长期运行中的状态漂移。</p>

## 设计目标

用户应该能在不同设备上看到同一套任务、审批和产物，并在切换设备后从上次的位置继续。设备可以拥有不同能力：手机更适合审批和接管，桌面电脑可以操作本地软件，家用服务器可以长期在线；系统不能假设所有设备完全对等。

连接运行时把传输、订阅、数据新鲜度和执行归属分开。每个设备与用户拥有独立连接，重连推进 generation，旧代次写入被拒绝；离线动作只进入 connection outbox，缓存投影标明 `cached`、`asOf` 和游标，不能冒充实时数据。远程动作断线后进入不确定状态并要求显式对账。真实远程节点、手机断网重连和跨节点 outbox 对账仍未验收，因此当前代码闭环不等于多设备交付完成。

离线是正常状态。设备断网时仍能查看已有任务、记录操作和排队待发动作；重新连接后按顺序补齐，冲突时保留双方来源并请求确认，不能静默覆盖。设备丢失或被撤销后，其他设备要停止向它发送敏感数据，并尽快收回能力和密钥。

长期运行要关注资源而不是只看“没有崩溃”。内存、磁盘、缓存、日志、后台任务、连接和临时文件都需要上限和清理规则；健康检查、异常提醒、升级和回滚要覆盖服务、数据库、设备代理和外部连接。

备份、恢复和迁移必须在真实数据上验证。用户要能导出任务、产物、记忆和必要配置，在另一台设备恢复，并确认敏感数据、权限和删除状态仍然正确。版本升级要保持旧数据可读，迁移失败可以回退。

## 设计取舍

Hearth 保持一个逻辑上的权威状态，设备保存本地投影和必要的离线队列。这样用户看到的是一个助手，而不是多台互相对不上的机器人。同步使用版本和删除标记，旧设备上线后不能把已经删除的内容复活。

| 场景 | Hearth 的处理 | 不能做什么 |
|---|---|---|
| 多设备切换 | 从统一记录重建任务和产物，保留最近操作位置 | 不把某台设备的临时界面状态当成事实 |
| 离线操作 | 本地排队，重连后按顺序提交并校验版本 | 不在冲突时静默选择一边覆盖 |
| 设备撤销 | 收回能力、停止同步、轮换密钥并清理敏感副本 | 不假设丢失设备会主动退出 |
| 备份恢复 | 加密导出，验证任务、产物、记忆和授权 | 不只备份数据库而忽略文件和配置 |
| 版本升级 | 迁移前备份，迁移后可验证、可回退 | 不在无法回滚时直接改数据结构 |
| 长期运行 | 资源上限、健康检查、清理和异常提醒 | 不用“重启一下”掩盖持续泄漏或状态漂移 |

设备是能力和信任边界，不只是登录终端。配对时要声明能做什么、能访问哪些数据、是否需要本地确认；高风险能力只在明确授权的设备上开放。设备离线时任务可以排队，但涉及实时外部动作的任务要暂停或转人工。

长稳测试要持续数周，观察内存、磁盘、任务状态、同步延迟、权限漂移和外部连接。出现权限扩大、状态无法收敛、删除后复活或重复副作用时，应停止发布并回到上一个稳定版本，而不是继续增加功能。

v1.0 的标准是用户可以独立安装、长期使用、备份、迁移和退出。系统不需要覆盖所有企业场景，但必须让个人用户知道数据在哪里、哪些设备仍有效、如何撤销授权、如何恢复失败任务，以及如何在不依赖开发者的情况下继续使用。
