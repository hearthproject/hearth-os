# Agent 参考模式：OpenClaw 与 Hermes

Hearth 在第三阶段不重新发明桌面控制协议，而是研究已经运行的开放式个人 Agent，吸收能直接降低误操作和接管风险的部分。本文记录调研结论和 Hearth 的采用边界。结论来自对 OpenClaw 与 Hermes 公开实现文档的阅读，以及 2026-11-06 的代码级核对。

## 共同结论

两个项目都把“连接设备”“授予能力”“执行动作”和“人工接管”拆成不同状态。设备在线不等于允许操作；一次批准也不等于永久授权。模型只能引用当前观察结果，不能持有长期凭据，也不能在能力和窗口范围之外静默降级。

## OpenClaw 的可借鉴做法

- **配对与能力审批分离。** 设备配对只建立连接握手；设备声明的命令或能力还要单独审批。命令必须同时满足“已声明、已批准、网关策略允许”。
- **拒绝规则优先。** 能力扩展要重新审批；撤销设备后，已批准能力立即失效。
- **短时配对、持久能力记录。** 配对请求只在短时间有效；未批准前不授予任何能力。
- **观察与操作分离。** 屏幕快照带 frame ID、尺寸和执行 ID；坐标引用会过期。桌面操作统一经过 `computer.act`，观察经过 `screen.snapshot`。
- **接管优先于继续执行。** 人工接管会暂停自动输入并取消待执行输入；代理恢复控制前必须显式重新取得控制并重新观察。
- **失败关闭。** 无法观察、控制提供方变化或请求越界时返回结构化拒绝，不静默换用另一条执行路径。

## Hermes 的可借鉴做法

- **明确的权限模式。** `standard`、`bounded` 和 `unrestricted` 在启动时固定；`bounded` 要求一次批准能力清单，越界动作直接失败关闭。
- **Windows 原生输入。** 通过 UIAutomation 和 `SendInput`/`PostMessage` 完成操作，尽量不抢占前台焦点。
- **引用短时有效。** 元素引用只在当前截图或观察代次内有效，过期后明确报错并要求重新观察。
- **独立健康检查。** 驱动缺失、权限不足、Session 0 等环境问题通过 `doctor` 暴露，而不是在任务执行到一半时才含糊失败。
- **凭据留在主进程。** 设备连接凭据不进入渲染层或普通插件。
- **取消和无降级。** 支持显式取消；能力清单不能在运行中静默修改。

## Hearth 的采用边界

| 决策 | Hearth 的做法 |
|---|---|
| 设备身份 | 同机 Windows 助手通过 `127.0.0.1` 创建短时配对请求；用户在 Hearth 输入配对码批准。设备令牌只保存在助手和服务端。 |
| 能力审批 | 配对成功不授予能力。观察、桌面控制、UI 自动化分别审批，并绑定应用/窗口白名单；撤销设备立即失效。 |
| 观察引用 | 每次观察返回带 frame ID、尺寸和时间的快照；后续动作必须携带 frame ID，服务端在执行前再次校验设备在线、能力、控制者和观察代次。 |
| 人工接管 | 暂停、继续、接管、交还、终止是一等状态。接管时服务端停止派发输入并通知助手取消待执行动作；交还必须重新观察。 |
| 输入粒度 | 只实现白名单应用的离散低风险动作，例如点击、键入短文本和按键。每次动作都返回前后观察结果与结构化回执。 |
| 数据保留 | 截图只保存在本地设备数据目录并设置短时过期；服务端记录审计事件，不把完整屏幕长期写入事件日志。 |
| 失败处理 | 驱动不可用、权限不足、窗口丢失、白名单不匹配或结果无法验证时停止并交还用户，不重试高风险动作，不伪造成功。 |

## 当前阶段不做

- 不做远程公网设备接入、多用户共享设备或跨设备屏幕串流。
- 不做不受窗口白名单约束的全局键盘鼠标控制。
- 不做密码库、系统安全设置、付款和不可逆文件操作。
- 不把截图自动发送到聊天渠道，也不让渲染层接触设备令牌。
- 不以合成成功代替真实 Windows 助手验收。无法在当前环境验证的项目会保持禁用并在交付状态中列明。

## 对阶段二的影响

同样的原则用于本地发件箱：草稿与审批分离，审批短时有效且只能使用一次；批准后只写入本地发件箱，不冒充真实邮件发送；重复确认不重复写入，失败时明确区分“未写入”和“结果不确定”。
