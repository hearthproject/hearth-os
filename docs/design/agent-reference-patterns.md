# Agent 参考模式：Pi、OpenClaw、Hermes、DeerFlow 与 LoopX

Hearth 在阶段三至六不重新发明设备控制、主动服务、记忆、方法评估和长期运行协议，而是研究已经运行的开放式 Agent，吸收能直接降低误操作、越权、错误记忆和无法回退风险的部分。本文记录调研结论和 Hearth 的采用边界。结论来自对 OpenClaw、Hermes、DeerFlow 与 LoopX 公开实现或设计文档的阅读，以及 2026-11-06 的代码级核对。

本文是设计参考记录，不是集成声明。Hearth 没有引入这些项目的运行时、代码库或协议实现；Pi 只影响原生 Agent 内核的消息循环与工具形态，DeerFlow 与 LoopX 只影响任务拆解、评估分层和交付方法。

## 共同结论

OpenClaw 与 Hermes 都把“连接设备”“授予能力”“执行动作”和“人工接管”拆成不同状态。设备在线不等于允许操作；一次批准也不等于永久授权。模型只能引用当前观察结果，不能持有长期凭据，也不能在能力和窗口范围之外静默降级。阶段四至六沿用同一原则：建议不等于执行，候选不等于正式能力，备份文件存在不等于完整迁移。

## OpenClaw 的可借鉴做法

- **配对与能力审批分离。** 设备配对只建立连接握手；设备声明的命令或能力还要单独审批。命令必须同时满足“已声明、已批准、网关策略允许”。
- **拒绝规则优先。** 能力扩展要重新审批；撤销设备后，已批准能力立即失效。
- **短时配对、持久能力记录。** 配对请求只在短时间有效；未批准前不授予任何能力。
- **观察与操作分离。** 屏幕快照带 frame ID、尺寸和执行 ID；坐标引用会过期。桌面操作统一经过 `computer.act`，观察经过 `screen.snapshot`。
- **接管优先于继续执行。** 人工接管会暂停自动输入并取消待执行输入；代理恢复控制前必须显式重新取得控制并重新观察。
- **失败关闭。** 无法观察、控制提供方变化或请求越界时返回结构化拒绝，不静默换用另一条执行路径。
- **主动建议与执行分离。** 主动模式先产生可解释的建议，用户接受或转成任务后仍走普通任务与审批链，不因来源是“主动”而获得额外权限。

## Hermes 的可借鉴做法

- **明确的权限模式。** `standard`、`bounded` 和 `unrestricted` 在启动时固定；`bounded` 要求一次批准能力清单，越界动作直接失败关闭。
- **Windows 原生输入。** 通过 UIAutomation 和 `SendInput`/`PostMessage` 完成操作，尽量不抢占前台焦点。
- **引用短时有效。** 元素引用只在当前截图或观察代次内有效，过期后明确报错并要求重新观察。
- **独立健康检查。** 驱动缺失、权限不足、Session 0 等环境问题通过 `doctor` 暴露，而不是在任务执行到一半时才含糊失败。
- **凭据留在主进程。** 设备连接凭据不进入渲染层或普通插件。
- **取消和无降级。** 支持显式取消；能力清单不能在运行中静默修改。
- **可诊断的运行状态。** 健康检查应独立于任务执行，提前暴露运行环境、权限和最近维护状态。Hearth 将其扩展为健康快照、维护记录和脱敏诊断导出。

## Pi 的可借鉴做法

- **小而清晰的单 Agent 循环。** 模型回合、工具调用、工具结果回填、下一回合构成主循环；不先引入复杂的多 Agent 编排。
- **消息就是状态。** 系统提示、用户输入、助手工具调用和工具结果按顺序保存，恢复时从同一消息序列继续，而不是重新拼一段提示词。
- **工具是能力边界。** 读取、写入、命令、联网和询问用户分别受任务权限约束，模型不能在执行中自行扩大权限。
- **可恢复的执行。** 每轮和每个工具步骤后写检查点；暂停等待用户、预算耗尽和服务重启后都能从明确位置继续。
- **简洁的完成信号。** 由明确的完成工具声明结果，再由系统检查产物；模型说“完成了”本身不算完成。

Hearth 已按这些原则实现自己的 `@hearth/agent-runtime`，没有引入 Pi 的 npm 包。原生执行器负责通用任务，Codex 继续负责仓库和工程任务；两者共用任务状态、权限、预算和产物契约。

## DeerFlow 的可借鉴做法

- **任务拆解与阶段产物。** 复杂任务先拆成可检查的阶段，再让后续步骤引用前序证据，而不是把整个目标一次性交给一个黑箱执行。
- **研究、生成和评估分层。** 生产候选和评估候选可以分开，避免同一轮执行既改方法又给自己打分。

Hearth 只借鉴这种“拆解、证据、分层评估”的结构，用于候选方法生成和基线/试跑对比；没有集成 DeerFlow，也没有引入多 Agent 协作运行时。

## LoopX 的可借鉴做法

- **小闭环交付。** 每次只收敛一个可验证的能力变化，避免把多个未验证功能打包成一次“大完成”。
- **状态与证据同行。** 交付说明同时记录已验证路径、明确缺口和不能宣称的能力，页面与测试通过不能替代真实验收。
- **按边界验收。** 设备、备份、长期运行等高风险能力必须单独演练失败路径，而不是只在正常路径上演示成功。

Hearth 只把 LoopX 作为交付方法参考，没有把它作为运行依赖，也没有把其工作流机制嵌入 Hearth 的调度器。

## Hearth 的采用边界

| 决策 | Hearth 的做法 |
|---|---|
| 设备身份 | 同机 Windows 助手通过 `127.0.0.1` 创建短时配对请求；用户在 Hearth 输入配对码批准。设备令牌只保存在助手和服务端。 |
| 能力审批 | 配对成功不授予能力。观察、桌面控制、UI 自动化分别审批，并绑定应用/窗口白名单；撤销设备立即失效。 |
| 观察引用 | 每次观察返回带 frame ID、尺寸和时间的快照；后续动作必须携带 frame ID，服务端在执行前再次校验设备在线、能力、控制者和观察代次。 |
| 人工接管 | 暂停、继续、接管、交还、终止是一等状态。接管时服务端停止派发输入并通知助手取消待执行动作；交还必须重新观察。 |
| 输入粒度 | 只实现白名单应用的离散低风险动作，例如点击、键入短文本和按键。每次动作都返回前后观察结果与结构化回执。 |
| 数据保留 | 截图只保存在本地设备数据目录并设置短时过期；服务端记录审计事件，不把完整屏幕长期写入事件日志。 |
| 失败处理 | 驱动不可用、权限不足、窗口丢失、白名单不匹配或结果无法验证时停止并交还用户，不重试高风险动作，不伪造成功。 |
| 主动服务 | 只生成带来源、为什么现在重要、建议动作、影响和风险的候选建议；接受只记录决定，转任务只创建排队任务，外部动作仍需审批；每日上限、安静时段、冷却和暂停限制打断。 |
| 记忆 | 记忆先进入候选并由用户确认；召回记录原因和预算，注入上下文标记为不可信背景；敏感信息默认不召回，`secret` 永不召回；遗忘会脱敏投影、版本、事件和召回审计。 |
| 方法进化 | 候选方法只能继承来源任务的权限交集；试跑只读取已有终态轨迹，不产生外部副作用；只有可重复改进证据才能晋升，并保留拒绝、回退和原因。 |
| 多设备执行 | 任务租约使用 owner、TTL 和 epoch；过期接管推进 epoch，旧执行者的提交被拒绝。同步只复制经过过滤的事件投影，不复制审批、来源、发件箱、设备和桌面控制事件。 |
| 撤销与迁移 | 设备能力、设备令牌和同步对端都可撤销或轮换；全局 kill switch 阻止审批和调度器重启；旧设备失效需要真实演练，备份恢复与产物迁移分开声明。 |
| 备份与恢复 | 使用口令加密的数据库归档，恢复前校验格式、schema、完整性和列结构，在临时数据库中重建后再事务替换；失败回滚，并明确排除产物正文、工作区、附件和截图。 |
| 长期运行 | 健康、维护和诊断是一等能力；维护只清理过期运行状态，不删除任务、记忆或产物；维护失败降级健康状态，不以自动修复为名放宽审批。 |

## 当前阶段不做

- 不做远程公网设备接入、多用户共享设备或跨设备屏幕串流。
- 不做不受窗口白名单约束的全局键盘鼠标控制。
- 不做密码库、系统安全设置、付款和不可逆文件操作。
- 不把截图自动发送到聊天渠道，也不让渲染层接触设备令牌。
- 不以合成成功代替真实 Windows 助手验收。无法在当前环境验证的项目会保持禁用并在交付状态中列明。
- 不把主动建议变成自动执行器，也不因建议来自系统就跳过审批。
- 不把候选记忆直接当成事实，不把候选方法直接当成正式能力。
- 不声称已实现实时 Shadow 执行器、手机 PWA/推送/远程接管或完整可迁移备份。
- 不把 DeerFlow 或 LoopX 描述为已集成组件；它们只提供设计与交付方法参考。
- 不把 Pi 描述为已集成依赖；Hearth 只参考其单 Agent 内核形态，并使用自己的 TypeScript 实现。

## 对各阶段的影响

- **阶段二：** 草稿与审批分离，审批短时有效且只能使用一次；批准后只写入本地发件箱，不冒充真实邮件发送；重复确认不重复写入，失败时明确区分“未写入”和“结果不确定”。
- **阶段三：** 设备配对、能力审批、观察帧、人工接管和控制代次分别建模；无法观察或验证的动作拒绝执行，不静默降级。
- **阶段四：** 主动建议只提供判断材料；接受、忽略、稍后提醒和转任务是一等动作；注意力预算、安静时段和暂停优先于“多提醒”。
- **阶段五：** 记忆与方法都先进入候选，召回和方法使用都保留来源与理由；遗忘、拒绝和回退是可验证的一等路径。
- **阶段六：** 同步、租约、撤销、备份恢复、健康和维护都以“失败时关闭或回滚”为默认，不以正常路径成功代替丢失、离线和长期运行演练。
