# 对话上下文压缩设计说明

本文记录对话层上下文压缩（`apps/server/src/conversation-context.ts`）的机制、一次排查中发现的五个正确性问题，以及各自的修复方式。运行时任务内压缩见 `context-compaction.md`；两者是独立的两层机制。

## 1. 位置与职责

对话层压缩管的是同一个会话内、跨任务的聊天历史：旧内容压成一份摘要，供后续所有执行器共享。它不决定什么时候派任务，也不负责执行器内部的上下文管理；scheduler 和各执行器 runtime 都是它的使用方。

| 入口 | 时机 |
| --- | --- |
| `renderForTask` | 任务开始前，取共享上下文简报 |
| `renderForChat` | 聊天渲染时 |
| `refreshAfterTask` | 任务完成后，尝试压缩 |
| `rememberUsage` | 持久化最近一次真实/估算的输入用量 |

## 2. 核心概念

| 名称 | 含义 |
| --- | --- |
| 摘要（`summary`） | 压缩掉的旧内容的文本，发给模型看 |
| 摘要数据（`summaryData`） | 摘要的结构化 JSON（目标、事实、决策、已完成任务等），程序自己用来过滤任务账本、做增量合并 |
| 有效区间（live） | 仍以原文形式发送的部分：`firstKeptMessageId` 及之后的单元 |
| 边界（`firstKeptMessageId`） | 第一条保留原文的消息 ID；它之前的内容已被摘要 |
| `lastSummarizedAt` | 边界的备用标记：边界处没有聊天消息（只剩任务记录）时，改用时间划分有效区间 |

阈值判断：`摘要 token + 有效区间 token` 超过阈值才压缩。压缩的起点和阈值统计共用同一个 `liveUnits()` 判断。

## 3. 压缩流程

1. 检查阈值，不超就不动。
2. 超了就从最新消息往前保留约 `keepTokens` 的原文，切点之前交给摘要模型。
3. 内容太多时分块（每块 4 万字符、最多 32 块），逐块压缩，后一块带着前一块的结果。
4. 生成结构化摘要后与旧摘要数据合并（旧事实标记 superseded，任务账本从覆盖单元里补全），存入 `summary` 与 `summaryData`，并记录边界。

## 4. 问题发现与修复

以下问题来自 2026-11-25 对压缩逻辑的一次排查，按发现顺序编号。

### 4.1 阈值按全部历史计算，压缩后反复触发

**发现**：通读 `compactIfNeeded` 时注意到 `rawTokens` 统计的是对话从第一条消息开始的全部单元，没有扣掉已摘要的部分。

**后果**：压缩一次后总量仍超过阈值，每轮都会进入压缩流程；新增内容稍多就再压一小段并调一次模型，压缩次数多、每次很小，阈值失去意义。

**修复**：阈值改为 `摘要 token + liveUnits 的 token`。压缩后有效占用远低于阈值，不会重复触发。

### 4.2 `firstKeptMessageId` 为 null 时从头重新摘要

**发现**：`indexForId(units, null)` 返回 0。当切点之后只剩任务记录、没有聊天消息可标记时，`firstKept` 就是 null，下一次压缩的起点于是回到对话开头。

**后果**：已摘要过的内容被再次送进模型；且聊天历史在 null 时改用 `lastSummarizedAt` 过滤，与压缩起点的判断标准不一致。另外 `chatHistory` 用的 `listChatMessagesAfter` 是严格大于边界，导致边界消息本身从历史里消失。

**修复**：删除 `indexForId`，压缩起点和阈值统计统一走 `liveUnits()`；`lastSummarizedAt` 改存最后一条被摘要单元的 `createdAt`（不再用压缩执行时的当前时间，避免压缩期间新到的消息被误判为已摘要）；`chatHistory` 改为包含边界消息。

### 4.3 token 估算对中文偏低 2–4 倍

**发现**：`estimateTokens` 是 `字符数 / 4`，中文每字只按 0.25 token 计；真实分词里中文接近每字 1 token。

**后果**：预算、阈值和 `tokensAfter` 在中文对话里系统性偏低，压缩触发偏晚。

**修复**：逐字估算，中日韩字符计 1 token、其余计 0.25；`clipText` 同步改为按 token 截断。

### 4.4 摘要截断切掉的是最有用的尾部

**发现**：结构化摘要是整段渲染再整体截断，截断从末尾开始；而渲染顺序是目标 → 约束 → 事实 → 决策 → 已完成 → 阻塞 → 下一步 → 待确认，最末尾的"下一步""待确认"最先被截掉。

**修复**：新增 `fitSummary()`，按优先级装入预算（目标 → 下一步 → 阻塞 → 待确认 → 约束 → 决策 → 已完成 → 事实），列表类条目保留最新；输出顺序保持不变。

### 4.5 摘要模型不返回 JSON 时，文本与结构化数据脱节

**发现**：摘要由模型生成，提示词要求只输出 JSON，但模型可能返回普通文本。`compact()` 里的合并逻辑是：

```ts
const summaryData = generated.data ? mergeCompleted(previous, generated.data, covered) : previous;
```

解析失败时保留旧的 `summaryData`。

**后果**：`summary` 文本已换成新内容（描述本轮覆盖的单元），`summaryData` 却还是上一轮的旧数据。任务账本过滤依赖 `summaryData.completed`，于是程序认为"任务 A 已在摘要里"而摘要文本里实际写的是任务 B，两者静默脱节。

**修复**：解析失败就把 `summaryData` 置为 null——明确承认"本轮没有结构化数据"。过滤逻辑遇到 null 视为空集合，所有任务照常显示，宁多勿漏；下一次压缩从空结构开始增量合并。`conversation.context.compacted` 事件新增 `structured` 字段记录本次摘要是否结构化。

### 4.6 分块超过上限时静默丢数据

**发现**：分块循环里有 `if (chunks.length >= MAX_CHUNKS) break;`，攒够 32 块后剩余单元不进任何块，摘要模型根本没见过它们。但 `compact()` 不知道这件事，仍把边界设在理想切点。

**后果**：被丢弃的单元既不在摘要里（模型没见过），也不在有效原文里（边界已越过），渲染时凭空消失，没有任何报错。大窗口模型（阈值 800k token）一次压缩的内容很容易超过 32 块上限，这是真实场景而非理论边界。

**修复**：`chunkUnits` 明确返回实际会进入摘要的单元集合（`included`，由已生成的块反推）；`compact()` 用它作为真正的覆盖范围，覆盖列表、边界、`tokensAfter` 都按它计算。超出上限的单元留在有效区间，等下一轮压缩继续处理——宁可少压一点、下次再压，也不假装压完了。事件新增 `truncated` 字段。

## 5. 验证

- `apps/server/src/conversation-context.test.ts` 从 3 个用例扩充到 10 个，新增：压缩后不重复触发、null 边界只摘要边界之后的消息、边界消息出现在历史里、中文 token 估算、摘要按优先级保留、纯文本回退后 `summaryData` 为 null 且第二轮压缩正常、分块超限时未摘要单元保留在历史中。
- `npm run typecheck` 通过。

## 6. 未解决问题

- **并发压缩使用过期快照**：`compactIfNeeded`/`compactNow` 在拿锁之前收集单元，排队的压缩基于旧快照计算，期间新到的消息可能漏进本轮覆盖范围。
- **渲染路径重复加载**：每次 `renderForChat` 都全量加载消息和任务，`renderTaskBrief` 里还有循环内 `tasks.find`，均为 O(n²)。
- **阈值比例仍为窗口的 80%**：本轮只修正了"统计什么"，未调整 `conversationCompactRatio` 本身；长对话每次带进新任务的历史量仍偏大。
- **`summaryData` 保存完整结构而 `summary` 是按预算渲染的文本**：文本是数据的确定性视图，属可接受的不一致，但若后续在界面展示数据，需明确以哪个为准。
