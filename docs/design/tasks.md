# 任务与持久执行

<p class="lead">Hearth 不把一次请求当成一段临时对话，而是把它变成可以跨重启、休眠和网络中断继续存在的任务。用户看到的是目标和进度，系统保存的是工作单元、执行尝试、证据和恢复路径。</p>

## 设计目标

一个任务要有清楚的目标、验收方式、截止时间、预算和取消入口。任务可以被拆成多个工作单元，每个工作单元只允许一个执行者推进；每次实际尝试都要留下输入、结果、产物、失败原因和是否可以继续的记录。

目标不是任务标题里的一句话，而是独立保存的契约。验收条件、证据要求、预算、截止时间、停止条件和复核策略随目标一起保存；调度器在关闭目标型任务前生成完成报告，缺少证据时只能保持等待、受阻或转人工。完整边界见[目标、完成判定与证据](/design/goals-and-evidence)。

任务状态必须对用户诚实。排队、执行、等待审批、等待输入、重试、失败、暂停和完成是不同的状态，不能用一句“处理中”全部覆盖。用户要能看到为什么停、停了多久、接下来会发生什么，以及是否需要自己介入。

持久执行要覆盖真实故障：服务重启、电脑休眠、网络断开、执行器崩溃、外部服务超时、设备离线和版本升级。恢复后系统要重新确认目标和当前状态，不信任旧的自然语言“已完成”，也不在没有核对的情况下重复产生外部副作用。

任务图用于表达依赖、并行、汇合、补偿和人工节点。第一阶段不追求完整的工作流平台，只实现能支撑真实任务的顺序、并行、等待和恢复，避免为了架构完整性引入难以维护的重型引擎。

## 设计取舍

任务、工作单元、执行尝试和产物分开保存。任务描述用户要的结果，工作单元描述被授权的一小段工作，执行尝试描述某一次实际运行，产物和回执描述真正交付了什么。把它们混成一个对象，会让重试、预算和审计都变得混乱。

事实记录优先于内存状态。每次状态变化都先写入本地记录，再更新界面和通知；界面只做投影，崩溃后可以从记录重建。早期采用单进程、单写者和本地数据库，用明确的定时器、待办队列和检查点完成恢复，不提前拆微服务。

| 取舍 | Hearth 的选择 | 代价与控制 |
|---|---|---|
| 工作流实现 | 显式状态机和简单任务图 | 复杂流程需要手工建模，但行为容易验证和恢复 |
| 执行权 | 同一工作单元只有一个有效执行者 | 需要租约和过期回收，但能避免两个执行器同时写入 |
| 失败处理 | 先验证，再决定重试、换执行器或转人工 | 恢复路径更多，但不会用盲目重试制造重复副作用 |
| 长任务 | 保存检查点和中间产物 | 需要更多存储和清理规则，但休眠和重启后可以继续 |
| 预算 | 每级都有硬上限和取消路径 | 任务可能需要用户追加预算，但不会静默透支 |
| 外部结果不确定 | 先对账，不直接重试 | 需要人工或连接器核对，但能避免重复发送或重复写入 |

旧执行者的结果不能覆盖新状态。工作单元被重新分配后，之前执行者提交的迟到结果只能作为证据保留，不能直接推进任务；需要合并时由当前执行路径重新验证。

恢复不是简单重跑。进程崩溃后从检查点继续，网络中断后保留待发动作并按同一标识重投，执行器超时后保存工作区并判断是否换执行方式，设备离线时进入设备队列，外部结果不确定时进入核对状态。每种恢复都要给用户一个可理解的原因和下一步。
