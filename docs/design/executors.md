# 执行器与路由

<p class="lead">Hearth 不把所有工作交给一个万能模型。通用推理、代码执行、连接器、浏览器、桌面操作、文档处理和人的判断各有边界，系统根据任务需要选择最合适的一种或几种能力。</p>

## 设计目标

执行器要能把一个工作单元真正做完，并返回结构清楚的结果：产物在哪里、依据是什么、哪些步骤成功、哪些步骤失败、是否产生了外部副作用、下一步应该验证还是转人工。执行器还要支持取消、超时、恢复和预算限制，不能一旦启动就无法收回。

不同任务需要不同能力。代码、长文档和复杂研究适合能力更强、工作区更完整的执行器；邮件、日历和云盘优先使用有明确接口的连接器；没有接口的网站使用浏览器；没有网页入口的软件使用桌面操作；解析、转换、表格和对账优先使用确定性的文档数据处理；需要承担责任的价值判断交给用户。

路由的目标不是“永远先用某个工具”，而是在硬约束下选择最可能成功、风险可控、成本合理的路径。权限、数据驻留、可逆性和安全等级是硬约束，成功率、延迟和费用是在满足硬约束之后的优化目标。

执行器之间要能协作，但不共享隐式状态。一个任务可以由浏览器取回资料、通用模型归纳、文档执行器生成表格、代码执行器完成复杂处理，最后由用户审批并由连接器发送。每一步都应说明输入、输出和负责范围，避免一个执行器把自己的猜测当成另一个执行器的事实。

## 设计取舍

Hearth 选择多个专长执行器并列，而不是一个无限扩展能力的超级代理。这样可以把权限、隔离、预算和失败恢复放在清楚的边界里，也可以根据真实数据替换表现不好的路径。

| 执行器 | 更适合 | 不适合 |
|---|---|---|
| Hearth 原生 | 通用任务的完整工具循环：读取资料、联网、写文件、暂停补问和恢复 | 需要完整仓库语义或多文件工程验证时 |
| Codex | 多文件、代码、长文档、复杂研究和深度写作 | 需要长期在线监听、低成本高频响应 |
| 连接器 | 邮件、日历、云盘、即时消息、工单等有接口的系统 | 没有接口、需要操作图形界面的软件 |
| 浏览器 | 网页研究、登录态、表单和软件即服务 | 高敏感凭据直接暴露、不可审计的批量操作 |
| 桌面操作 | 没有开放接口的本地软件和跨应用流程 | 需要绝对确定性和高吞吐的重复任务 |
| 文档与数据 | 解析、转换、表格、对账和确定性处理 | 开放式判断、复杂跨系统协作 |
| 人工 | 价值判断、责任承担、异常接管和审批 | 高频、低价值、已经可以自动验证的工作 |

路由顺序不是固定等级。能规则、脚本或官方接口完成的工作不调用模型；需要外部数据时先找连接器，没有连接器再考虑浏览器或桌面；确定性文档处理不交给生成模型；长链路和复杂产物再选择高能力执行器。同一任务可以在中途换执行器，但换执行器必须保留输入、预算、权限和当前证据。

当前注册表包含七个执行器，并由同一套启动解析、健康检测、托管安装和设置界面管理：

| 执行器 | 接入方式 | 适用边界 |
|---|---|---|
| `native` | Hearth 内置单 Agent 工具循环 | 通用任务、资料读取、文件交付、暂停补问和恢复 |
| `codex` | 读取本机 Codex Profile 和认证 | 多文件代码、仓库、测试、构建和 GitHub 工作区 |
| `hermes` | `PATH` 中的 `hermes` 命令或自定义命令 | 通用代理、多步工具调用和自动化流程 |
| `qoder` | `@qoder-ai/qoder-agent-sdk`，复用本机 qodercli 登录或 PAT | 编码、工作区和会话续跑 |
| `workbuddy` | `@tencent-ai/codebuddy-code`，复用本机登录 | 编码、工作区和会话续跑 |
| `zcode` | ZCode 桌面内置 `zcode.cjs`，以实验方式接入 | 本机 ZCode 工作区和一次性 JSON 执行 |
| `kimi` | `@moonshot-ai/kimi-code` 的 stream-json 模式 | 编码、工作区和非交互批量执行 |

原生执行器由 Hearth 自己实现单 Agent 工具循环，包含预算、检查点、等待用户补充和恢复；它不是一段转发提示词。执行器不会因为一次失败而静默替换身份，实际执行器会写入运行记录和产物清单。需要联网或工程工作区权限的任务先在聊天中生成提案，用户确认后才进入队列。

设置页的“执行器管理”从注册表生成七个纵向卡片，每张卡片统一提供安装、检测、命令或脚本路径、并发数和诊断信息。全局“优先执行器”只作为新对话的初始值；对话输入框的选择器可以覆盖它。选择不可用或缺少任务所需能力时，路由先回到任务原始匹配的执行器，再按注册表顺序寻找可用项。

## 接入一个新执行器

新增执行器不使用分叉的特殊路径，而是沿同一条注册表链路完成：

1. 在 `packages/core/src/types.ts` 的 `EXECUTOR_IDS` 中增加稳定 ID，让会话设置、并发、运行记录和 API 校验自动获得该字段。
2. 在 `apps/server/src/executors.ts` 增加名称、说明、能力、Provider 和是否支持续跑的描述；如果它能读取本地 GitHub 工作区，把它加入对应能力列表。
3. 在 `apps/server/src/executor-runtime.ts` 增加启动解析：优先使用用户配置路径，其次托管安装，再检测全局安装和 `PATH`；同时提供版本探测和健康状态。
4. 在 `apps/server/src/executor-install.ts` 增加固定版本的包规格。无法托管安装的桌面应用应明确返回不支持，并给出检测或手工路径提示。
5. 在 `apps/server/src/external-executor.ts` 增加参数构造和流式输出解析，把最终文本、用量、会话 ID、退出码和错误统一成 `ExternalRunResult`。
6. 在 `apps/server/src/executor-adapter.ts` 注册适配器。外部 CLI 默认复用 `ExternalExecutorAdapter`，把任务提示词、工作区、权限模式、预算和上一次会话 ID 传给执行器。
7. 补充测试：launch 解析、健康探测、安装任务、参数与事件解析、偏好路由和回退。前端设置页和执行器选择器从 `/api/executors` 自动渲染，不需要再写一套开关。

这条流程的约束是：执行器只能返回结果和证据，不能直接改任务状态；外部副作用仍由 Hearth 的审批和效果账本处理；凭据留在本机 CLI 或环境变量中，不写入任务上下文。

执行器的输出契约统一，但执行方式不统一。系统关心的是结果类型、证据、产物、失败分类和可恢复性，不关心某个执行器内部用了什么模型或界面。这样可以在不改变任务层的前提下替换模型、增加新工具或降级到人工。

路由结果要用真实数据更新。历史成功率、失败类型、人工接管率、延迟和成本都应该进入选择依据；一次演示成功不能证明某个执行器长期更好。高风险动作的权限和数据范围优先于速度与费用，不能用更高的成功率抵消越权风险。
