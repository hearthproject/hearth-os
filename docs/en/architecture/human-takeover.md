# Human Takeover and Approval

<p class="lead">Humans are not a patch applied after failure, but first-class participants in the execution system. Approvals, takeovers, and human error must all be designed for.</p>

## Human Executor and Takeover

Humans are not a patch applied after failure, but a first-class executor of the system.

### Approval Card

Approvals must let the user decide within ten seconds:

- What is about to be done;
- Which account is used;
- The target recipient/file/repository/calendar/resource;
- The content and attachments;
- Reversibility;
- How failure and compensation work;
- The approval's validity period and scope.

### Takeover Protocol

- Show the current browser/desktop;
- Clearly state what the user needs to do;
- Pause automated input;
- Allow actions, annotations, and supplementary information;
- Record the state before and after takeover;
- Support handing back, narrowing scope, and termination.

### Human Error Is Also Input

User rejections, modifications, revocations, and takeovers are not noise, but important samples for evaluation and skill improvement; however, user corrections must not automatically become higher privileges.

## Phase Mapping

| Executor | First Appearance |
|---|---|
| Codex | Phase 1, step 1.3 |
| Native (thin layer) | Phases 1–2 |
| Connector | Phase 2 |
| Browser | Phase 2 |
| Document/Data | Phase 2 |
| GUI + Human real-time takeover | Phase 3 |

Phase 1 first defines the capability matrix and interface conventions, then uses one execution capability to prove the smallest task loop; later phases add the other executors gradually.
