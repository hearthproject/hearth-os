## What this increment solves

Users see full impact, second confirmation, and compensation for irreversible desktop actions; failure leaves no unknown high-risk state.

Stage 3 follows observation, takeover, low-risk action, and high-risk action; desktop automation that cannot be observed or taken over is not product-ready.

## Before you start

- Stage 1–2 recovery, approval, idempotency, receipts, and browser isolation are stable.
- A dedicated desktop device can pair and has explicit allowed windows, applications, and file scopes.
- GUI tasks run in an isolated desktop and users can pause and take over at any time.
- D3.3 deliverables have passed review; do not enter this increment otherwise.

## Four implementation work packages

> Every work package must produce runnable code, a reproducible check, or a concrete UI result; interfaces alone or pages alone do not count as complete.

### 01 · Isolated desktop and snapshots

Run irreversible or high-impact tasks in an isolated virtual desktop with restricted network, shared folders, and peripherals, and take a recoverable snapshot first. Preserve snapshot and action log after completion or failure until the user confirms impact. Isolation never bypasses approval.

### 02 · Irreversible-action catalog and risk matrix

List deletion, overwrite, send, payment, permission change, and public publishing as irreversible actions, graded by impact, compensability, and observability. Each level defines approval, second confirmation, snapshot, human presence, or prohibition. No high-risk action runs unattended in a proactive loop.

### 03 · Impact preview and second confirmation

Effect Preview shows target, real parameters, expected result, irreversible portion, compensation script, and failure resting state. Require parameter-bound second confirmation; expiry, changed parameters, or a different device invalidates it. Users must understand impact, not merely click Continue.

### 04 · Failure drills and Stage 3 release

Inject window crashes, network loss, snapshot failure, half-complete actions, and interrupted takeover; failure must leave no unknown high-risk state. Complete at least five representative desktop tasks covering takeover, high-risk approval, and recovery. Release notes list prohibited apps, irreversible boundaries, and human fallback.

## Engineering map

### Primary directories and modules

- `apps/agentd` — pairing, capability declaration, health checks, and revocation
- `packages/devices` — device identity, sessions, capability catalog, and online state
- `packages/desktop-observation` — window bounds, screenshots, accessibility tree, and redaction
- `packages/desktop-control` — allowlists, locators, input actions, and pre/postconditions
- `packages/desktop-verification` — screenshot comparison, focus checks, and half-complete detection
- `packages/approval` — desktop Effect Preview, second confirmation, and compensation guidance
- `apps/web` — device page, observation view, live takeover, and recovery

### Key interfaces

| Interface | Contract that must hold |
| --- | --- |
| `DeviceManifest` | deviceId, publicKey, agentdVersion, capabilities, allowedRoots, expiresAt, revocationState; undeclared capabilities cannot be called. |
| `ObservationFrame` | captureId, windowBounds, screenshotRef, accessibilityTree, capturedAt, redactions; capture only the minimum scope required. |
| `DesktopAction` | actionType, targetWindow, locator, preconditions, expectedPostconditions, riskLevel, timeout; policy checks precede execution. |
| `DesktopReceipt` | actionId, beforeRef, afterRef, verification, partialState, compensation, approvalId; failure preserves recoverable evidence. |

### Shared verification commands

```bash
pnpm test:device: pairing, capability escalation, offline, revocation, and session expiry
pnpm test:desktop: observation, takeover, focus changes, half-complete, and compensation
pnpm test:desktop-fault: window drift, vanished elements, input contention, and crashes
pnpm eval:computer: at least eight real desktop tasks and failure samples
```

## Acceptance rehearsal

1. Start hearthd from a clean data directory, open the [D3.4 page](/en/delivery/stage-3/d3-4), and confirm it relies on no browser cache or hand-seeded data.
2. Complete the four work packages in order: Isolated desktop and snapshots; Irreversible-action catalog and risk matrix; Impact preview and second confirmation; Failure drills and Stage 3 release. Preserve the matching test output, screenshot, or artifact version after each package.
3. Reproduce the failure case "Window or element mismatch". The page must show "The task pauses with the current screenshot and the element that needs confirmation.", then recover with "Relocate, request takeover, or adjust the allowlist; never click coordinates blindly."; no duplicate effect or unregistered state is allowed.
4. Restart the service and reopen the task. Runtime state, approvals, artifacts, and recovery entry points must all come from durable projections rather than the current page.
5. Run the shared verification commands above and export the evidence. The completion gate is: Five representative desktop tasks complete; takeover and high-risk approval work; no vault or system-settings overreach; failure leaves no half-complete high-risk state; users understand undo/compensation.

## Failure and recovery

| Case | User sees | Recovery |
| --- | --- | --- |
| Window or element mismatch | The task pauses with the current screenshot and the element that needs confirmation. | Relocate, request takeover, or adjust the allowlist; never click coordinates blindly. |
| Automatic input contends with the user | Automatic input pauses immediately and control goes to the user. | Wait for hand-back and confirm focus, window, and next step. |
| A high-risk action is half complete | The task shows Needs inspection, hides continue, and preserves the snapshot. | Recover with compensation or takeover and record the remaining impact. |

## Out of scope

- Do not automate when observation, verification, or takeover is unavailable.
- Do not read password vaults, change system security settings, or operate unauthorized windows.
- Do not treat one successful coordinate click as general GUI capability.
