# D3.1 · Device agentd and visibility

<p class="lead">Turn a desktop into an identifiable, authorizable, revocable execution node before discussing GUI actions.</p>

## What this increment solves

Users can see a trusted desktop come online, its capabilities, and whether it can currently run GUI tasks.

Stage 3 follows observation, takeover, low-risk action, and high-risk action; desktop automation that cannot be observed or taken over is not product-ready.

## Before you start

- Stage 1–2 recovery, approval, idempotency, receipts, and browser isolation are stable.
- A dedicated desktop device can pair and has explicit allowed windows, applications, and file scopes.
- GUI tasks run in an isolated desktop and users can pause and take over at any time.

## Implementation steps

1. Implement device pairing, agentd registration, and device identity storage.
2. Create a capability catalog for windows, files, keyboard, mouse, and applications.
3. Add health checks, local permission declarations, and a device detail page.
4. Implement disconnect, revocation, and audit linking devices to tasks.
5. Reject assignment when capabilities mismatch and show the missing capability.
6. Verify agentd cannot access undeclared capabilities and offline devices have explicit state.

## Data and interface contracts

| Checkpoint | Must hold |
| --- | --- |
| Device capability | agentd declares window, file, keyboard, mouse, and app capabilities at registration; undeclared capabilities cannot be called. |
| Observation and takeover | Screenshots, accessibility tree, and window bounds form auditable observation; takeover pauses automatic input. |
| Action verification | Every GUI action has before/after state, bounds, screenshot/accessibility evidence, and half-complete detection. |
| Safety boundary | Password vaults, system security settings, non-allowlisted apps, and irreversible actions are denied by default. |
| High-risk execution | Irreversible or high-impact desktop actions require isolation, second confirmation, and a compensation/snapshot path. |

## Deliverables

- Device pairing flow
- Capability catalog and device detail
- Disconnect/revoke demo
- Undeclared-capability test

## Verification checklist

- [ ] A device registers, is visible, and can be revoked; mismatched tasks are not assigned; offline devices have explicit state; agentd cannot exceed declared capability.
- [ ] Deliverables match the contracts and task-card projection with no unregistered field or state.
- [ ] At least one failure path has an actionable recovery, and key actions leave audit events.
- [ ] The demo needs no manual database edit, terminal-only stitching, or permanent mock.

## Failure and recovery

| Case | User sees | Recovery |
| --- | --- | --- |
| Window or element mismatch | The task pauses with the current screenshot and the element that needs confirmation. | Relocate, request takeover, or adjust the allowlist; never click coordinates blindly. |
| Automatic input contends with the user | Automatic input pauses immediately and control goes to the user. | Wait for hand-back and confirm focus, window, and next step. |
| A high-risk action is half complete | The task shows Needs inspection, hides continue, and preserves the snapshot. | Recover with compensation or takeover and record the remaining impact. |

## Out of scope

- Do not automate when observation, verification, or takeover is unavailable.
- Do not read password vaults, change system security settings, or operate unauthorized windows.
- Do not treat one successful coordinate click as general GUI capability.
