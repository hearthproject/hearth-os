## What this increment solves

A candidate passes evaluation, Canary, and limited real use to promote; regressions roll back with a reason.

Stage 5 makes memory correctable and forgettable before making skills evaluable and rollbackable; no unexplained provenance or authority change reaches production.

## Before you start

- Stage 1–4 tasks, approval, verification, proactivity, and cross-device entry are stable.
- The boundary for remembered facts, preferences, experience, and sensitive data is explicit.
- Every skill change has a control evaluation, version, permission intersection, and rollback path.
- D5.3 deliverables have passed review; do not enter this increment otherwise.

## Four implementation work packages

> Every work package must produce runnable code, a reproducible check, or a concrete UI result; interfaces alone or pages alone do not count as complete.

### 01 · Promotion state machine and authority intersection

Implement Draft → Evaluated → Shadow → Canary → Promoted → Rolled back, requiring reviewable evidence at each transition. Effective authority is the intersection of parent task, user Mandate, skill manifest, and environment policy. Any reduction applies immediately; self-evolution is never a privilege path.

### 02 · Versions, signatures, and runtime selection

Skill versions are immutable and signed. Runtime selects by task, capability, and evaluation result, never defaulting to the newest candidate. Rollback only switches a pointer and preserves events; old versions remain verifiable. Reject invalid signatures, stale evaluations, or changed manifests.

### 03 · Skill UI and user explanation

The skill page shows current version, candidate differences, required authority, evaluation set, Shadow and Canary results, promotion reason, and rollback entry. Users understand why the new method was adopted and what it adds. Candidates without evaluation evidence or authority rationale cannot appear promotable.

### 04 · Full promotion, rollback, and Stage 5 release

Complete at least one real skill promotion from Shadow to limited Canary, then deliberately rehearse rollback and record impact scope. The safety report proves no privilege expansion, no leaked real effect, and no evaluation contamination. Incomplete Stage 5 exits block the multi-device stage.

## Engineering map

### Primary directories and modules

- `packages/memory/core` — five memory classes, write, retrieval, and conflict
- `packages/memory/provenance` — source, confidence, sensitivity, freshness, and recall explanations
- `packages/memory/forget` — index, cache, device propagation, and forgetting audit
- `packages/memory/browser` — browse, correct, delete, and export memory
- `packages/evolution/trajectory` — capture, replay, redaction, and sample stratification
- `packages/evolution/skills` — manifest, authority, version, signature, and runtime selection
- `packages/evolution/evaluation` — evaluation sets, baseline, Shadow, Canary, and rollback

### Key interfaces

| Interface | Contract that must hold |
| --- | --- |
| `MemoryRecord` | memoryId, kind, value, provenance, confidence, sensitivity, observedAt, updatedAt, expiresAt; conflict never silently overwrites. |
| `ForgetRequest` | targetIds, scope, reason, requestedAt, propagationState, auditId; deletion propagates to indexes, caches, and devices. |
| `SkillManifest` | skillId, version, inputs, outputs, requiredCapabilities, evaluationRef, signature, status; authority is intersection only. |
| `EvolutionDecision` | candidateId, stage, baseline, shadowResult, canaryResult, permissionDelta, rollbackRef; every promotion is traceable. |
| `TrajectoryRecord` | taskId, steps, toolCalls, inputsDigest, results, failureClass, consent, redactions; replay cannot cause external effects. |

### Shared verification commands

```bash
pnpm test:memory: write, recall, conflict, correction, forgetting, and project isolation
pnpm test:poison: prompt injection, forged provenance, privilege escalation, and memory poisoning
pnpm test:evolution: authority intersection, Shadow, Canary, promotion, and rollback
pnpm eval:skills: same-task candidate versus baseline with contamination defenses
```

## Acceptance rehearsal

1. Start hearthd from a clean data directory, open the [D5.4 page](/en/delivery/stage-5/d5-4), and confirm it relies on no browser cache or hand-seeded data.
2. Complete the four work packages in order: Promotion state machine and authority intersection; Versions, signatures, and runtime selection; Skill UI and user explanation; Full promotion, rollback, and Stage 5 release. Preserve the matching test output, screenshot, or artifact version after each package.
3. Reproduce the failure case "A wrong memory is recalled". The page must show "The recall card shows source and reason; the user can correct or delete it.", then recover with "Update memory, rebuild indexes, and record the correction event."; no duplicate effect or unregistered state is allowed.
4. Restart the service and reopen the task. Runtime state, approvals, artifacts, and recovery entry points must all come from durable projections rather than the current page.
5. Run the shared verification commands above and export the evidence. The completion gate is: All Stage 5 exits hold; one skill has control evaluation, promotion, and rollback records; no security regression; users understand why the new method is used.

## Failure and recovery

| Case | User sees | Recovery |
| --- | --- | --- |
| A wrong memory is recalled | The recall card shows source and reason; the user can correct or delete it. | Update memory, rebuild indexes, and record the correction event. |
| Forgetting did not propagate | The page shows Forgetting incomplete and blocks reliance on it. | Retry index cleanup, device sync, and cache invalidation before marking complete. |
| A candidate expands permissions | Evaluation flags the overreach and rejects promotion. | Narrow the manifest or redesign the skill to preserve the permission intersection. |

## Out of scope

- Do not auto-launch a skill without provenance, evaluation, or rollback.
- Do not let memory poisoning change permission, approval policy, or system facts.
- Do not replace repeatable evaluation with model self-assessment.
