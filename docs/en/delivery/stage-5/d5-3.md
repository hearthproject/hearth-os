## What this increment solves

Repeated work begins to yield reusable candidate methods; users see what a candidate does, its permissions, and whether it beats the current method.

Stage 5 makes memory correctable and forgettable before making skills evaluable and rollbackable; no unexplained provenance or authority change reaches production.

## Before you start

- Stage 1–4 tasks, approval, verification, proactivity, and cross-device entry are stable.
- The boundary for remembered facts, preferences, experience, and sensitive data is explicit.
- Every skill change has a control evaluation, version, permission intersection, and rollback path.
- D5.2 deliverables have passed review; do not enter this increment otherwise.

## Implementation steps

1. Implement trajectory capture and replay with tool calls, inputs, results, and failure samples.
2. Define skill manifests, permission declarations, versions, and evaluation metadata.
3. Generate candidates from success and failure trajectories without touching production skills.
4. Create evaluation sets, baseline comparison, and contamination defenses.
5. Run Shadow mode with no real external side effects.
6. Show candidate differences, permissions, and gains; verify no cherry-picked evidence.

## Data and interface contracts

| Checkpoint | Must hold |
| --- | --- |
| Memory provenance | Every memory records source, confidence, sensitivity, freshness, version, and recall reason. |
| Forgetting propagation | Deletion and forgetting create tombstones and propagate to indexes, caches, and relevant devices. |
| Skill permissions | A candidate skill can only inherit or narrow existing permissions; evolution cannot expand authority. |
| Repeatable evaluation | Evaluation sets, baselines, failure samples, and run configuration repeat; improvement is not compared only with an old build. |
| Rollbackable promotion | Shadow, Canary, Promote, and Rollback are recorded, and a regression can restore the previous version. |

## Deliverables

- Trajectory capture/replay
- Skill manifest and permissions
- Evaluation set and baseline
- Shadow run record

## Verification checklist

- [ ] Evaluation repeats; candidates do not expand permissions; Shadow creates no real side effect; users see differences; no cherry-picking fakes a gain.
- [ ] Deliverables match the contracts and task-card projection with no unregistered field or state.
- [ ] At least one failure path has an actionable recovery, and key actions leave audit events.
- [ ] The demo needs no manual database edit, terminal-only stitching, or permanent mock.

## Failure and recovery

| Case | User sees | Recovery |
| --- | --- | --- |
| A wrong memory is recalled | The recall card shows source and reason; the user can correct or delete it. | Update memory, rebuild indexes, and record the correction event. |
| Forgetting did not propagate | The page shows Forgetting incomplete and blocks reliance on it. | Retry index cleanup, device sync, and cache invalidation before marking complete. |
| A candidate expands permissions | Evaluation flags the overreach and rejects promotion. | Narrow the manifest or redesign the skill to preserve the permission intersection. |

## Out of scope

- Do not auto-launch a skill without provenance, evaluation, or rollback.
- Do not let memory poisoning change permission, approval policy, or system facts.
- Do not replace repeatable evaluation with model self-assessment.
