## What this increment solves

A user connects one real email, calendar, or document account, lets Hearth read a scoped range, and sees source, time, and original citation on the task card.

Stage 2 moves from read-only access toward real writes. Every new authority must first prove provenance, revocation, approval, and receipts still hold.

## Before you start

- Stage 1's local MVP, two task families, approval, idempotency, receipts, and recovery are stable.
- A real email, calendar, document, or data account is scoped for the first user, with a test account available.
- Connectors request least privilege only; every write has preview, approval, and a receipt.

## Implementation steps

1. Connect one Connector with least-privilege OAuth scopes and short-lived credentials.
2. Implement Source normalization, deduplication, cursors, rate limits, and expiry handling.
3. Build source projection and detail UI showing account, object, time, and citation scope.
4. Add connector health, disconnect, and revoke actions; revocation immediately affects later reads.
5. Demonstrate one read-only research task with real, redacted objects without exposing raw credentials.
6. Confirm tasks cite only authorized scope and every source traces back to the original object.

## Data and interface contracts

| Checkpoint | Must hold |
| --- | --- |
| Sources and authority | Every Source records account, object ID, time, scope, citation, and revocation state; tasks never exceed authorized scope. |
| Connectors | OAuth uses least-privilege scopes and short-lived credentials; sync has cursors, deduplication, rate limits, and health checks. |
| Write actions | Email, calendar, and sharing writes pass through Connector Effect, Effect Preview, outbox, and Receipt. |
| Context boundary | Accounts, projects, and tasks never leak into each other; only the minimum necessary content enters a Context Pack. |
| Uncertain results | Timeout, network loss, or unknown external state requires reconciliation before retry. |

## Deliverables

- One real read-only connector
- Source projection and detail page
- OAuth scope list
- Revocation and expiry demo

## Verification checklist

- [ ] Read-only sync works; users can revoke the connection; tasks reference only authorized scope; sources trace to originals; the UI exposes no raw credentials.
- [ ] Deliverables match the contracts and task-card projection with no unregistered field or state.
- [ ] At least one failure path has an actionable recovery, and key actions leave audit events.
- [ ] The demo needs no manual database edit, terminal-only stitching, or permanent mock.

## Failure and recovery

| Case | User sees | Recovery |
| --- | --- | --- |
| A connector expires or is revoked | The task asks for reconnection and preserves drafts and completed steps. | Reauthorize and continue without replaying successful external actions. |
| Page content tries to expand authority | The task pauses, marks the content as untrusted, and asks the user to confirm. | Drop the injected instruction, preserve source evidence, and regenerate a safe plan. |
| A write result is unknown | The UI shows Reconciling, neither success nor blind retry. | Query the test account or external system, then write a receipt or compensate. |

## Out of scope

- Do not expand channels before one connector proves permission, idempotency, and receipt behavior.
- Do not automatically perform high-risk submissions, public publishing, or irreversible sharing.
- Do not let page content, attachments, or model output change authority.
