## What this increment solves

Proactive mode works quietly and appears only when needed; users can predict interruptions and downgrade at any time.

Stage 4 is not about background uptime but doing the right thing at the right time with acceptable interruption, built on existing recovery and approval.

## Before you start

- Stage 1–3 recovery, approval, verification, takeover, and revocation are stable.
- Allowed triggers, time windows, budgets, and quiet hours for proactive work are explicit.
- The phone is an entry for viewing, approval, takeover, and initiation, not the default execution authority.
- D4.3 deliverables have passed review; do not enter this increment otherwise.

## Four implementation work packages

> Every work package must produce runnable code, a reproducible check, or a concrete UI result; interfaces alone or pages alone do not count as complete.

### 01 · Attention budget and quiet hours

Set maximum interruptions, quiet hours, and a minimum value threshold by hour, task type, and user state; meetings, focus time, and night are quiet by default. Count real notifications rather than polling cycles. Exhaustion moves candidates to a digest or waiting state; a high-priority label cannot bypass the budget.

### 02 · Interruption measurement and value capture

Record trigger source, interruption count, response time, acceptance or dismissal, completion, manual minutes, and satisfaction for every proactive task. Separate rapid dismissal from actual value, identifying notification fatigue, false triggers, and genuine human-need cases.

### 03 · Shadow and control trials

Shadow mode generates candidates and evaluations without interrupting users or executing external effects. Compare proactive and manual handling of similar tasks on completion, manual minutes, Token, interruption cost, and miss rate with a pre-fixed sample, scorer, and time window.

### 04 · Intensity settings, fallback, and kill switch

Offer off, suggest-only, low, and standard levels, adjustable per trigger. The kill switch immediately stops all proactive loops, withdraws pending candidates, and disables push. Expand, hold, or revert scope from trial evidence rather than short-term satisfaction that hides long-term fatigue.

## Engineering map

### Primary directories and modules

- `apps/hearthd/triggers` — trigger adapters, dedupe keys, candidate generation, and degradation
- `packages/control` — autonomy levels, candidate policy, risk gates, and kill switch
- `packages/attention` — attention budget, quiet hours, notification aggregation, and value scoring
- `apps/pwa` — mobile task cards, approval, takeover, offline read-only, and push entry
- `packages/devices/pairing` — public-key pairing, short sessions, and remote revocation
- `packages/relay` — end-to-end encrypted push, minimal metadata, and replay defense
- `apps/web` — Why now, proactive inbox, intensity settings, and interruption history

### Key interfaces

| Interface | Contract that must hold |
| --- | --- |
| `TriggerEvent` | triggerId, source, dedupeKey, observedAt, payloadRef, scope, sensitivity; duplicate events cannot create duplicate tasks. |
| `ProactiveCandidate` | candidateId, whyNow, proposedAction, autonomyLevel, risk, budget, expiresAt; a candidate is not authority. |
| `AttentionBudget` | window, maxInterruptions, quietHours, valueThreshold, spent; exhaustion must stop proactive interruption. |
| `MobileApproval` | approvalId, nonce, parameterHash, expiresAt, deviceId, signature; offline state cannot confirm external effects. |

### Shared verification commands

```bash
pnpm test:triggers: duplicate, out-of-order, expired sources, and budget exhaustion
pnpm test:attention: quiet hours, aggregation, fatigue thresholds, and kill switch
pnpm test:pwa: offline, disconnect, biometrics, replay, and remote revocation
pnpm eval:proactive: proactive versus manual success, interruption, and satisfaction
```

## Acceptance rehearsal

1. Start hearthd from a clean data directory, open the [D4.4 page](/en/delivery/stage-4/d4-4), and confirm it relies on no browser cache or hand-seeded data.
2. Complete the four work packages in order: Attention budget and quiet hours; Interruption measurement and value capture; Shadow and control trials; Intensity settings, fallback, and kill switch. Preserve the matching test output, screenshot, or artifact version after each package.
3. Reproduce the failure case "Duplicate triggers flood notifications". The page must show "They collapse into one candidate card with duplicate sources marked.", then recover with "Widen the deduplication window, pause triggers, or lower proactivity."; no duplicate effect or unregistered state is allowed.
4. Restart the service and reopen the task. Runtime state, approvals, artifacts, and recovery entry points must all come from durable projections rather than the current page.
5. Run the shared verification commands above and export the evidence. The completion gate is: Average interruptions per task ≤ 1; proactive tasks create real value; no notification fatigue; users can explain why they were notified; pause, revoke, or downgrade works.

## Completion decision

- [ ] Average interruptions per task ≤ 1; proactive tasks create real value; no notification fatigue; users can explain why they were notified; pause, revoke, or downgrade works.
- [ ] Deliverables match the contracts and task-card projection with no unregistered field or state.
- [ ] At least one failure path has an actionable recovery, and key actions leave audit events.
- [ ] The demo needs no manual database edit, terminal-only stitching, or permanent mock.

## Failure and recovery

| Case | User sees | Recovery |
| --- | --- | --- |
| Duplicate triggers flood notifications | They collapse into one candidate card with duplicate sources marked. | Widen the deduplication window, pause triggers, or lower proactivity. |
| A mobile approval is replayed | Approval is rejected with a device/time mismatch. | Require reauthentication and generate a new approval request. |
| Background budget is exhausted | The proactive task stops at the budget boundary and explains why. | Wait for the user to raise budget or resume manually; never overspend. |

## Out of scope

- Do not enable proactive loops without recovery, approval, and verification.
- Do not manufacture tasks or notifications to look active.
- Do not make the phone a long-term credential-holding execution device.
