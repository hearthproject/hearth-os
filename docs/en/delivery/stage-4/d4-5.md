## What this increment solves

A low-interruption personal agent whose critical actions can be handled on a phone.

Stage 4 is not about background uptime but doing the right thing at the right time with acceptable interruption, built on existing recovery and approval.

## Before you start

- Stage 1–3 recovery, approval, verification, takeover, and revocation are stable.
- Allowed triggers, time windows, budgets, and quiet hours for proactive work are explicit.
- The phone is an entry for viewing, approval, takeover, and initiation, not the default execution authority.
- D4.4 deliverables have passed review; do not enter this increment otherwise.

## Implementation steps

1. Run representative Trigger scenarios and real proactive task trials.
2. Evaluate notification fatigue, approval safety, cross-device audit, and budget control.
3. Complete privacy guidance, emergency-stop documentation, and known proactive limits.
4. Verify mobile approval and takeover remain safe under real network fluctuation.
5. Publish the Stage 4 safety and evaluation report with proactive value and interruption cost.
6. Confirm proactive mode pauses, rolls back, and has no budget overspend or runaway loop.

## Data and interface contracts

| Checkpoint | Must hold |
| --- | --- |
| Trigger idempotency | Each source event passes deduplication and window aggregation and cannot create duplicate proactive tasks. |
| Approval safety | Mobile approval binds parameters, nonce, device, and expiry; reauthentication precedes confirmation. |
| Notification privacy | Push contains only redacted summaries, never body text, attachments, credentials, or full task context. |
| Attention budget | Users set quiet hours, interruption limits, and proactivity level; exhaustion stops work immediately. |
| Revocability | Proactive mode, devices, and notification permission can all pause, degrade, or revoke with an audit trail. |

## Deliverables

- Representative Trigger report
- Proactive value/interruption evaluation
- Privacy and emergency-stop guide
- Stage 4 release audit

## Verification checklist

- [ ] All Stage 4 exits hold; mobile approval and takeover are stable; proactive mode pauses and rolls back; no background overspend or runaway loop.
- [ ] Deliverables match the contracts and task-card projection with no unregistered field or state.
- [ ] At least one failure path has an actionable recovery, and key actions leave audit events.
- [ ] The demo needs no manual database edit, terminal-only stitching, or permanent mock.

## Failure and recovery

| Case | User sees | Recovery |
| --- | --- | --- |
| Duplicate triggers flood notifications | They collapse into one candidate card with duplicate sources marked. | Widen the deduplication window, pause triggers, or lower proactivity. |
| A mobile approval is replayed | Approval is rejected with a device/time mismatch. | Require reauthentication and generate a new approval request. |
| Background budget is exhausted | The proactive task stops at the budget boundary and explains why. | Wait for the user to raise budget or resume manually; never overspend. |

## Out of scope

- Do not enable proactive loops without recovery, approval, and verification.
- Do not manufacture tasks or notifications to look active.
- Do not make the phone a long-term credential-holding execution device.
