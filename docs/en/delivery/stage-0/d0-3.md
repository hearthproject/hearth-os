## What this increment solves

Core entities, state transitions, UI projections, event interfaces, and contract tests form an implementable protocol.

Stage 0 produces product truth and implementation contracts. Without real tasks, a clickable prototype, and repeatable evaluation, later work mistakes assumptions for facts.

## Before you start

- An empty repository, a recordable set of real work samples, and one first user willing to keep giving feedback.
- Baselines for fully manual work and direct Codex use are observable before the system exists.
- This stage does not connect real sending, payment, deletion, or system-setting changes.
- D0.2 deliverables have passed review; do not enter this increment otherwise.

## Implementation steps

1. Define the fields and relationships for Event, Task, Ticket, Run, Executor, Approval, Artifact, Receipt, and Budget.
2. Define Task Pack, Result, the failure taxonomy, and the user explanation and recovery action for each failure.
3. Define task-card, approval, and artifact projections so the UI never depends on internal database structure.
4. Set interface boundaries for the Event Log, outbox, lease, schema migration, and SSE.
5. Build a mock server that drives the prototype from one event stream, with contract tests for success and failure paths.
6. Version schemas and degrade unknown states safely so evolution never makes the page pretend to succeed.

## Data and interface contracts

| Checkpoint | Must hold |
| --- | --- |
| Task card projection | The UI consumes only a stable TaskCard projection; it never reads database columns or internal task objects. |
| Event source of truth | Every state change enters an append-only Event Log; the same event stream can rebuild the page. |
| Unknown states | An unrecognized state can only become Needs attention, never Completed or Successful. |
| Contract tests | A mock server and frontend contract tests ship with the schema, and CI blocks regressions. |

## Deliverables

- Domain entities and state machine
- TaskCard/Approval/Artifact contracts
- Mock server and contract tests
- Schema versions and migration notes

## Verification checklist

- [ ] The frontend does not depend on database columns; every core transition has one explanation; schemas are versioned; projections rebuild from events; unknown states become Needs attention.
- [ ] Deliverables match the contracts and task-card projection with no unregistered field or state.
- [ ] At least one failure path has an actionable recovery, and key actions leave audit events.
- [ ] The demo needs no manual database edit, terminal-only stitching, or permanent mock.

## Failure and recovery

| Case | User sees | Recovery |
| --- | --- | --- |
| A prototype state cannot be mapped | The page shows Needs attention and records the unknown projection field and task ID. | Add the mapping, update contract tests, and replay the original path. |
| A real task cannot be accepted | The task stays in the candidate pool with a reason; it never becomes a build commitment. | Clarify inputs, artifacts, or acceptance, or replace the task. |
| Baselines are not comparable | The task stays out of the evaluation set so distorted data cannot prove value. | Recapture manual minutes, success rate, Token usage, and failure type. |

## Out of scope

- Do not build a complete kernel before the interface.
- Do not substitute document completion for a clickable prototype and repeatable evaluation.
- Do not connect real high-risk external side effects.
