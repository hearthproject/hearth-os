## What this increment solves

Users export, back up, restore, and migrate Hearth; failed upgrades roll back with consistent events, memory, and skills.

Stage 6 turns a single-device product into a long-running, portable, revocable personal Agent OS; multi-device extends one logical identity rather than cloning agents.

## Before you start

- Single-device install, recovery, backup, security, and upgrade paths are stable.
- Events, leases, fencing tokens, memory versions, and device identity have stable contracts.
- Multiple devices share one logical identity, event history, memory, and authority without bypassing approval, idempotency, or revocation.
- D6.3 deliverables have passed review; do not enter this increment otherwise.

## Four implementation work packages

> Every work package must produce runnable code, a reproducible check, or a concrete UI result; interfaces alone or pages alone do not count as complete.

### 01 · Encrypted backup and complete restore

A backup contains event range, artifact roots, memory references, skill versions, configuration, and a checksum manifest, encrypted with a separate key. Restore validates version, checksum, and key, then replays events in an isolated directory. Switch to the restored instance only after events, artifacts, memory, and skills verify.

### 02 · Migration manifest and version pinning

Every upgrade produces a MigrationPlan listing source and target versions, schema changes, executor versions, irreversible steps, backup reference, and rollback path. Preflight checks disk, authority, queue, and compatibility. Pin executor versions so restore never silently changes behavior.

### 03 · Upgrade, rollback, and migration verification

Upgrade step by step with checkpoints; failure enters maintenance mode and restores the backup. Rollback returns to a known-good version while preserving failure evidence. After migration, verify event continuity, artifact hashes, memory provenance, skill signatures, and credential references; any mismatch blocks startup.

### 04 · Empty-database drills and user health checks

From an empty database, complete install, task creation, backup, deletion, restore, upgrade, and rollback without manual database edits. The health page shows version, last backup, migration state, known limits, and next action. Acceptance requires events, memory, skills, and credential references to remain consistent after migration.

## Engineering map

### Primary directories and modules

- `apps/hearthd/sync` — event cursors, incremental pull, reconnect, and projection replicas
- `packages/devices/router` — capability catalog, routing, lease, fencing, and single writer
- `packages/devices/security` — remote revocation, key rotation, pairing, and device audit
- `packages/backup` — encrypted backup, restore, export/import, and migration manifest
- `packages/upgrade` — schema migration, version pinning, preflight checks, and rollback
- `apps/hearthd/operations` — scheduling, quotas, watchdog, logging, and maintenance mode
- `apps/web` — device state, health checks, diagnostics export, and recovery

### Key interfaces

| Interface | Contract that must hold |
| --- | --- |
| `SyncCursor` | deviceId, stream, lastEventId, lastSyncedAt, filterHash, resumeToken; reconnect cannot skip events. |
| `DeviceLease` | taskId, deviceId, scope, expiresAt, fencingToken; one execution right has at most one active writer. |
| `BackupManifest` | backupId, schemaVersion, executorVersions, eventRange, artifactRoots, memoryRefs, checksum, encryption; restore must be verifiable. |
| `MigrationPlan` | fromVersion, toVersion, preconditions, backupRef, steps, verification, rollback; upgrades require passing checks. |
| `HealthSnapshot` | serviceState, disk, memory, queueDepth, stuckTasks, lastBackup, knownLimits; user-facing health explanation. |
| `RevocationRecord` | deviceId, reason, requestedAt, sessionsInvalidated, keysRotated, localEraseState, auditId; revocation must be traceable. |

### Shared verification commands

```bash
pnpm test:sync: disconnect, ordering, duplication, cursor loss, and sensitive-field filtering
pnpm test:devices: lease, fencing, offline handoff, revocation, and key rotation
pnpm test:backup: empty install, restore, migration, failed upgrade, and rollback
pnpm test:soak: long run, resource exhaustion, state drift, and automatic recovery
```

## Acceptance rehearsal

1. Start hearthd from a clean data directory, open the [D6.4 page](/en/delivery/stage-6/d6-4), and confirm it relies on no browser cache or hand-seeded data.
2. Complete the four work packages in order: Encrypted backup and complete restore; Migration manifest and version pinning; Upgrade, rollback, and migration verification; Empty-database drills and user health checks. Preserve the matching test output, screenshot, or artifact version after each package.
3. Reproduce the failure case "Sync conflict or offline device". The page must show "The task shows device and sync state and does not mistake offline for failure.", then recover with "Keep the local queue, merge by cursor after reconnect, and prevent duplicate execution."; no duplicate effect or unregistered state is allowed.
4. Restart the service and reopen the task. Runtime state, approvals, artifacts, and recovery entry points must all come from durable projections rather than the current page.
5. Run the shared verification commands above and export the evidence. The completion gate is: Events, artifacts, memory, skills, and credential references verify after migration; rollback works; old data survives; upgrades need no manual database edits.

## Completion decision

- [ ] Events, artifacts, memory, skills, and credential references verify after migration; rollback works; old data survives; upgrades need no manual database edits.
- [ ] Deliverables match the contracts and task-card projection with no unregistered field or state.
- [ ] At least one failure path has an actionable recovery, and key actions leave audit events.
- [ ] The demo needs no manual database edit, terminal-only stitching, or permanent mock.

## Failure and recovery

| Case | User sees | Recovery |
| --- | --- | --- |
| Sync conflict or offline device | The task shows device and sync state and does not mistake offline for failure. | Keep the local queue, merge by cursor after reconnect, and prevent duplicate execution. |
| An old device still has access | Device state says Revocation incomplete and blocks approval and reads. | Invalidate sessions, rotate keys, clear local caches, and verify again. |
| Data is inconsistent after migration | Recovery enters Needs verification and blocks a completion claim. | Compare events, artifacts, memory, and skill manifests, repair, and rerun the drill. |

## Out of scope

- Do not package multiple inconsistent agents as multi-device support.
- Do not excuse duplicate external actions through sync conflicts or offline queues.
- Do not declare v1.0 without migration drills and device revocation.
