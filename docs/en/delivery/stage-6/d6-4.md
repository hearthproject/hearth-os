## What this increment solves

Users export, back up, restore, and migrate Hearth; failed upgrades roll back with consistent events, memory, and skills.

Stage 6 turns a single-device product into a long-running, portable, revocable personal Agent OS; multi-device extends one logical identity rather than cloning agents.

## Before you start

- Single-device install, recovery, backup, security, and upgrade paths are stable.
- Events, leases, fencing tokens, memory versions, and device identity have stable contracts.
- Multiple devices share one logical identity, event history, memory, and authority without bypassing approval, idempotency, or revocation.
- D6.3 deliverables have passed review; do not enter this increment otherwise.

## Implementation steps

1. Implement encrypted backup, full restore, export/import, and a migration manifest.
2. Add schema migration, executor version pinning, and pre-upgrade checks.
3. Implement upgrade rollback and migration verification.
4. Verify events, artifacts, memory, skills, and credential references stay consistent after migration.
5. Provide user-visible health checks and known limitations.
6. Rehearse install, restore, upgrade, and rollback from an empty database.

## Data and interface contracts

| Checkpoint | Must hold |
| --- | --- |
| Synchronized facts | Events sync incrementally by cursor; projections rebuild from events; conflicts have explicit handling. |
| Single writer | Lease and fencing tokens guarantee one execution authority per task; offline queues cannot duplicate side effects. |
| Device revocation | Revocation immediately invalidates sessions, approvals, and read access while retaining audit evidence. |
| Migration integrity | Backup, restore, migration, and upgrade verify events, artifacts, memory, skills, and credential references. |
| Long-running operations | Health checks, quotas, reclamation, maintenance mode, and kill switches are observable and recoverable. |

## Deliverables

- Encrypted backup/full restore
- Schema migration and rollback
- Data export/import
- Empty-database install drill

## Verification checklist

- [ ] Events, artifacts, memory, skills, and credential references verify after migration; rollback works; old data survives; upgrades need no manual database edits.
- [ ] Deliverables match the contracts and task-card projection with no unregistered field or state.
- [ ] At least one failure path has an actionable recovery, and key actions leave audit events.
- [ ] The demo needs no manual database edit, terminal-only stitching, or permanent mock.

## Failure and recovery

| Case | User sees | Recovery |
| --- | --- | --- |
| Sync conflict or offline device | The task shows device and sync state and does not mistake offline for failure. | Keep the local queue, merge by cursor after reconnect, and prevent duplicate execution. |
| An old device still has access | Device state says Revocation incomplete and blocks approval and reads. | Invalidate sessions, rotate keys, clear local caches, and verify again. |
| Data is inconsistent after migration | Recovery enters Needs verification and blocks a completion claim. | Compare events, artifacts, memory, and skill manifests, repair, and rerun the drill. |

## Out of scope

- Do not package multiple inconsistent agents as multi-device support.
- Do not excuse duplicate external actions through sync conflicts or offline queues.
- Do not declare v1.0 without migration drills and device revocation.
