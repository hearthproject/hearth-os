## What this increment solves

A user can create a task in the real Web app, watch it queue, run, and complete, and find it again after refresh or restart.

Stage 1 delivers a real narrow loop first, safe side effects second, and broader task families and recovery last; do not stack modules on an empty kernel.

## Before you start

- Stage 0's 12 tasks, prototype, protocols, evaluation, and safety baseline have passed review.
- The default wedge is research/document work; if the first user mainly needs coding, replace the wedge without changing the vertical structure.
- A local development environment, SQLite, isolated workspaces, and the Web build are available.

## Implementation steps

1. Start a single hearthd process with explicit local port, data directory, health check, and log location.
2. Add SQLite WAL, a minimal Event Log, and rebuildable read projections.
3. Implement the minimum Task/Run state machine; every transition writes an event instead of mutating a status column directly.
4. Use a fake executor to produce real execution events, covering success and at least one failure path.
5. Connect Web task list, detail, creation, and SSE, restoring from durable state after refresh.
6. Provide a minimal CLI for diagnostics, replay, and health checks only, never as the product entry.

## Data and interface contracts

| Checkpoint | Must hold |
| --- | --- |
| Events and recovery | The Event Log is the source of truth; SQLite WAL stores events and projections; SSE resumes after disconnects. |
| State machine | Task/Run changes only through controlled transitions and can be rebuilt after refresh, restart, or crash. |
| Side effects | External actions pass through Effect Preview, outbox, idempotency key, and Receipt; reconcile uncertain results first. |
| Secrets boundary | Secrets never enter task cards, logs, model context, or executor workspaces; only the Broker injects credentials. |

## Deliverables

- Startable hearthd
- Minimal Event Log and projections
- Web create/list/detail/SSE
- Restart-recovery demo and contract tests

## Verification checklist

- [ ] The main path needs no manual database edits; tasks and states survive restart; cards show real rather than static mock state; UI contract tests pass.
- [ ] Deliverables match the contracts and task-card projection with no unregistered field or state.
- [ ] At least one failure path has an actionable recovery, and key actions leave audit events.
- [ ] The demo needs no manual database edit, terminal-only stitching, or permanent mock.

## Failure and recovery

| Case | User sees | Recovery |
| --- | --- | --- |
| Process crash or restart | The detail page shows the last known state, unfinished step, and Continue/Cancel/Retry. | Replay the Event Log and reacquire the lease; never silently drop the task. |
| A duplicate external action | The system shows Reconciling and does not create a second success receipt. | Query the sink by idempotency key, then write the Receipt or start compensation. |
| An uncertain side effect | The task enters Waiting for confirmation and hides automatic retry. | Query the external system or check manually before retry, compensation, or closure. |

## Out of scope

- Do not prove MVP readiness through CLI, logs, or database rows alone.
- Do not expand task families before recovery and approval are stable.
- Do not treat permanent mock output as real execution.
