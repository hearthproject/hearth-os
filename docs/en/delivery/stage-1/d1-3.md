## What this increment solves

Hearth MVP-1 works: create, inspect, cancel, retry, rehearse approval, retrieve artifacts, and recover entirely in the browser.

Stage 1 delivers a real narrow loop first, safe side effects second, and broader task families and recovery last; do not stack modules on an empty kernel.

## Before you start

- Stage 0's 12 tasks, prototype, protocols, evaluation, and safety baseline have passed review.
- The default wedge is research/document work; if the first user mainly needs coding, replace the wedge without changing the vertical structure.
- A local development environment, SQLite, isolated workspaces, and the Web build are available.
- D1.2 deliverables have passed review; do not enter this increment otherwise.

## Four implementation work packages

> Every work package must produce runnable code, a reproducible check, or a concrete UI result; interfaces alone or pages alone do not count as complete.

### 01 · MVP task lifecycle

Complete durable Runs, detail timeline, cancel, retry, failure page, artifact center, and budget limits. All actions work in the browser without opening a terminal.

### 02 · Failure explanation and recovery

Every failure shows what happened, impact, retryability, duplicate-effect risk, and next step. If automatic recovery is unsafe, hand over explicitly instead of spinning.

### 03 · Practice-effect approval loop

Use a local test service or test account to demonstrate Effect Preview, approve, reject, and Receipt. Approval binds action, parameters, scope, and expiry.

### 04 · Ten real tasks and UX closeout

Let the first user complete at least 10 real tasks and record success, manual minutes, Token, failure, and recovery. Fix copy, layout, and state ambiguity that blocks the main path.

## Engineering map

### Primary directories and modules

- `apps/hearthd` — single process, Gateway, Control, Harness, and SSE
- `packages/eventlog` — SQLite WAL, events, projections, migrations, and replay
- `packages/harness` — Ticket, Run, lease, outbox, recovery, and dead letters
- `packages/executors/codex` — Codex adapter, workspace, and structured output
- `packages/policy` — Policy, Mandate, Approval, and risk levels
- `packages/artifacts` — content-addressed artifacts, hashes, versions, and validators
- `apps/web` — task cards, detail/timeline, approval, artifacts, and recovery

### Key interfaces

| Interface | Contract that must hold |
| --- | --- |
| `Run` | runId, ticketId, state, checkpoint, budget, terminalReason; one execution attempt has one terminal state. |
| `Ticket / Lease` | owner, scope, expiresAt, fencingToken; one Ticket has at most one active writer. |
| `TaskPack` | objective, inputs, constraints, outputSchema, acceptance, budget, permissions; the executor stays inside this pack. |
| `Effect / Receipt` | effectIntent, approvalId, idempotencyKey, receipt, reconciliation; reconcile uncertain outcomes instead of blindly retrying. |

### Shared verification commands

```bash
pnpm eval:mvp: compare 10 real tasks against the baseline
```

## Acceptance rehearsal

1. Start hearthd from a clean data directory, open the [D1.3 page](/en/delivery/stage-1/d1-3), and confirm it relies on no browser cache or hand-seeded data.
2. Complete the four work packages in order: MVP task lifecycle; Failure explanation and recovery; Practice-effect approval loop; Ten real tasks and UX closeout. Preserve the matching test output, screenshot, or artifact version after each package.
3. Reproduce the failure case "Process crash or restart". The page must show "The detail page shows the last known state, unfinished step, and Continue/Cancel/Retry.", then recover with "Replay the Event Log and reacquire the lease; never silently drop the task."; no duplicate effect or unregistered state is allowed.
4. Restart the service and reopen the task. Runtime state, approvals, artifacts, and recovery entry points must all come from durable projections rather than the current page.
5. Run the shared verification commands above and export the evidence. The completion gate is: Five representative real tasks pass; three repeat reliably; four critical interruptions recover; the user wants to continue; no uncontrolled real side effect exists.

## Completion decision

- [ ] Five representative real tasks pass; three repeat reliably; four critical interruptions recover; the user wants to continue; no uncontrolled real side effect exists.
- [ ] Deliverables match the contracts and task-card projection with no unregistered field or state.
- [ ] At least one failure path has an actionable recovery, and key actions leave audit events.
- [ ] The demo needs no manual database edit, terminal-only stitching, or permanent mock.

## Failure and recovery

| Case | User sees | Recovery |
| --- | --- | --- |
| Process crash or restart | The detail page shows the last known state, unfinished step, and Continue/Cancel/Retry. | Replay the Event Log and reacquire the lease; never silently drop the task. |
| A duplicate external action | The system shows Reconciling and does not create a second success receipt. | Query the sink by idempotency key, then write the Receipt or start compensation. |
| An uncertain side effect | The task enters Waiting for confirmation and hides automatic retry. | Query the external system or check manually before retry, compensation, or closure. |

## Out of scope

- Do not prove MVP readiness through CLI, logs, or database rows alone.
- Do not expand task families before recovery and approval are stable.
- Do not treat permanent mock output as real execution.
