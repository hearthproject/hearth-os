# Stage 0 · 定义与原型

<p class="lead">先把“为谁做、做什么、怎么验收”钉死，再开始写真实执行内核。Stage 0 的产物必须足以支撑第一个可运行纵向切片，而不是一堆无法落地的概念文档。</p>

## 本模块要回答

- 谁是首位真实用户，第一个高频、可验收的任务楔子是什么？
- Hearth 与直接使用 Codex、聊天助手或自动化脚本相比，独立价值在哪里？
- 任务在创建、执行、审批、失败和恢复时，用户分别看到什么？
- 前后端、执行器、审批和评测依赖哪些稳定契约？

## 前置条件

- 一个空仓库，以及一位愿意提供真实任务和反馈的首位用户。
- 可以记录全人工基线与直接使用 Codex 的基线。
- 暂不接入真实高风险外部副作用。

## 开发步骤

1. **锁定产品楔子。** 选定首位用户、第一个任务族和明确非目标；写出一句话定位与“不做什么”清单。
2. **建立真实任务集。** 收集 20–30 个真实任务，筛出至少 12 个有输入、产物和验收方式的任务，覆盖成功、失败、等待审批和需要接管。
3. **跑基线。** 记录全人工与直接使用 Codex 的人工分钟、成功率、Token、错误类型和用户不满点。
4. **画端到端原型。** 覆盖今日、需要你、产物、设置四个入口，以及排队、执行、审批、需要信息、完成、失败和可恢复状态。
5. **定义核心契约。** 固定 Task、Ticket、Run、Event、Executor、Approval、Artifact、Receipt、Budget 的字段和状态迁移；定义 Task Pack、Result、失败分类与 UI 投影。
6. **搭工程骨架。** 初始化 monorepo、类型检查、lint、测试、CI、ADR 模板、文档目录和 fake executor。
7. **建立评测与安全基线。** 为 12 个任务建立 runner、评分与人工复核；完成威胁模型、风险分级、审批矩阵和秘密处理规则。
8. **做契约演练。** 用 mock server 驱动完整原型流程，确认同一事件流可以重建页面状态，未知状态不会伪装成成功。

## 增量拆分

每个增量现在按四层阅读：结果与门槛 → 四个实施工作包 → 工程落点与接口 → 验收演练。工作包可以拆给不同开发者并行，但必须按依赖顺序合并；只完成一个包不等于完成增量。

| 增量 | 用户可见结果 | 完成证据 |
|---|---|---|
| [D0.1](/delivery/stage-0/d0-1) 产品楔子与任务基线 | 能解释首批用户为什么使用 Hearth | 12+ 个真实任务、双基线、非目标与成功指标 |
| [D0.2](/delivery/stage-0/d0-2) 端到端原型 | 不读说明也能创建任务、审批、查看产物和恢复 | 桌面/手机原型、全部状态、可用性走查 |
| [D0.3](/delivery/stage-0/d0-3) 协议与数据契约 | 原型状态都能映射到稳定字段和事件 | 实体定义、状态机、投影契约、契约测试 |
| [D0.4](/delivery/stage-0/d0-4) 评测、安全与工程基线 | 每个后续增量从第一天就能被验证 | 评测 runner、威胁模型、审批矩阵、CI、fake executor |

## 退出验收

- [ ] 至少 12 个任务有明确输入、产物、验收标准和失败样本。
- [ ] 新用户可以在原型中完成主路径，每个状态只有一个主动作。
- [ ] 页面不依赖内部数据库字段，事件流能重建 UI 投影。
- [ ] 高风险动作已有审批路径；评测可重复运行；CI 能拦截契约和 schema 回归。
- [ ] fake executor 能驱动完整 UI 流程，且没有真实外部副作用。

## 本模块不做

- 不先做完整内核再补界面。
- 不接入真实发送、支付、删除或系统设置修改。
- 不用“文档已写完”代替可点击原型和可重复评测。
