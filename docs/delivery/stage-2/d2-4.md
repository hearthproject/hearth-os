## 这一增量解决什么

用户看到邮件草稿、日历变更或文档分享的完整预览，可以批准或拒绝，并在之后查看回执。

Stage 2 从只读能力逐步走向真实写入。每增加一种权限，都先证明来源、撤销、审批和回执仍然成立。

## 开始前

- Stage 1 的本地 MVP、两个任务族、审批、幂等、回执和恢复路径稳定。
- 已限定首位用户的真实邮箱、日历、文档或数据账户，并准备测试账户。
- 连接器只能申请最小范围；任何写入都必须有预览、审批和回执。
- D2.3 的交付物已经验收；未通过时不进入本增量。

## 实施步骤

1. 实现邮件草稿、日历冲突检查和待审批写入、文档导出/分享。
2. 接入真实 Connector Effect，但全部在测试账户和受限收件人上运行。
3. 用 Effect Preview 展示收件人、时间、内容、范围和撤销/补偿说明。
4. 把审批、outbox 重投、Receipt 对账和失败死信串成完整链路。
5. 验证审批与真实参数绑定，旧审批不能用于新动作。
6. 至少演练一次重复投递、超时和不确定结果，确认不会重复发送或写入。

## 数据与接口契约

| 检查点 | 必须满足 |
| --- | --- |
| 来源与权限 | 每个 Source 记录账户、对象 ID、时间、范围、引用和撤销状态，任务不得越过授权范围。 |
| 连接器 | OAuth 使用最小 scope 和短期凭据；同步具备游标、去重、限流和健康检查。 |
| 写入动作 | 邮件、日历、分享等写入必须经过 Connector Effect、Effect Preview、outbox 与 Receipt。 |
| 上下文边界 | 不同账户、项目和任务之间不串扰；最小必要内容进入 Context Pack。 |
| 不确定结果 | 超时、网络中断和外部状态未知时先对账，不能直接重复发送或写入。 |

## 交付物

- 邮件/日历/文档测试账户闭环
- Effect Preview 示例
- Receipt 对账记录
- 重复投递与不确定结果演练

## 验证清单

- [ ] “读取 → 理解 → 起草 → 审批 → 执行 → 回执”闭环可用；测试账户无重复发送/写入；不确定结果先对账；审批绑定真实收件人、时间、内容和范围。
- [ ] 交付物已经和契约、任务卡投影保持一致，没有未登记的字段或状态。
- [ ] 至少一个失败路径有可操作恢复，关键动作留下审计事件。
- [ ] 演示不依赖手工修改数据库、只在终端拼接命令，或永久 mock。

## 失败与恢复

| 情况 | 用户看到 | 恢复动作 |
| --- | --- | --- |
| 连接器过期或被撤销 | 任务显示重连要求，保留草稿和已完成步骤。 | 重新授权后继续，不重放已成功的外部动作。 |
| 网页内容试图扩大权限 | 任务暂停并提示内容不可信，要求用户确认。 | 丢弃注入指令，保留来源证据并重新生成安全计划。 |
| 写入结果未知 | 显示“等待对账”，不显示成功或允许盲目重试。 | 查询测试账户或外部系统，确认后补写回执或执行补偿。 |

## 本增量不包含

- 不在一个连接器上证明权限、幂等和回执之前扩展多个渠道。
- 不自动执行高风险提交、公开发布或不可逆分享。
- 不让网页内容、附件或模型输出直接改变权限。
