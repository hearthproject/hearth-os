# 验收与证据

<p class="lead">Hearth 不用“页面存在”“代码合并”或“测试通过”冒充交付。验收必须回答三个问题：做了什么、证据在哪里、还有什么没有证明。</p>

## “完成”的定义

一项能力只有同时满足以下条件，才能标记为完成：

1. **有用户可见结果。** 用户能在界面、产物或回执中看到结果，而不是只看到模型说“好了”。
2. **有可复核证据。** 输入、运行记录、产物摘要、审批和外部回执可以追溯。
3. **有失败路径。** 失败会进入可恢复或明确失败状态，不伪造成功，不盲目重试外部动作。
4. **有真实验收。** 至少用真实任务、真实设备或真实账户跑过约定场景；自动测试不能替代真实验收。

## 测试层级

| 层级 | 证明什么 | 不能证明什么 |
|---|---|---|
| 单元测试 | 状态机、预算、权限、提取、加密等纯逻辑 | 真实环境、真实账户、用户是否愿意使用 |
| API / 集成测试 | 服务端路由、投影、审批、备份、同步等代码闭环 | 真实桌面、真实网络、长期运行 |
| 隔离实例运行 | 端到端链路在受控环境中可执行 | 真实用户任务和失败恢复意愿 |
| 真实任务验收 | 约定任务在真实环境中完成并可核对 | 长期稳定性和所有边界 |
| 长期运行验收 | 数周运行、资源漂移、升级回退 | 未覆盖的任务类型 |

当前自动测试基线是 **40 个测试文件、199 个测试**。它覆盖了服务层、API、模型协议、原生工具循环、预算、权限、检查点、提案确认、桌面边界、记忆、方法、同步、安全、备份与运维，但不替代真实验收。

## 证据规则

### 保留失败证据

- 网页访问失败时保留 HTTP 状态、最终 URL、抓取时间和失败原因。
- 任务缺少产物时进入恢复或失败，不把空文件当结果。
- 外部动作结果不确定时先对账，不盲目重试。
- 设备撤销后无法操作要有演练记录，而不是只写“已实现”。

### 外部动作必须可核对

- 外部动作先生成预览。
- 审批绑定参数指纹，只执行一次。
- 效果账本记录执行结果和回执。
- 审批被拒绝或失效时，草稿与任务状态同步更新。

### 不伪造成功

- T04 的 WCAG 页面访问失败被保留为证据。
- T07 因未提交测试文件而未通过，没有推送分支或创建 PR。
- T08 的评论审批仍是 `pending`，没有外部副作用。
- 备份不包含产物正文时，界面和文档都明确说明边界。

## 验收记录模板

每个阶段或工作流完成时，至少保留以下记录：

```text
工作流：
验收日期：
真实环境：
任务数量：
通过 / 失败 / 待批准：
每个任务的输入与输出路径：
失败原因与恢复方式：
外部动作与回执：
仍未证明的边界：
```

## 下一步验收重点

下一轮验收不再增加“看起来完整”的页面，而是补齐：

1. 真实邮件/日历账户与 10–15 个日常内容任务。
2. 至少 5 个真实桌面任务及高风险失败演练。
3. 手机审批/接管与 5–10 个主动任务打扰验收。
4. 错误记忆/错误方法与采用前后生产对照。
5. 双设备、断网、设备丢失和备份恢复演练。
6. 数周连续运行、资源漂移和版本升级回退。

这些项目没有完成前，阶段二至六保持“部分完成”。
