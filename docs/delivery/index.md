# 交付路线与实施计划

<p class="lead">这里只有一套总纲：Stage 0–6 定义能力门槛，35 个 D 增量定义具体施工顺序，每个增量再拆成四个工作包。路线不承诺日期，只承诺每阶段可见的产品结果、验证证据和恢复路径。</p>

## 推进原则

- **Stage 是能力门槛，不是工期。** 可以停留、试用和回退，但不能跳过恢复、界面、验证或安全边界。
- **每个增量都是纵向切片。** 用户结果、界面、持久状态、真实执行、验证与恢复必须同时出现。
- **MVP 尽早出现。** MVP-1 是 Stage 1 的早期出口，不是等项目结束才形成的演示。
- **先窄后宽。** 先让一个任务族真正可依赖，再扩展连接器、桌面、主动性和多设备。
- **安全先于副作用。** 发送、写入、分享、删除和桌面操作必须先有授权、幂等和回执。
- **证据先于宣布。** 阶段是否完成，以真实任务、故障恢复和评测结果判断，不以“代码写完”判断。

## 阶段总览

| 阶段 | 用户得到什么 | 进入下一阶段前必须证明 |
|---|---|---|
| Stage 0 | 可点击的端到端原型 | 产品楔子、12 个真实任务、稳定契约、评测与审批基线 |
| Stage 1 | 本地每天可用的个人任务工作台 | 持久状态、真实 Codex 执行、审批、产物、失败恢复与 MVP-1 |
| Stage 2 | 能处理日常内容工作的 Personal Operator | 连接器闭环、引用来源、文档/数据验证、审批写入与回执 |
| Stage 3 | 能操作桌面的 Computer Operator | GUI 观察、人工接管、隔离、桌面验证与高风险审批 |
| Stage 4 | 低打扰的主动个人 Agent | Trigger、注意力预算、手机审批、暂停与设备撤销 |
| Stage 5 | 会积累上下文并安全改进方法的 Agent | 记忆可纠正/遗忘/导出，技能有评估、晋升和回滚 |
| Stage 6 | 多设备、可迁移、长期运行的 Personal Agent OS | 同步一致、离线恢复、设备撤销、迁移与长期运维证据 |

具体目标、范围与退出条件在对应阶段页展开；阶段之间按能力依赖推进，不按日历切换。

## 35 个增量，140 个工作包

每个 D 增量都按同一模板交付，避免“后端做完了但用户看不到”的伪进度：

| 交付项 | 必须回答 |
|---|---|
| 用户可见结果 | 用户能在浏览器里多做哪一件具体的事？ |
| 实现与工程落点 | 哪些模块、接口、事件和测试需要完成？ |
| 验收演练 | 用什么可重复的步骤证明它真的完成？ |
| 失败与恢复 | 失败时用户看到什么，如何取消、重试、接管或撤销？ |

每个增量包含四个实施工作包；工作包可以分工，但不能用其中任何一个的完成代替整个增量的验收。

## MVP 在哪里

MVP-1 位于 Stage 1 的 D1.3，是一个真实可用的本地个人任务工作台。它必须包含 Web 任务卡、持久任务状态、真实 Codex 执行、产物、审批演练和失败恢复，但不包含邮件、日历、GUI、主动循环和多设备。

## 六条执行规则

1. **纵向切片优先。** 不交付只有 CLI、日志、数据库或接口的“半成品阶段”。
2. **前端同步生长。** Stage 0 有原型，Stage 1 有真实 Web 任务卡，之后每个增量都必须有用户路径。
3. **持久性先于自主性。** 任务不能丢、副作用不能重复、失败必须可见。
4. **安全先于真实副作用。** 高风险动作必须经过预览、授权、幂等和回执。
5. **评估先于扩展。** 新执行器、连接器、模型和技能都要有代表性任务、基线和失败样本。
6. **范围可以裁，地基不能裁。** 先减少覆盖和主动性，不减少界面、状态、恢复、审计和撤权。
