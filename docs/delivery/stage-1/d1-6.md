## 这一增量解决什么

一个可以持续试用的本地产品，具备明确的范围、已知限制、恢复方式和指标基线。

Stage 1 的顺序是先有真实短闭环，再有安全副作用，最后扩大任务族和恢复覆盖；不能在空内核上先堆模块。

## 开始前

- Stage 0 的 12 个任务、原型、协议、评测与安全基线已经评审通过。
- 默认任务楔子是研究/文档整理；如果首位用户更依赖代码任务，可以替换楔子，但纵向结构不能改变。
- 本地开发环境、SQLite、可隔离 workspace 和 Web 构建链路可用。
- D1.5 的交付物已经验收；未通过时不进入本增量。

## 实施步骤

1. 跑 10 个真实任务，覆盖两个任务族、失败、审批和恢复路径。
2. 对比全人工和直接使用 Codex 的基线，记录人工分钟、成功率、Token 和失败类型。
3. 修复高频失败与最影响信任的恢复问题，不扩大新的能力范围。
4. 补全安装、备份、升级、数据导出和已知限制说明。
5. 完成 Stage 1 安全与评测报告，明确下一阶段进入条件。
6. 确认用户可独立使用，不依赖开发者手工运维或数据库操作。

## 数据与接口契约

| 检查点 | 必须满足 |
| --- | --- |
| 事件与恢复 | Event Log 是事实源；SQLite WAL 保存事件与投影，SSE 支持断线续传。 |
| 状态机 | Task/Run 只能通过受控迁移变化；刷新、重启和崩溃后都能从事实源重建。 |
| 副作用 | 外部动作必须经过 Effect Preview、outbox、幂等键和 Receipt，结果不确定时先对账。 |
| 秘密边界 | 秘密不进入任务卡、日志、模型上下文或执行器工作区；凭据只能由 Broker 注入。 |

## 交付物

- 10 个真实任务报告
- 与两条基线的对比
- 安装/备份/升级/导出说明
- Stage 1 安全与评测报告

## 验证清单

- [ ] Stage 1 退出条件全部满足；MVP 没有被后续内核工作破坏；用户能独立使用，不依赖开发者手工运维。
- [ ] 交付物已经和契约、任务卡投影保持一致，没有未登记的字段或状态。
- [ ] 至少一个失败路径有可操作恢复，关键动作留下审计事件。
- [ ] 演示不依赖手工修改数据库、只在终端拼接命令，或永久 mock。

## 失败与恢复

| 情况 | 用户看到 | 恢复动作 |
| --- | --- | --- |
| 进程崩溃或重启 | 任务详情显示最后已知状态、未完成步骤和“继续/取消/重试”。 | 从 Event Log 重放并重新领取 lease，禁止静默丢弃任务。 |
| 外部动作重复 | 系统显示“正在对账”，不生成第二个成功回执。 | 按幂等键查询 sink，确认已完成后补写 Receipt 或走补偿。 |
| 副作用结果不确定 | 任务进入“等待确认”，隐藏自动重试按钮。 | 先查询外部系统或人工核对，再决定重试、补偿或关闭。 |

## 本增量不包含

- 不允许只靠 CLI、日志或数据库证明 MVP 可用。
- 不在恢复与审批未稳定前扩大任务族。
- 不把永久 mock 结果当成真实执行。
