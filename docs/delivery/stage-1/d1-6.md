## 这一步要交付什么

一个可以持续试用的本地产品，具备明确的范围、已知限制、恢复方式和指标基线。

Stage 1 的顺序是先有真实短闭环，再有安全副作用，最后扩大任务族和恢复覆盖；不能在空内核上先堆模块。

## 开始前

- Stage 0 的 12 个任务、原型、协议、评测与安全基线已经评审通过。
- 默认任务楔子是研究/文档整理；如果首位用户更依赖代码任务，可以替换楔子，但纵向结构不能改变。
- 本地开发环境、SQLite、可隔离 workspace 和 Web 构建链路可用。
- D1.5 的交付物已经验收；未通过时不进入本增量。

## 四个实施工作包

> 每个工作包都要产生可运行的代码、可复现的验证或明确的界面结果；只写接口或只做页面都不算完成。

### 01 · Stage 1 出口审计

逐条收集 MVP、恢复、副作用、任务族和成本门槛的证据，缺一项就停留在当前阶段；不要用后续路线图替代当前验收。

### 02 · 故障与安全复核

完成 200 次故障注入、崩溃恢复、重复投递、越权和秘密检查；记录未解决风险、规避方式和是否阻断发布。

### 03 · 安装与支持文档

从空目录完成安装、启动、创建任务、重启恢复和导出；写清前置条件、已知限制、诊断命令和回滚方式。

### 04 · 发布说明与下一阶段入口

发布 Stage 1 版本说明，说明可用任务族、不能做什么、数据位置和升级路径；把 Stage 2 的只读优先级写进下一阶段入口。

## 工程落点

### 主要目录与模块

- `apps/hearthd` — 单进程常驻、Gateway、Control、Harness 与 SSE
- `packages/eventlog` — SQLite WAL、事件、投影、migration 与 replay
- `packages/harness` — Ticket、Run、lease、outbox、恢复与死信
- `packages/executors/codex` — Codex adapter、workspace 与结构化输出
- `packages/policy` — Policy、Mandate、Approval 与风险等级
- `packages/artifacts` — 内容寻址产物、哈希、版本与验证器
- `apps/web` — 任务卡、详情/时间线、审批、产物与恢复

### 关键接口

| 接口 | 必须保持的契约 |
| --- | --- |
| `Run` | runId、ticketId、state、checkpoint、budget、terminalReason；一次执行尝试只能有一个终态。 |
| `Ticket / Lease` | owner、scope、expiresAt、fencingToken；同一 Ticket 同时最多一个有效写者。 |
| `TaskPack` | objective、inputs、constraints、outputSchema、acceptance、budget、permissions；执行器只在该包内工作。 |
| `Effect / Receipt` | effectIntent、approvalId、idempotencyKey、receipt、reconciliation；不确定结果先对账，不盲目重试。 |

### 共享验证命令

```bash
pnpm dev：hearthd 与 Web 同时启动
pnpm test:fault：kill -9、断网、超时、重复投递
pnpm test:e2e：创建→取消→重试→审批→产物→恢复
pnpm eval:mvp：10 个真实任务与基线对比
```

## 验收演练

1. 从干净的数据目录启动 hearthd，打开 [D1.6 页面](/delivery/stage-1/d1-6)，确认当前页面没有依赖浏览器缓存或手工种子数据。
2. 按顺序完成四个工作包：Stage 1 出口审计、故障与安全复核、安装与支持文档、发布说明与下一阶段入口。每完成一个工作包，保存对应测试输出、截图或产物版本。
3. 复现失败案例“进程崩溃或重启”。页面必须显示“任务详情显示最后已知状态、未完成步骤和“继续/取消/重试”。”，然后按“从 Event Log 重放并重新领取 lease，禁止静默丢弃任务。”恢复；不得出现重复副作用或未登记状态。
4. 重启服务并重新打开任务，确认运行状态、审批、产物和恢复入口都来自持久投影，而不是只存在于当前页面。
5. 运行上方的共享验证命令并导出证据。完成门槛是：Stage 1 退出条件全部满足；MVP 没有被后续内核工作破坏；用户能独立使用，不依赖开发者手工运维。

## 完成判定

- [ ] Stage 1 退出条件全部满足；MVP 没有被后续内核工作破坏；用户能独立使用，不依赖开发者手工运维。
- [ ] 交付物已经和契约、任务卡投影保持一致，没有未登记的字段或状态。
- [ ] 至少一个失败路径有可操作恢复，关键动作留下审计事件。
- [ ] 演示不依赖手工修改数据库、只在终端拼接命令，或永久 mock。

## 失败与恢复

| 情况 | 用户看到 | 恢复动作 |
| --- | --- | --- |
| 进程崩溃或重启 | 任务详情显示最后已知状态、未完成步骤和“继续/取消/重试”。 | 从 Event Log 重放并重新领取 lease，禁止静默丢弃任务。 |
| 外部动作重复 | 系统显示“正在对账”，不生成第二个成功回执。 | 按幂等键查询 sink，确认已完成后补写 Receipt 或走补偿。 |
| 副作用结果不确定 | 任务进入“等待确认”，隐藏自动重试按钮。 | 先查询外部系统或人工核对，再决定重试、补偿或关闭。 |

## 本增量不包含

- 不允许只靠 CLI、日志或数据库证明 MVP 可用。
- 不在恢复与审批未稳定前扩大任务族。
- 不把永久 mock 结果当成真实执行。
