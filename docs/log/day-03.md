# Day03 · 开发增量扩写为可施工手册

<p class="lead">把每个 D 增量从一页提纲扩写成能直接分配、实现和验收的开发手册：每个增量固定包含四个工作包、工程落点、接口契约、验收演练和失败恢复。</p>

## 今日完成

- 将 Stage 0–6 的 35 个增量全部补齐为四个独立工作包，共 140 个工作包；Stage 0 的 D0.1–D0.4 保留并扩写。
- 为每个阶段补充主要目录、关键接口和共享验证命令，开发者能定位实现位置，而不是只看概念描述。
- 为每个增量增加五步验收演练、交付物、完成判定、失败恢复、明确边界和延伸阅读。
- 在 Stage 总览与开发计划总览中说明“产品路线图总纲 → 开发计划 → Stage → D 增量 → 四个工作包”的阅读层级。
- 同步扩写中文与英文页面，保持标题、列表、表格和链接结构一致。

## 验证证据

- 增量 ID 与详情数据逐阶段核对，35 个增量都有且仅有四个中英文工作包。
- 页面已重新生成，交付侧栏仍对应 35 个增量，没有改变既有 URL。
- 双语构建、站内链接、来源覆盖和翻译结构检查通过。
- 桌面与手机宽度下检查长段落、表格和命令块，没有横向溢出。

## 遇到的问题

- 旧页面把阶段级契约和失败表重复复制到每个增量，内容看似完整，实际没有回答“这一增量具体怎么做”。
- 只有笼统实施步骤时，多个开发者无法并行判断各自负责的代码位置和完成证据。
- 扩写后单页信息量明显增加，如果没有固定层级，反而会更难阅读。

## 决定与取舍

- 每个增量固定四个工作包，不继续无限细分；四包按依赖合并，任何一个包都不能代替增量验收。
- 阶段共享的目录、接口和命令明确标注为“共享”，不伪装成每个增量独有。
- 保留用户结果、完成门槛和失败恢复作为硬约束，新增内容只提供施工方法，不降低出口标准。
- 不把开发日志冒充产品发版说明；版本记录仍在真正发版时维护。
