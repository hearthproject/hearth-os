# 首次运行验证

<p class="lead">单元测试通过不等于你的模型、-key、工具循环和测试链路真的通。这一页提供一个可复现的最小真实任务：让模型读一个文件、写出预期答案、跑一次测试，并返回结果。它复用服务端已有的首次任务验证逻辑，不另起一套模型调用。</p>

## 它验证什么

一次成功的首跑会同时证明四件事：

1. **模型可用**：你配置的 provider 与 key 能正常返回，并驱动多轮工具调用。
2. **工具循环可用**：模型能 `read_file` 读取 `hello.txt`、`write_file` 写出 `answer.txt`。
3. **测试链路可用**：`npm test` 真的执行了 `check.mjs`，并以退出码 0 结束。
4. **产物与收尾可用**：任务以 `completed` 结束，`answer.txt` 内容为 `hearth`。

四项都通过才算首跑成功；任何一项失败都会给出具体检查项，便于定位是 key、模型、工具还是环境问题。

## 前置条件

1. 在 **设置 → 模型** 创建模型档案（选择服务商或自定义，填入 API Key），并在 **设置 → 执行器** 把它绑定到执行器。
2. 启动本地服务端：开发模式 `npm run dev`，或生产式 `npm run build && npm start`。
3. 确认 <http://127.0.0.1:4317/api/ready> 返回 `{"ok":true,...}`。

## 运行

```bash
# 真实模式：用你配置的聊天模型跑一次真实任务
npm run first:run

# 指定服务地址
node scripts/first-run.mjs --base-url http://127.0.0.1:4317
```

输出示例：

```text
首次运行验证（真实模型）
结果：passed
  [PASS] 模型调用了工具并完成 (completed)
  [PASS] answer.txt 内容正确 (hearth)
  [PASS] 真实测试通过 (任务以 completed 结束)
说明：模型已经完成一次真实的读写和测试。
完成：模型已经跑通一次真实的读写与测试。
```

退出码：`0` 通过；`1` 任务失败；`2` 环境或配置问题（服务未启动、模型未配置等）。

## 离线自检（--fake）

```bash
npm run first:run -- --fake
```

`--fake` 不联网、不需要模型、不需要服务，在临时目录里确定性地复现同一套「写 `answer.txt` → `node check.mjs`」流程，用来验证**脚本自身**的输出与退出码。它**不能**证明你的模型可用——真实模型请用默认模式。

## 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| `无法连接本地服务` | 服务端未启动或端口不对 | 先 `npm start`；端口不同用 `--base-url` |
| `尚未配置聊天模型` | 未绑定可用的聊天模型档案 | 在 设置 → 模型 / 执行器 完成绑定后重试 |
| `Access to model denied` 等 | key 无权限或额度不足 | 换用有权限的 key 或服务 |
| 任务超时 | 模型响应慢或工具循环卡住 | 检查网络与模型状态；必要时换执行器 |
| `answer.txt 内容正确` 失败 | 模型未按指令写文件 | 看任务说明与执行记录，确认工具是否被正确授权 |

## 与自动测试的关系

`--fake` 的自检逻辑与服务端 `onboarding-verify` 使用同一套 fixture，但**自动测试**（`npm test` 中的 `onboarding-verify.test.ts`）通过注入 fake runner 覆盖成功与失败路径，是确定性的回归门禁。本脚本的真实模式则是对**当前代码 + 你自己的模型**做一次端到端确认，两者互补：前者保证代码正确，后者保证你的环境真的能用。
