# 文档地图

<p class="lead">所有正式文档只在 `docs/` 中维护，仓库和线上站点使用同一份内容。中文是默认路径，英文使用相同结构。找不到某类信息时，可以先从这里确定该读哪一块。</p>

## 文档地图

| 区域 | 内容 | 入口 |
|---|---|---|
| 设计说明 | 1 篇总体设计 + 9 篇并列模块设计，包含技术选型 | [总体设计](/design/) |
| 交付路线 | 六个阶段、24 个小阶段和 MVP 位置 | [交付路线](/delivery/) |
| 开发日志 | 每天一段概述和提交明细 | [Day02](/log/day-02) |
| 附录 | 工程、风险、决策、自研边界、术语、清单和维护资料 | [附录](/reference/) |
| 站点入口 | 首页和双语切换 | [首页](/) |

设计说明的九篇模块是入口与交互、任务与持久执行、控制面与授权、执行器与路由、审批与外部副作用、运行环境与安全、记忆与能力进化、评估与成本、多设备与长期运行。它们彼此并列，不按代码目录组织。

第一次了解项目，可以按“为什么做 → 先做什么 → 怎么实现”的顺序阅读：

1. 从[总体设计](/design/)理解产品定位、任务链路、技术选型和模块边界；
2. 按需要阅读九个模块，不必按固定顺序；
3. 看[交付路线](/delivery/)确认六个阶段和当前 MVP 的位置；
4. 进入具体阶段时，再看[工程实施](/reference/engineering)、[关键决策](/reference/decisions)和[风险与停止条件](/reference/risks)。

只想快速判断项目是否值得继续看，先读总体设计的“产品定位与目标”和交付路线的阶段总览即可。准备实现时，再读工程实施和默认清单。

## 维护与发布规则

1. 先改中文页面，确认结论、边界和链接准确，再在同一次提交中更新英文镜像。
2. 修改设计说明或交付路线后，检查附录、导航、侧栏、首页和语言切换是否仍然对得上。
3. 设计说明不要引入代码路径、内部类名和实现示例；工程约束留在附录。
4. 删除旧页面时直接下线，不保留重定向和重复正文；全站搜索旧路径，避免留下死链。
5. 运行 `npm run docs:build`，再检查站内链接、移动端宽度和搜索入口。
6. 不写“应该”“以后会”来掩盖尚未做出的决定；未验证的内容明确标成假设。

当前文档描述产品规格、设计判断和开发计划，不代表功能已经交付。开发日志记录当天的工作和提交，不冒充产品发版说明。只有形成可安装版本后，才维护正式版本号和发布说明。

线上站点应当与仓库的 `docs/` 构建结果一致。每次发布后检查旧地址是否已经下线、双语页面是否都能访问、侧栏与首页入口是否指向新结构。
