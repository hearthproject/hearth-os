# 文档地图与维护

<p class="lead">所有正式文档只存放在仓库的 <code>docs/</code>。文档站由这个目录直接构建，README 只负责仓库入口，因此仓库内容与线上站点始终是同一份文档。</p>

## 文档地图

| 区域 | 内容 | 入口 |
|---|---|---|
| 设计说明 | 定位、原则、取舍、架构与当前状态 | [设计说明](/design/) |
| 架构细节 | 协议、控制面、执行器、安全、记忆与评估 | [总体架构](/architecture/overview) |
| 交付路线 | Stage 0–6、D 增量、工作包与 MVP | [交付路线](/delivery/) |
| 开发日志 | 每天一段概述，加上提交、具体修改与作者 | [Day02](/log/day-02) |
| 附录 | 工程、风险、决策、术语、清单与归档 | [附录](/reference/) |

## 阅读层级

1. **设计说明**回答为什么做、边界在哪、关键取舍是什么；
2. **交付路线**把设计变成 Stage 0–6 的能力门槛和施工顺序；
3. **Stage 页面**说明前置条件、阶段出口和本阶段不做什么；
4. **D 增量页**给出可独立施工和验收的纵向切片；
5. **四个工作包**进一步说明实施步骤、工程落点、接口和失败恢复。

先确认当前阶段的范围和出口，再进入具体开发页；不要从单个工作包反推整个产品范围。

## 主题页面与完整归档

- 主题页面是日常阅读和维护的主路径，按设计、交付、日志和附录组织。
- [完整路线图归档](/reference/full-roadmap)保留长文细节，适合检索、引用和差异核对。
- 归档页与主题页面都位于 `docs/`，不是两个独立文档源。
- 修改事实、协议或阶段门槛时，同时更新主题页面、归档页和英文镜像。

## 维护流程

1. 先修改中文页面，确认结论、边界和链接仍然准确。
2. 在 `docs/en/` 的相同相对路径创建或更新英文镜像。
3. 更新相关入口、侧栏和交叉链接，避免留下失效路径。
4. 运行 `npm run docs:build`，先消除构建错误和站内死链。
5. 在本地预览中检查长表格、代码块、移动端宽度和语言切换。

## 提交前检查

- 正式文档只修改 `docs/`，不要新增第二个文档根目录。
- 中文与英文页面路径对应，标题层级和列表数量一致。
- 交付路线保持“设计 → 交付 → Stage → D 增量 → 工作包”的层级。
- README 只保留项目简介、快速开始和文档导航，不复制长篇正文。
- 开发日志每天只保留一段概述和提交明细，不恢复日志首页或模板。
- 不提交 `docs/.vitepress/dist`、缓存、本地密钥或无证据的完成声明。

## 文档与发版边界

- 当前文档描述规格、设计判断和开发计划，不代表产品已经发布。
- 开发日志按天记录概述、提交、具体修改与作者，不冒充产品发版说明。
- 只有实现开始并形成可安装版本后，才维护正式版本号和发布说明。
