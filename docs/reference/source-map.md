# 文档地图

<p class="lead">所有正式文档只在 `docs/` 中维护，仓库和线上站点使用同一份内容。中文是默认路径，英文使用相同结构。找不到某类信息时，可以先从这里确定该读哪一块。</p>

## 站点结构

| 区域 | 内容 | 入口 |
|---|---|---|
| 设计说明 | 1 篇总体设计 + 11 篇并列模块设计，包含技术选型 | [总体设计](/design/) |
| 交付路线 | 六个阶段、24 个小阶段、阶段二至六交付状态和真实验收边界 | [交付路线](/delivery/) |
| 开发日志 | Day01–Day04 的逐日记录、提交明细与边界 | [Day04](/log/day-04) |
| 附录 | 工程、风险、决策、自研边界、术语、清单和维护资料 | [附录](/reference/) |
| 站点入口 | 首页和双语切换 | [首页](/) |

设计说明的十一个模块是入口与交互、任务与持久执行、控制面与授权、执行器与路由、原生 Agent Runtime、审批与外部副作用、运行环境与安全、记忆与能力进化、评估与成本、多设备与长期运行与 Agent 参考模式。它们彼此并列，不按代码目录组织。

第一次了解项目，可以按“为什么做 → 现在有什么 → 还缺什么 → 怎么实现”的顺序阅读：

1. 从[总体设计](/design/)理解产品定位、任务链路、技术选型和模块边界；
2. 按需要阅读十一个模块，不必按固定顺序；
3. 看[交付路线](/delivery/)确认六个阶段的真实状态：阶段一已验收，阶段二至六已有代码闭环但尚未完成真实验收；
4. 准备继续开发时，再看[工程实施](/reference/engineering)、[关键决策](/reference/decisions)、[风险与停止条件](/reference/risks)和[Day04 开发日志](/log/day-04)。

只想快速判断项目是否值得继续看，先读总体设计的“产品定位与目标”和交付路线的阶段总览即可。准备实现时，再读工程实施和默认清单。

## 维护与发布规则

1. 先改中文页面，确认结论、边界和链接准确，再在同一次提交中更新英文镜像。
2. 修改设计说明或交付路线后，检查附录、导航、侧栏、首页和语言切换是否仍然对得上。
3. 设计说明不要引入代码路径、内部类名和实现示例；工程约束留在附录。
4. 删除旧页面时直接下线，不保留重定向和重复正文；全站搜索旧路径，避免留下死链。
5. 运行 `npm run docs:build`，再检查站内链接、移动端宽度、搜索入口和暗色模式。
6. 不写“应该”“以后会”来掩盖尚未做出的决定；未验证的内容明确标成假设或留空。

当前文档记录已经实现的代码闭环、已经取得的验收证据，以及仍未验收的边界。阶段二至六有可运行代码和自动测试，但没有用真实账户、真实设备或长期运行冒充完成。开发日志记录当天的工作和提交，不冒充产品发版说明；只有形成可安装版本后，才维护正式版本号和发布说明。

线上站点应当与仓库的 `docs/` 构建结果一致。每次发布后检查旧地址是否已经下线、双语页面是否都能访问、侧栏与首页入口是否指向正确结构。
