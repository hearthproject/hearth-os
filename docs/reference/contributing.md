# 参与贡献

<p class="lead">Hearth 已进入第一阶段 MVP 实现。最有价值的贡献仍然是澄清边界、挑战风险假设、补充真实任务，以及让实现者更容易读懂文档；现在也欢迎带验收证据的实现改动。改动不需要写得很多，但必须让结论更准确、证据更清楚。</p>

## 本地运行与写作约定

正式文档只放在 `docs/`，站点直接从这些文件构建。README 是仓库入口，不是另一份正文副本。中文是默认阅读路径，英文镜像使用相同路径和结构。

| 目录 | 内容 |
|---|---|
| `docs/design/` | 1 篇总体设计和 9 篇并列模块设计 |
| `docs/delivery/` | 六个阶段、24 个小阶段和交付总览 |
| `docs/reference/` | 工程、风险、决策、边界、术语、清单和维护资料 |
| `docs/en/` | 所有页面的英文镜像 |
| `docs/.vitepress/` | 站点配置、导航、侧栏和主题 |
| `scripts/` | 交付页面生成和覆盖检查 |

本地开发需要 Node.js 20 或更新版本以及 npm。安装依赖运行 `npm ci`，开发预览运行 `npm run docs:dev`，构建运行 `npm run docs:build`，预览构建结果运行 `npm run docs:preview`。构建产物写入 `docs/.vitepress/dist`，不要提交。

写作时先讲结论，再讲原因；一个段落只承担一个主要意思。设计说明只写产品目标和设计取舍，不写代码路径、内部类名和实现细节。文章尽量少用二级标题，不要用三级标题拆分碎片内容；需要比较时优先用表格，需要步骤时用短列表。

使用用户能理解的统一概念。必要技术名称首次出现时解释，不做名词堆叠。区分事实、判断和待验证假设，不把计划写成已经交付的能力。中文和英文保持相同路径、相同标题层级和相近内容，不新增只存在于一侧的页面。修改设计或交付结论时，同时检查相关附录、导航、侧栏和交叉链接。

开发日志每天只有一个页面：一段当天概述，加上提交、作者和具体修改。同一天有新提交就追加表格行，不恢复日志首页、模板或阶段汇报。

## 提交检查与文档事实源

提交前至少完成以下检查：

1. 运行 `npm run docs:build`，确认没有构建错误和站内死链。
2. 检查中文与英文路径是否对应，侧栏和语言切换是否可达。
3. 检查设计说明没有代码块、代码路径和无意义小标题。
4. 如果修改事实、权限、风险或阶段目标，同步更新相关决策和附录。
5. 不提交构建产物、缓存、本地密钥、真实用户数据或无证据的完成声明。

提交说明应写清楚改了什么、为什么改、影响哪些读者或阶段，以及还需要什么证据才能确认完成。

`docs/` 是仓库和文档站共同使用的唯一正式文档源。没有第二份长文副本，也没有“归档版”与线上版同时维护。中文页面先改，英文镜像在同一次提交中跟上；发现翻译或链接问题，应直接修正源文件。

项目使用 Apache-2.0 许可证。提交贡献即表示同意按该许可证发布内容。
