# 关键决策

<p class="lead">下面这些判断决定了产品边界和实现方向。它们可以随证据修正，但不应该在日常开发中被悄悄绕过。遇到争议时，先确认是否真的改变了这里的结论，而不是只改了说法。</p>

| 决策 | 结论 | 主要影响 |
|---|---|---|
| 产品形态 | 单用户、自托管、本地优先的个人 Agent OS | 不做企业多租户；数据默认留在用户控制的环境 |
| 核心对象 | 以任务为中心，而不是以聊天记录为中心 | 界面围绕任务卡、审批、产物和恢复组织 |
| 事实来源 | 先记录事实，界面、索引和通知都是投影 | 刷新、换设备和崩溃后可以重建状态 |
| 写入方式 | 每个状态只有一个写权威 | 早期采用单进程、单写者和本地数据库 |
| 执行方式 | 持久执行，允许重试、暂停、检查点和接管 | 长任务跨重启、休眠和断网继续存在 |
| 系统结构 | 模块化单体优先，不为未出现的规模拆微服务 | 用接口、测试和权限边界保证模块独立 |
| 执行器 | 多种专长执行器并列，由能力、风险和成本路由 | 不把所有工作交给一个万能模型 |
| Codex 定位 | Codex 是高能力外部执行器之一，不是产品本体 | Hearth 保留任务、权限、验证、记忆和回执 |
| 外部动作 | 先预览、再授权、后执行、最后对账 | 发送、写入、删除、发布和付款不会盲目重试 |
| 安全边界 | 最小权限、短期凭据、隔离环境、默认拒绝网络 | 模型和执行器看不到长期原始凭据 |
| 记忆与进化 | 记忆可纠正、可遗忘；方法经过评估、灰度和回退 | 不允许无界自修改，也不允许技能自行扩权 |
| 评估标准 | 真实任务、独立验证、人工时间、恢复和成本 | 演示成功或模型自评不能证明能力 |
| 移动端 | 手机优先覆盖审批、查看、接管和简单发起 | 不复制桌面端全部管理功能 |
| 明确不做 | 企业多租户、公开 Agent 市场、无审批的高风险自动化 | 保持产品聚焦和个人可控 |

**为什么这样选。** Hearth 的主要矛盾不是“模型够不够聪明”，而是长任务能不能被授权、验证、恢复和解释。如果任务状态只存在聊天记录里，用户无法判断哪一步真的完成，也无法在失败后恢复。因此事实记录、单写者和持久执行是基础，而不是后期优化。

选择多个执行器，是因为不同工作有不同边界。通用推理适合短链路理解，Codex 适合代码、长文档和复杂工作区，连接器适合有官方接口的系统，浏览器和桌面操作覆盖没有接口的软件，文档数据处理适合确定性工具，价值判断和责任承担仍然属于人。路由的目标是满足权限、风险和可逆性之后，再优化成功率、延迟和成本。

记忆和方法进化必须慢。记忆会直接影响判断，错误事实会造成持续返工；方法变化会扩大系统能力，也可能悄悄扩大权限。两者都必须有来源、评估、灰度和回退，不能因为一次演示成功就默认长期有效。

**交付判断。** Hearth 不按“后端做完再做界面”的方式推进。每个阶段都交付一条完整链路：用户能看到结果，系统能保存状态，执行能产生证据，失败能恢复，外部动作能审批和对账。第一阶段先交付最小完整 MVP，之后按六阶段路线扩展工作范围、主动性、记忆和多设备能力。

Hearth 真正的护城河不是拥有一个更强的模型，而是知道什么时候不该调用模型、该给执行器多少上下文、哪些动作必须经过谁授权、如何证明任务完成、失败后如何恢复、什么应该记住、什么应该遗忘，以及什么时候应该停下来把注意力还给人。
