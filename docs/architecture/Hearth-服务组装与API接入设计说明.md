## 0. 一句话总览

整个服务端是**一个进程、一个组装函数**：所有服务对象在一个函数里被手工创建并用回调互相连线，同一函数里顺带完成安全边界、约 120 条接口、两条事件流和静态站托管。没有依赖注入容器，也没有按业务拆分的控制器目录。

---

## 1. 先定性：三个容易误解的地方

| 误解 | 代码里的实际做法 |
|---|---|
| 以为有一个「服务运行时框架」在管理生命周期 | 没有。约 40 个服务在一个函数作用域里逐个创建，靠构造函数参数和回调闭包连线，启动与停止顺序也是手写清单 |
| 以为 API 分散在各业务模块里 | 几乎所有路由都内联在装配文件里，只有聊天与评测两组接口被抽成独立注册函数 |
| 以为监听端口就是启动 | 组装函数只负责「造出应用」并返回，不监听；监听、飞书长连接、退出信号都在另一个极短的入口文件里 |

> 另一个易踩的坑：`runtime.ts` 不是服务运行时，它是任务级依赖环境的准备器，见[Hearth-工作区隔离与产物设计说明](./Hearth-工作区隔离与产物设计说明.md)。

## 2. 启动链：从进程到可用

顺序是固定的五步：

1. **组装**：入口传入一组开关（调度器、主动建议、常驻意图心跳、邮件同步、日志），调用组装函数。此时约 40 个服务被创建，部分后台循环在 Fastify 实例创建**之前**就已启动。
2. **监听**：入口对组装返回的实例调用监听，绑定本机地址与默认端口 4317。
3. **飞书长连接**：拿到监听地址后才启动，且是「发出去就不管」的异步调用，失败只打印错误，不阻断主服务。
4. **打印执行器状态**：读取 Codex 配置档，输出是否可运行及原因。
5. **退出信号**：注册一次性的中断与终止处理，用一个布尔量防重入，统一走应用的关闭钩子。

后台循环有个隐蔽的联动：维护、技能策展、看门狗三者的开关**没有单独传值**，而是回退到「调度器开关」的值。所以入口里只写了启动调度器，这三项也就一起启动了。

此外，调度器的启动既不在入口、也不在组装开头，而是在静态托管段之后，并且被全局停止开关（kill-switch）门控：如果上次停机时开关是拉下的，这次调度器就不会起来。

## 3. 手工依赖图：回调就是接线

组装函数接受约 27 项可覆盖配置，主要是为了测试时能注入假的存储、假的邮件/飞书传输、假的目录。生产路径上则全部使用真实实现。它没有容器，靠两类手段连线：

- **构造函数传依赖**：例如存储、服务门面、工作区根目录、密钥箱等直接传进去。
- **回调闭包传「事后动作」**：这是最能看出设计意图的部分，四个典型例子：

| 连线 | 回调做的事 | 把哪几块接了起来 |
|---|---|---|
| 服务门面 → 上下文账本 | 聊天消息落库后，若上下文模式未关闭，顺手记一条上下文 | 事件门面与上下文采集，且带开关门控 |
| 来源注册 → 本体写入 | 一个来源条目就绪后，回写知识本体 | 数据采集与知识沉淀 |
| 审批管理器 → 守卫 | 每次审批前依次检查全局停止开关、任务租约归属、委派权限；结果不确定进对账队列；有结论回写本体 | 一个回调串起安全、租约、委派、对账、本体五处 |
| 调度器 → 外部执行器 | 把 Codex 的运行函数、配置档、环境变量打包注入 | 调度层与执行器适配层 |

审批管理器创建完还会立刻做两件恢复动作：恢复中断的效果、扫描不确定的副作用。也就是说**启动即自愈**，不依赖外部定时任务补跑。

进程内事件总线极其简单：一个监听器集合，发布时同步逐个调用，不做异常隔离、不排队、不持久化。真正持久的是事件表（见存储文档），总线只是同进程内的广播。

## 4. 请求安全：三道关 + 一个例外

所有请求在进路由前依次过三关：

| 关卡 | 判据 | 拒绝结果 |
|---|---|---|
| ① 主机名 | 必须是 127.0.0.1、localhost、::1 等等价形式 | 仅本机可用 |
| ② 跨站标记 | 请求头标记为跨站即拒 | 跨站被拦截 |
| ③ 来源头 | 非只读方法带来源头、且来源不是本机，即拒 | 来源被拦截 |

**唯一例外**是入站同步端点（`/api/sync/events`）：它只被豁免第 ① 关，②③ 两关照样生效；而它自己还要求 Bearer 令牌鉴权、并且用严格的模式校验查询参数。所以它不是后门，只是允许其它设备把事件推过来。

另有几条旁路：设备类端点使用独立的 Bearer 令牌体系；静态资源与页面回退走通用 404 处理器；业务错误由一批专用映射函数按错误子类转成状态码，全局兜底一律返回内部错误且不泄漏细节。

## 5. 接口规模与校验方式

- **规模**：装配文件内约 109 条路由，聊天注册函数 13 条，评测注册函数 2 条，合计约 124 条。
- **分组**：健康检查与引导、集成设置、模型与执行器、MCP、项目、搜索设置、定时计划、维护/诊断/安全/系统、主动式与意图、注意力、本体、预备动作、后台工具、订阅、看门狗、入站分拣、记忆、方法、技能、同步、连接、模板、来源、发件箱、桌面与设备、导出与备份、目标、任务与回收站、产物/运行/审批/效果/对账、统计、事件、上下文、会话与聊天、附件、评测。
- **校验**：请求体先过严格的模式校验（多数字段集不允许出现未声明的键），失败统一返回参数错误；枚举直接复用共享契约层的常量数组；分页默认 50 条。
- **体积上限**：默认请求体约 8 MB；备份恢复接口单独放宽到 512 MB；聊天附件走多部分表单，单文件 25 MB、最多 5 个文件。

## 6. 两条输出通道与静态站

**全局事件流**是本项目实时性的地基，设计上处理了一个经典竞态：

1. 先订阅总线，订阅期间到达的实时事件先存进缓冲区；
2. 再按客户端给的序号回放历史事件；
3. 回放完才把缓冲区倒出来，之后转为直发。

这样「订阅与回放之间刚好发生的事件」不会丢。每条消息带单调序号，重复序号会被丢弃，也可以按任务编号过滤。每 15 秒发一次注释行作心跳，连接关闭时清理定时器与订阅。另有轮询版的历史查询接口，支持前后双向游标、类型与任务过滤、最多 500 条。

**聊天流**是另一条独立的事件流，由聊天注册函数自己劫持响应写出，关闭连接时会中止正在进行的模型调用。

**静态站**：只有当编译产物存在且未被显式关闭时才注册静态托管；非 `/api/` 开头的 GET 请求一律回退到单页入口 HTML，让前端路由接管深链接。

## 7. 优雅关闭：顺序是手写的

关闭钩子里的顺序是：飞书 → 邮件 → 主动建议 → 常驻意图 → 看门狗 → 订阅投递 → 维护 → 技能策展 → 定时计划 → 调度器 → 最后才关数据库。其中飞书与调度器的停止是显式等待完成的，其余是同步停止。数据库是否关闭取决于「是不是自己创建的」——测试注入进来的存储不会被误关。

---

## 8. 配置：一个根目录下的世界

默认只绑定 127.0.0.1:4317，数据根目录是仓库下的 `.hearth`，可以由环境变量整体改位置。其下按用途分出工作区、Git 缓存、产物、来源正文、发件箱、设备截帧、备份、上下文长文本、执行器主目录、附件等子目录；模型与执行器另有两个 JSON 设置文件（旧格式会迁移进主库，见[Hearth-模型接入与执行器适配设计说明](./Hearth-模型接入与执行器适配设计说明.md)）。还提供一个「仓库内路径解析」函数，拒绝任何逃出仓库的路径。

## 9. 只读代码才会发现的事实

1. 组装函数返回应用但**不监听**，监听在入口；这让测试可以直接拿到实例而不占端口。
2. 全局停止开关只挡调度器启动，不挡其它后台循环，也不挡接口。
3. 事件总线的发布没有异常隔离：某个订阅者抛错会打断这一轮广播并冒泡给发布者。
4. 飞书之所以被挂到应用实例上，只是为了让入口在拿到监听地址后能启动长连接；长连接本身完全不在组装函数里。
5. `/api/sync/events` 是唯一被主机名白名单放行的路径，但仍受跨站、来源与令牌三重约束。

## 10. 与其它模块的分界

| 方向 | 内容 |
|---|---|
| 输入 | 入口文件、配置常量、共享契约类型、存储层、约 40 个服务实现、前端编译产物 |
| 输出 | REST 接口、全局事件流、聊天流、静态站与页面回退、总线订阅点 |
| 不讲 | 事件如何落库（存储）、前端如何刷新（前端）、计划如何补跑（定时任务）、审批如何判定（判定审批） |
