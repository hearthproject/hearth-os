# 代码架构说明

<p class="lead">这一板块不看设计文档，只看代码。它回答的是「这套系统现在实际上是怎么被拼起来、怎么跑起来的」，而不是「当初打算怎么设计」。</p>

## 为什么单独有这个板块

站上的[设计说明](/design/)写的是产品定位、方案取舍和验收目标，属于方案视角；随着实现推进，其中部分事实已经与代码脱节。本板块在 2026-11-13 从 `apps/` 与 `packages/` 的源码逐文件重新整理，刻意不参考仓库内的既有设计文档，也不列举具体代码，只用自然语言描述结构、流程、状态与边界。

两者不是替代关系：想知道「为什么这样设计」读设计说明，想知道「代码里现在是什么」读本板块。遇到不一致时，以源码和本板块的描述为准。

## 建议的阅读顺序

- **先建立全貌**：服务组装与 API 接入 → 领域契约与状态机 → 事件溯源与存储管理，这三者决定后面所有模块的形状。
- **再看主线**：任务执行调度器 → 模型接入与执行器适配 → Agent 运行时 → 工作区隔离与产物，跟完一次任务的执行路径。
- **按需深入**：其余篇章可单独阅读；每篇开头的「本文边界」表格会指出前置知识在哪一篇。

## 阅读约定

- 每篇开头的边界表格写明「哪些内容已被哪篇讲过」，因此本板块内部不重复展开同一机制；跨篇引用都做成了可点击链接。
- 括号里出现的文件名只用于定位核对，不是代码片段；全文不列举具体实现代码。
- 状态名、常量数值、默认值与目录名均以整理时的源码为准，代码变更后需重新核对。
- 整理范围主要是服务端源码、共享包与前端源码；评测控制台只保留构建产物，未在代码中展开。
