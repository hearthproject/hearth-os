## 0. 一句话总览

一套典型的不对称适配：飞书「长连接收、REST 发」，邮件「SMTP 发、IMAP 收」，设备「配对 → 心跳 → 截帧 → 指令」；中间夹一层统一入站幂等，出口则一律经审批与效果账本，不允许绕过。

## 1. 先定性：三个容易误解的地方

| 误解 | 代码里的实际做法 |
|---|---|
| 以为飞书消息走 REST 回调 | 入站走 SDK 长连接，REST 只用来发文本、下载资源与校验凭据 |
| 以为「默认飞书聊天客户端」是远程服务 | 它是本机客户端：反过来用 HTTP 调本服务的聊天接口并自己解析事件流，等于一次自环调用 |
| 以为统一入站层同时管出站 | 出站意图的完整链路在生产代码里**没有消费者**，目前只有入站侧被接线；真正的外发走审批 + 效果账本 |

## 2. 飞书：两条通道与一条路由表

**入站**用官方 SDK 的长连接，开启自动重连、握手超时 15 秒，订阅消息接收事件。代码注释点明一个工程细节：平台超过 3 秒未收到确认会重投，因此消息**先立即确认、再异步处理**。连接状态有五种：未启用、连接中、已连接、重连中、出错；启动后有一个 15 秒看门狗，超时仍没连上就置为出错。

**出站**是 REST：租户令牌会缓存并在到期前 30 秒提前刷新（默认有效期 2 小时），发送文本走消息接口，下载图片/文件走资源接口。国内版与国际版用两个不同的基础地址，由配置中的域选择。

**设置与白名单**：应用密钥用加密箱保存，界面只返回「是否已有密钥」与固定掩码；启用前必须同时具备应用编号、密钥和至少一个允许的用户标识（去重后最多 50 个）。另有一张「群聊 → 会话」的路由表存在应用设置里。

**消息解析**规则很具体：必须有消息体与发送者且发送者类型为人；必须有所需标识；群聊若没有被 @ 就**直接丢弃**；正文是 JSON 字符串，去掉 @ 占位符并压缩空白；同时解析出文本、文件键、图片键、文件名；时间戳兼容毫秒数字与字符串。

**入站处理**：按群聊串成队列（同一会话串行）→ 查用户白名单 → 交给统一入站层做幂等 → 成功后处理消息 → 确认；失败则按可重试规则（限流、网关错误、网络错误、超时）标记重试。

消息分两种走向：审批命令（`/approve`、`/reject`、中文「批准/拒绝」加审批编号前 8 位）直接找待审批记录并给出结论，顺带同步发件箱状态；普通消息则经本机聊天接口转成 SSE 流，拿到会话编号后绑定群聊路由，再把回复逐条发回（单条文本上限 4 千字符，按已发消息编号去重）。

出站通知还会订阅总线：聊天消息创建时转发助手回复；审批创建时（仅待审批且任务确实在等确认）发一条带命令提示的通知。

## 3. 邮件：发与收是两条独立链路

账号配置分 SMTP 与 IMAP 两组，各自有主机、端口、是否加密、用户名与加密后的密码；界面只给「是否已有密码」与掩码。同步间隔默认 15 分钟，允许 5 分钟到 24 小时；端口范围 1–65535。

**发**：用 nodemailer 建传输，返回消息编号与接受/拒绝列表；发件人支持「显示名 + 地址」格式。

**收**：用 ImapFlow 以**只读方式**打开收件箱，按当前邮件总数算出起始序号，只取尾部若干封（1–50，默认 20），解析出主题、发件人、日期、正文，最后把结果反转成时间顺序。

定时器每 60 秒走一次（最低 10 秒），对每个启用的账号按各自的同步间隔做进程内节流。

一个重要的实现事实：**没有持久化的邮件游标**。去重完全交给来源层的「消息编号 + 正文哈希」（见数据源文档），而节流用的「上次同步时间」只存在内存里，进程重启就清零。这意味着重启后会重新扫一遍尾部邮件，但不会产生重复条目。

每封邮件会被转成一条外部来源条目：定位符是 imap 协议形式的地址，正文由「主题 + 发件人/时间/接收账户 + 正文」拼成（无纯文本正文时有固定占位文案），喂入后该来源的提供者会被改写成 IMAP。

## 4. 统一入站幂等层

所有外部消息进入业务前先过这一层，它回答三个问题：**这条消息是不是重复、它的代次是不是过期的、处理结果该记成什么**。

| 环节 | 规则 |
|---|---|
| 认证 | 未通过直接拒；凭据已过期单独报错 |
| 重复判断 | 按「渠道 + 外部编号 + 入站方向」查既有记录，命中即返回重复，**不再校验游标** |
| 代次与游标 | 代次低于当前值拒；同代次但游标回退拒 |
| 落记录 | 状态置为处理中，载荷先递归脱敏再存 |
| 确认 / 失败 | 确认是幂等的；失败分可重试与不可重试，累加尝试次数与错误 |

记录状态共七种：已接收、处理中、已处理、重复、重试中、失败、不确定。

**出站侧的设计很严但当前闲置**：准备出站时生成一个「需要审批」的意图；真正投递前会强制校验效果类型、幂等键与「效果已成功且有回执」，注释明确写着「不能绕过审批和效果账本」。但生产代码里只有飞书入站用到这一层，出站意图没有消费者，发件箱走的是另一条链路。

## 5. 设备：配对、能力、心跳、截帧

| 环节 | 规则 |
|---|---|
| 配对 | 设备令牌 32–256 位且无空白；生成 6 位配对码与一个密钥，只存哈希；平台固定为 Windows；5 分钟过期 |
| 兑换 | 设备用配对密钥查询状态，校验哈希；已批准的配对在查询时自动转为「已兑换」并返回设备信息 |
| 能力 | 三类：观察、桌面控制、界面自动化；状态为待批准 / 已批准 / 已撤销。批准后设备初始为离线，所有申请的能力初始待批准 |
| 撤销联动 | 撤销观察会终止会话；撤销桌面控制会暂停会话；撤销设备会吊销全部能力并终止所有未结束会话；轮换令牌会置离线并终止会话 |
| 在线判定 | 最近心跳在 30 秒内才算在线；5 秒内的重复心跳不写库以节流 |
| 审计 | 配对、撤销、轮换、冻结都写安全审计事件 |

设备端点使用独立的 Bearer 令牌链路（按哈希查库），与全局停止开关是**两层不同的东西**：停止开关只在创建会话、请求观察、入队动作时做门禁，不负责令牌校验。

截帧校验包括：观察能力与应用白名单、当前活动应用必须与请求目标一致、宽高范围、JPEG 魔数、4 MB 上限；落盘后记录哈希与 2 分钟过期时间，并设为会话的当前帧；过期文件会被清理。

## 6. 桌面会话与指令：入队不等于执行

会话有四种状态：活跃、暂停、被接管、已终止；每次暂停/恢复/接管/释放/终止都会让「控制代次」加一，用于让在途指令失效。

动作白名单只有六种：点击、输入、按键、聚焦、界面自动化调用、界面自动化设值；后两种额外需要界面自动化能力。入队时还要求设备没有其它排队指令、必须引用**当前帧**（否则报「帧已过期」）、目标应用获准，并把当前帧清空。

指令状态从排队开始，设备来取指令时才做二次校验（会话状态、控制代次、帧哈希、活动应用、是否过期），通过才转为「已认领」，再由设备上报成功或失败；会话变化、暂停、接管会取消指令，认领后 30 秒未完成会过期。也就是说**「入队」只是登记意图，真正的许可发生在设备来取的那一刻**。

---

## 7. 连接与离线回放

连接会话有代次与游标：首次连接生成代次，重连时先校验代次，再算出「最新数据事件序号」，返回一个回放计划（源游标、最新游标、待拉取事件数、过期项、离线操作列表）。心跳默认 90 秒超时，会话 15 分钟有效期，缓存 24 小时。

对外呈现的四组状态都是**派生值而非存储字段**：传输状态（已连接/断开/失败）、订阅状态（失败/陈旧/追赶中/实时）、数据新鲜度（当前/缓存/过期）、执行归属（已租/自有/未知）。离线操作有六种状态，按幂等键去重；传输未连接时，远程类操作直接被标为「不确定」。

---

## 8. 发件箱：草稿到渠道的出口

草稿状态有八种，默认账户是「本地发件箱」，主题 500 字、正文 20 万字符、每类收件人最多 50 个、附件最多 20 个（校验产物存在、哈希一致、文件在盘）。

提交时先校验完整性，再按账户类型二选一生成一个**等待审批的任务**：有 SMTP 账户就走真实邮件，否则走本地发件箱写入；两者都带「草稿哈希」作为目标版本，防止审批后草稿被改动。审批通过后由效果执行器落地为本地发件箱文件或调用邮件发送；随后按审批与效果状态把草稿映射为已发送/已存储/已拒绝/不确定/失败（审批与效果机制见[判定审批机制说明](./判定审批机制说明.md)）。

---

## 9. 只读代码才会发现的事实

1. 出站意图链路在生产代码里没有消费者，统一入站层目前是**单向的**。
2. 默认飞书聊天客户端是自环调用本服务的聊天接口，超时 180 秒。
3. 邮件没有持久化游标；去重靠来源层，节流状态重启即清零。
4. 设备令牌鉴权与全局停止开关是两层独立机制。
5. 桌面指令「入队」不等于执行，设备取指令时才做完整二次校验。
6. 连接页的四组状态全是派生值；配对查询时「已批准」会自动转为「已兑换」。

| 方向 | 内容 |
|---|---|
| 输入 | 事件总线与存储、加密箱、共享契约枚举、审批与效果、外部 SDK 与命令行工具 |
| 输出 | 飞书消息与路由表、邮件转来源条目、入站幂等记录、设备与桌面视图、连接回放计划、发件箱效果 |
