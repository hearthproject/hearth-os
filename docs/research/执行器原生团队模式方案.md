# 执行器原生团队模式方案

> 状态：设计建议。当前 Hearth 0.8.0 已实现统一 `agentMode` 开关和 Native 团队闭环；Codex / DSH 仍属于“允许使用原生团队”，尚未达到“强制创建团队”。
>
> 适用范围：`apps/server/src/agent-mode.ts`、`apps/server/src/scheduler.ts`、`packages/codex-executor`、`packages/deepseek-executor`、`apps/web/src/components/AgentRoster.tsx`。

## 1. 结论

统一开关、各执行器使用自己的原生团队能力，是更自然的产品架构。

Hearth、Codex、DeepSeek Harness 都是完整执行主体，各自拥有执行循环和内部协作方式。Hearth 不应该代替 Codex 创建一支 Hearth 团队，也不应该代替 DSH 管理其成员。Hearth 的职责是统一任务入口、上下文、审批、产物、运行记录和结果展示。

但这不等于“点击团队就一定能看到成员”。当前实现更准确的语义是：

> **团队开关 = 允许当前执行器使用自己的原生团队能力。**

如果产品要承诺“必须至少出现一个内部成员”，就需要为每种执行器增加明确的强制启动方式，不能只靠提示词。

## 2. 目标架构

三类执行器各自负责自己的执行循环和团队机制，Hearth 只做外围统一。

| 执行器 | 负责人 | 团队由谁创建 | Hearth 负责什么 |
|---|---|---|---|
| Hearth | Hearth | Hearth | 创建成员、分配任务、收集回执、展示 roster |
| Codex | Codex | Codex | 发起任务、传递团队意图、接收过程事件、保存产物 |
| DeepSeek Harness | DSH | DSH | 发起任务、传递团队意图、接收过程事件、保存产物 |

对应到产品语义：

- 选择 Hearth 并开启团队：Hearth 既是负责人，也是团队管理者。
- 选择 Codex 并开启团队：Codex 是负责人，Codex 自己决定是否启动内部 Agent。
- 选择 DSH 并开启团队：DSH 是负责人，DSH 自己决定是否使用内部协作方式。

Hearth 不把 Codex / DSH 的内部成员拉进自己的团队，也不冒充它们的编排者。

## 3. 三种执行器的语义矩阵

| 执行器 | 请求团队后的行为 | 当前保证程度 | 团队展示来源 |
|---|---|---|---|
| Hearth | Hearth 注入只读成员工具并编排成员 | **确定编排** | Hearth 自己的 `subagent.*` 事件 |
| Codex | 提示词表达团队意图，Codex 自行决定是否组队 | **允许，不保证** | Codex 返回的协作事件（如果可用） |
| DSH | 提示词表达团队意图，DSH 自行决定是否组队 | **允许，不保证** | DSH 返回的协作事件（如果可用） |

当前 0.8.0 的实现落点：

- `resolveAgentMode` 对非 Native 执行器返回 `effective: "executor-managed"`。
- `agentModePrompt` 对 Codex / DSH 只说明“允许自行决定是否使用内部子代理”，并要求如实说明。
- `scheduler` 只在 Native 且 `effective === "team"` 时注入 `agent`、`agent_wait` 等 Hearth 委派工具。
- Codex 的 `multi_agent` 配置和 DSH 的团队选项没有被 Hearth 直接打开。

因此，当前方向与“各执行器原生团队”一致，差别只在：

1. 没有强制启动；
2. 没有把“保证级别”显式暴露给用户；
3. 没有区分展示来源是 Hearth 成员还是执行器内部成员。

## 4. “允许使用”与“保证启动”必须分开

这是本方案最重要的产品判断。

### 4.1 允许语义

用户点击“团队”，表示授权当前执行器使用自己的团队能力，但是否真正拆出成员由执行器判断。

优点：

- 简单任务不会被强制拆成多个成员，token 和延迟更可控。
- 尊重 Codex / DSH 自己的运行策略。
- Hearth 不需要维护第二套编排器。

风险：用户可能把“团队”理解成“一定有成员”，产生预期落差。

### 4.2 保证语义

用户点击“团队”，产品承诺至少出现一个内部成员。

这需要每个执行器都有可验证的强制启动方式：

- Hearth：Hearth 自己创建成员，天然可保证。
- Codex：需要确认并写入 Codex 真实支持的 `multi_agent` 配置或启动参数。
- DSH：需要确认 SDK 是否暴露团队 / 子 Agent 选项。

如果执行器没有这种配置面，就不能用提示词假装强制，否则只是语义表演。

### 4.3 建议

保留统一开关，但用“保证级别”区分底层能力：

| 保证级别 | 含义 | 适用 |
|---|---|---|
| `hearth-orchestrated` | Hearth 确定创建并管理成员 | Native 团队 |
| `native-required` | 执行器必须启动至少一个内部成员 | Codex / DSH 确认支持后 |
| `native-advisory` | 允许执行器使用内部团队，不保证成员 | Codex / DSH 当前默认 |
| `unsupported` | 执行器不支持团队模式，开关禁用或提示 | 能力未验证时 |

## 5. 推荐协议改动

### 5.1 模式解析

在现有 `AgentModeResolution` 上增加保证级别，不改任务和运行状态机：

```ts
type TeamGuarantee =
  | "hearth-orchestrated"
  | "native-required"
  | "native-advisory"
  | "unsupported";

interface AgentModeResolution {
  requested: "single" | "team";
  effective: "single" | "team" | "executor-managed";
  executorId: ExecutorId;
  guarantee: TeamGuarantee;
}
```

### 5.2 事件与证据

`agent.mode` 事件和 `run-evidence.json` 增加：

```json
{
  "requested": "team",
  "effective": "executor-managed",
  "executorId": "codex",
  "guarantee": "native-advisory"
}
```

这样导出运行证据时能回答两个问题：

- 用户请求了什么模式？
- 实际由谁编排，保证到什么程度？

### 5.3 成员来源

如果未来接入 Codex / DSH 的内部成员事件，事件负载增加来源字段：

```json
{
  "source": "hearth | codex | dsh",
  "orchestrator": "hearth | executor",
  "childId": "..."
}
```

Hearth 自己的 roster 只消费 `source=hearth` 的成员；执行器返回的成员单独分组展示，不能混在一起。

### 5.4 不注入 Hearth 委派工具

Codex / DSH 的团队模式不注入 `agent`、`agent_wait`、`agent_kill` 等 Hearth 工具。

原因：

- 避免让 Codex / DSH 误以为自己应该调用 Hearth 的委派协议；
- 避免 Hearth 误以为自己管理了执行器的内部成员；
- 保持执行器内部工具面和权限边界不变。

## 6. UI 建议

### 6.1 开关文案

当前“单 Agent / 团队”可以保留，但增加保证级别提示：

- Hearth：`团队 · Hearth 编排`
- Codex / DSH：`团队 · 由执行器决定`
- 不支持：`团队 · 当前执行器不支持`

开关的 tooltip 不要写“将创建团队”，而写“允许当前执行器使用其原生团队能力”。

### 6.2 Roster 展示

| 情况 | 展示 |
|---|---|
| Hearth 团队 | 展示 Hearth 创建的成员、状态、回执、证据 |
| Codex / DSH 返回成员事件 | 分开展示“执行器内部成员” |
| Codex / DSH 没有返回事件 | 显示“执行器未报告成员”，不推断“没有使用” |
| 执行器不支持 | 隐藏团队开关或显示禁用原因 |

没有成员事件不等于没有内部协作。执行器可能没有把内部事件暴露给 Hearth，UI 不能把“未报告”说成“未使用”。

### 6.3 成本提示

团队模式可能增加 token 和延迟。开关旁应说明：

> 团队模式会授权执行器并行拆分任务，复杂任务更快，简单任务可能更贵。

## 7. 分阶段落地

### 阶段 1：把语义说清楚（低风险）

- 保持当前 `native-advisory` 行为。
- UI 增加“由执行器决定”提示。
- `agent.mode` / run-evidence 增加 `guarantee` 字段。
- Roster 区分 Hearth 成员与执行器成员。

这一阶段不改变执行器内部行为，只修正产品承诺和可观测性。

### 阶段 2：接入 Codex 原生团队（需验证）

- 确认 Codex 当前版本是否支持 `multi_agent` 配置或启动参数。
- 如果支持，按会话 / 运行写入该配置，并在运行结束后恢复。
- 验证 Codex 是否真的产生内部成员事件；如果没有事件，仍标记为 `native-advisory`。

### 阶段 3：接入 DSH 原生团队（需验证）

- 检查 DSH SDK 是否暴露团队、子 Agent 或协作模式选项。
- 只有 SDK 明确支持时才标记 `native-required`。
- 不通过自然语言提示假装强制。

### 阶段 4：强制模式（可选）

- 仅对已验证支持的执行器开放 `native-required`。
- 启动后如果未观察到成员，任务不应静默完成；应显示“执行器未按团队模式启动”，由用户决定重试或降级为单 Agent。
- 强制模式应单独标注成本风险，不建议默认开启。

## 8. 非目标

- 不新建第二套 Orchestrator 或消息总线。
- 不让 Hearth 替 Codex / DSH 管理内部成员。
- 不把执行器内部成员伪装成 Hearth 成员。
- 不通过提示词假装“强制团队”。
- 不用团队模式替代审批、对账、产物验证和完成证据。
- 不为简单任务默认强制拆分成员。

## 9. 验收标准

### 当前“允许”语义的验收

- Native 团队模式确定产生 Hearth 成员，事件和 roster 可见。
- Codex / DSH 团队模式不注入 Hearth 委派工具。
- UI 明确显示“由执行器决定”，不承诺一定出现成员。
- `agent.mode` 和 run-evidence 能读出 `guarantee`。
- 没有执行器成员事件时，UI 显示“未报告”，不显示“未使用”。

### 未来“保证”语义的验收

- 选择 `native-required` 后，执行器必须产生至少一个可验证的内部成员事件。
- 只有确认支持该能力的执行器才能显示“保证团队”。
- 未产生成员时任务不能静默成功，必须有明确状态和用户可执行的下一步。
- 强制模式与成本提示同时出现。

## 10. 最终建议

短期保持 0.8.0 的“允许原生团队”实现，不强行改 Codex / DSH 的内部协议；先把 `guarantee`、成员来源和 UI 文案补齐。

中期分别验证 Codex 和 DSH 的真实团队配置面，再决定是否开放“保证团队”。

长期形成统一产品语义：

> 用户选择的是“谁来负责这次任务”，团队开关决定“这个负责人采用单人还是自己的团队方式”。Hearth 不统一创建所有团队，只统一任务入口、证据和结果展示。
