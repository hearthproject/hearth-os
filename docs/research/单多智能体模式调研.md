# 单智能体与多智能体双模式调研

本文回答三个问题。DeepSeek Harness 怎么做单/多智能体切换；Hearth 适合怎么做到"默认单 agent、需要时开团队"，且不做系统性改造；这套能力是否只能落在 Native 执行器上。

结论基于 2026-11-27 的 Hearth `v0.7.5` 工作树、`@deepseek-ai/dsh-sdk-client 0.2.2-rc.1`、`@deepseek-ai/dsh-agent-team 0.2.2-rc.2`，以及 `@openai/codex 0.166.0` 的公开资料。

## 结论摘要

DeepSeek 的"单/多"不是两套 runtime，而是同一个 agent loop 上的**会话级工具面开关**。团队能力默认关闭，打开只是在子代理树上挂一块共享任务板；关掉时只隐藏团队工具和提示，任务与子代理数据都保留。

Hearth 已经有实现这套开关的全部零件：`ConversationSettings`、按会话持久化的 `settings_json`、`SubagentTaskManager`、`agent` 工具、`output_schema` 校验。缺的不是编排器，而是**模式开关、工具面裁剪和可信回执**。

因此建议只做四件事：会话级 `agentMode`；团队模式才注入 `agent`；团队 v1 只开只读 profile、Lead 是唯一写者；用结构化回执和证据替代自由文本 summary。不引入 PlanStore、CAS、独立 Orchestrator、Workboard 文件或 worktree 合并。

执行器边界要分开看。Hearth 能编排并验收的只有 Native；DSH 能用自己的团队，Hearth 目前既没挂载也看不到；Codex 能开原生 subagents，但 SDK 不暴露子代理事件，属于黑盒。

## 一、DeepSeek Harness 的做法

### 1.1 底座是插件组合，不是多套运行时

DeepSeek Harness（`deepseek-ai/deepseek-harness`，MIT）建立在 Cordis 的 "everything is a plugin" 架构上。一次运行是 profile、bundle、patch 按顺序叠出来的插件树，模型适配器、工具注册表、会话日志和 agent loop 本身都是可替换的插件，没有需要打补丁的特权核心。官方给"让某个会话拥有不同能力集"的答案就是组合一个 agent preset，而不是 fork 运行时。

`web`、`headless`、`sdk`、`sdk-minimal`、`acp` 是随包发布的 profile；`--patch` 可以在不改变上游代码的前提下插入或替换任意配置行。Hearth 的 DSH 适配器用的正是这条路：固定 `--profile sdk`，再叠加自己生成的 patch 文件。

### 1.2 子代理和团队是两层能力

**子代理层是常驻的。** `dsh-base` 提供 continuable subagent、`list_agents`、`send_message`、`wait_agent`、`interrupt_agent`，以及宿主级的 `subagent.maxDepth`、`subagent.maxActiveSubagents` 上限。这一层不依赖团队开关。

**团队层是可选的。** `dsh-agent-team` 在已有的子代理树上加一块持久共享任务板：任务有依赖、owner、compare-and-set revision，`writeScopes` 只是"计划改哪些文件"的提示。`dsh-tool-agent-team` 再给成员九个工具：`spawn_teammate`、`send_message`、`list_agents`、`wait_agent`、`interrupt_agent`，以及 `team_task_create/list/get/update`。只有 Lead 能创建和中断队友，队友只能自己认领任务。

团队不创建新的成员体系。树的根会话就是 Team 的 owner，队友就是 continuable subagent，消息路由、冷恢复、中断都归子代理运行时。

### 1.3 开关语义：会话级、默认关、只隐藏工具

产品化包 `@deepseek-ai/dsh-agent-team` 的说明写得很直接：

- 新会话，包括普通 fork，默认关闭 Team。
- 在根会话的"模型与推理等级"菜单里选择 **Use Agent Teams**。
- 关掉会把 Team 工具和 guidance 从后续步骤中隐藏，**但保留任务和子代理**。
- 选择会持久化，重启后仍在；历史任务板没有保存过选择的，保持开启。
- 后代会话跟随当前 root 的模式；`defaultEnabled: true` 可以让新根会话在第一步之前就默认打开。

也就是说，开关改变的是"模型下一步能看到哪些工具、读到哪段 policy"，不是"有没有另一个编排服务"。运行中的已接纳操作会跑完，排队中的操作在启动时重新检查模式。

### 1.4 官方取舍：协调，不做隔离

这套设计对自己的限制写得很坦白：

- **一个进程、一个共享 checkout**。没有 worktree、没有 merge、没有文件锁，成员看到的是同一份工作区。
- **writeScopes 只是警告**。Bash、格式化器、代码生成器和外部写入都可以绕过，Lead 必须自己复核最终 diff。
- **扁平 roster**，不能嵌套 Team；只有祖先能中断后代。
- **不自动释放 owner**。空闲、中断、进程退出都不会把任务还回池子。
- **prompt policy 是协调，不是限制**。

换句话说，DeepSeek 把多 agent 定义成"共享任务板 + Lead 协调 + Lead 复核"，而不是"隔离执行 + 自动合并"。这和 Hearth 上一份方案里"worktree 隔离 + Orchestrator 串行合并"是两条路线。

### 1.5 一个容易抄错的细节

**Team 关掉不等于不能派子代理。** 子代理工具本来就在 base 里，Team 只加任务板。所以 DSH 的开关严格说是"团队协作 on/off"，不是"单 agent / 多 agent"。

Hearth 如果照抄，会得到一个"单模式仍然会偷偷派子代理"的系统，token 并没有省下来。这一点必须做得比 DSH 更彻底：单模式连 `agent` 工具一起收走。

## 二、Hearth 的现状

### 2.1 零件已经齐了

- `ConversationSettings` 里有 `approvalMode`、`executionMode`、`preferredExecutorId`、`collaborationMode`，存在 `conversations.settings_json`，读写都走 `mergeConversationSettings`，加字段不需要迁移。
- `scheduler.ts` 在 Native 分支里无条件创建 `SubagentTaskManager`、`agent` 工具和 `agent_wait/status/kill`。
- `agent` 工具已经支持四种 profile：`explore`、`plan`、`review` 只读，`general-purpose` 在 worktree 里写。
- `output_schema` 已经接通 Ajv，子代理完成前会校验结构化输出。
- `plan` 已经在 `AgentToolState` 里，带 `owner`、依赖和状态，每轮由 `renderPlanContext` 注入。

缺的是把这四样拼成一个"可选的能力面"，以及让子代理的结果可信。

### 2.2 团队模式现在不可信的六个缺口

这些问题与开不开团队无关，但团队模式会把它们放大：

1. **证据在 `%TEMP%`**。transcript、checkpoint、journal 都在临时目录，任务结束后不可追溯。
2. **子代理绕过审批**。`SubagentToolOptions` 没有 `onAuthorizeTool` 字段，父 run 有，子 run 没有。
3. **子代理不进账本**。`executeAgentJob` 没有传 `operationLedger`、`runId`、`taskId`、`onContextEvent`，工具副作用不落 `run_operations`，也不进事件流。
4. **没有全局总量**。`MAX_TOTAL_SUBAGENTS = 8` 是死常量，从未被引用；只有每个工具实例 4 个，嵌套后单次 run 极端可到 4+16+64。
5. **只读子代理共享父 outDir**。`outDir/.hearth/executing.json` 是单槽标记，子 run 会看到并清掉父正在使用的"未执行完"标记。
6. **worktree 没有合并**。子代理只 commit 到自己的分支，父任务需要手动 cherry-pick；`TaskWorktreeService` 没有 merge 能力。

前五条是"信任"问题，第六条是"成果落地"问题。团队 v1 只开只读 profile 可以绕开第六条，前五条必须补。

### 2.3 和 DSH 的关键差异

| 维度 | DeepSeek Harness | Hearth 现状 |
|---|---|---|
| 会话模型 | root Session + 后代 Agent，树内共享 | task + run，子代理是同一进程里的嵌套 run |
| 模式载体 | 根会话的 Team 选择，持久化 | 会话 settings，但没有任何 agent 模式字段 |
| 工具面 | 插件组合决定，关掉即隐藏 | Native 分支无条件注入 |
| 任务板 | 独立 Team 服务，CAS revision | plan 在 run state 里，单写者 |
| 隔离 | 无，共享 checkout，writeScopes 提示 | worktree 隔离，但没有 merge |
| 可观测性 | session tree + 持久日志 | 子代理 transcript 在 tmpdir，事件不进任务时间线 |

Hearth 的优势是账本、审批、worktree 隔离和事件溯源；劣势是这些优势目前只覆盖父 run。

## 三、建议方案

### 3.1 两种模式的语义

| | 单智能体（默认） | 团队 |
|---|---|---|
| 模型可见的委派工具 | 无 `agent`，无 lifecycle tools | `agent` + `agent_wait/status/kill` |
| 可用 profile | — | v1 只有 `explore` / `plan` / `review` |
| 写权限 | 主 agent 正常写 | Lead 是唯一写者，队友只读 |
| 计划 | 可选，纯记录 | plan 作为任务板，步骤可绑 agent |
| 成本 | 与今天的单 agent 持平 | 明确提示 token 更高，不做预算闸门 |

默认 single，按会话保存，下一轮生效。历史任务不受影响。

### 3.2 四个改动

**① 会话开关**

`ConversationSettings` 增加 `agentMode: "single" | "team"`，默认 `single`；`ConversationSettingsPatch` 与 `mergeConversationSettings` 各加一行；`chat-routes` 的 zod schema 增加可选 enum；`ChatPage` 输入区设置弹层加一个 switch，文案对齐 DeepSeek："复杂任务表现更佳，token 开销也相应更高"。

不需要给 tasks 表加列。任务开始时读取会话设置，把生效模式写进 run 事件或 run-manifest，用于复盘。

**② 工具面裁剪**

`scheduler.ts` 现在只要 `executorId === "native"` 就进入子代理装配。改成 `executorId === "native" && agentMode === "team"` 才进入；single 下不创建 manager、不注入 `agent`、不注入 lifecycle tools，steering 也不接。

single 模式的系统提示加一句："本次运行是单智能体模式，不要委派子代理，直接完成任务。" 模型看不到工具，这句话只是兜底。

这是两种模式的全部机制，不改 `runAgent` 主循环，不改工具调度、压缩、checkpoint 或审批状态机。

**③ 团队 v1 只开只读**

给 `createAgentTool` 增加 `allowedTypes` 选项，`agentDefinition` 的 enum 由它生成。v1 传 `["explore", "plan", "review"]`，`general-purpose` 暂时不暴露。

这样团队模式的能力边界是：并行读代码、并行调研、独立 review；写仍然由 Lead 完成。既拿到并行收益，又完全避开 worktree 合并。等证据链和合并方案成熟，再开 `general-purpose`。

**④ 可信回执与证据**

- `agent` 接一个可选 `stepId`。成功返回时把对应 plan 步骤标为 `completed`；失败时保持原状态并在 notes 写原因，**不扩展 `AgentPlanStepState`**（现有 union 会被 `planToTodos` 直接投影成 todo 状态，加 `failed` 会破坏类型和恢复）。
- 团队模式默认注入一份 canonical `output_schema`：`status`、`summary`、`evidence[]`、`artifacts[]`、`unresolved[]`。模型仍可用自己的 schema 覆盖。
- 子代理的 transcript、checkpoint、journal、report 落到 `taskRoot/.hearth/agents/<childId>/`，不再进 `%TEMP%`。
- 子 run 传 `onAuthorizeTool`，写操作走父任务的审批链；传 `operationLedger` 和 `runId`，至少让操作能归到父 run 并附 `agentId`。
- 每个 child 用独立 `outDir`，避免 `executing.json` 互踩。
- 把 `MAX_TOTAL_SUBAGENTS` 变成真正的任务级预算，并在 `agent` 工具里执行。

成本展示只做拆解，不做闸门。`runtime.ts` 已经 `if (result.usage) addUsage(usage, result.usage)`，子代理 token 早就算进父 run；`agent.usage.attributed` 只能用于"谁花了多少"的展示，不能再加总一次。

### 3.3 不做什么

- 不做 `PlanStore`。plan 已经是单写者、随 checkpoint 恢复，够用。加 SQLite 表、revision CAS、`PLAN_REVISION_CONFLICT` 会与现有 `PlanService` 的同名错误码和 plans 表冲突。
- 不做 `dispatch_plan` / 独立 Orchestrator。模型自己按 plan 调 `agent` 就是编排；runtime 同一轮已经用 `Promise.all` 并行执行多个工具调用，不需要第二个调度器。
- 不做 Workboard 文件。plan 就是任务板，`renderPlanContext` 已经每轮注入。
- 不做多写者合并。worktree 子代理的 merge 目前不存在，团队 v1 只读。
- 不改 `runAgent` 主循环、压缩、checkpoint 格式或 task 状态机。

### 3.4 改动面与工期

| 阶段 | 内容 | 文件 | 估算 |
|---|---|---|---|
| P1 | 会话开关、工具面裁剪、prompt policy、UI | `core/types.ts`、`chat-routes.ts`、`ChatPage.tsx`、`scheduler.ts` | 0.5–1 天 |
| P2 | 只读 profile 白名单、`stepId` 绑定、canonical report schema | `subagents.ts`、`plan-state.ts`、prompts | 1–2 天 |
| P3 | taskRoot 证据、审批、账本、独立 outDir、全局预算 | `subagents.ts`、`native-executor.ts`、`run-evidence.ts` | 2–3 天 |

合计约一周。没有新表、没有新进程模型、没有新编排服务。改动集中在 7–8 个文件。

## 四、执行器边界

### 4.1 三种"多 agent"要分开看

| 能力 | Native | Codex | DSH |
|---|---|---|---|
| Hearth 在 run 内注入 `agent` | 是，走 `extraNativeTools` | 否，适配器不接收额外工具 | 否，适配器不接收额外工具 |
| 执行器自带多 agent | —（就是 Hearth 这套） | 是，`[features] multi_agent` + `[agents] max_threads/max_depth`，SDK 的 `config` 可按 run 覆盖 | 是，agent-team 包 + `subagent.maxDepth` 等，可通过 profile patch 挂载 |
| Hearth 能看到子代理轨迹 | 是，transcript、事件、账本都能接 | 否，SDK 的 `ThreadItem` 没有 subagent 事件类型 | 部分。SDK 有 `subscribeSessionTree()`，按 `subagent.started` 发现子会话；当前适配器只处理 `session.event`，其余通知被丢弃 |
| Hearth 能审批队友的写 | 是，可补 `onAuthorizeTool` | 否，执行器内部策略 | 待验证。审批回调带 sessionId，teammate 是否走同一条回调需要实测 |
| Hearth 级跨执行器 fan-out | `TaskGraph` + `DelegationService` 对所有执行器成立；子任务没有 conversation 所以能并行，每执行器 `maxParallel=3`；但今天只挂在 HTTP API 上，模型没有工具 | 同左 | 同左 |

### 4.2 结论

**不是"只能原生"，但"能编排、能审计、能验收"的只有原生。**

- **Hearth 编排并验收**：只有 Native。因为 `agent` 工具只能进 Native 的工具循环，证据也只能从 Native 的 runtime 事件和账本里拿。
- **执行器自己编排**：Codex 和 DSH 都能开。Codex 在 single 模式下甚至可以用 `config: { features: { multi_agent: false } }` 明确关掉原生 subagents，成本意义真实存在，只是过程不可见。DSH 可以用 patch 挂 agent-team，再用 session tree 观察，但版本、包体、审批和用量都要额外对齐。
- **Hearth 跨执行器派子任务**：任务级，不是 run 内 teammate。粒度粗、延迟高，但它是唯一对三种执行器都成立的方式。

### 4.3 产品建议

1. **v1 的团队开关只对 Native 生效**。Codex/DSH 下显示"该执行器自行管理多 agent"，不要假装 Hearth 在编排。
2. **不要在 DSH 外面再套一层编排**。用户选了 DSH，就让它用自己的 team；Hearth 只做 patch 挂载和 session tree 展示。代价是 Hearth 固定的 `0.2.2-rc.1` 与 team 包的 `0.2.2-rc.2` 需要对齐，还要额外安装实验包。
3. **Codex v1 不做团队模式**。能开但不可审计，和 Hearth"证据可留下来"的产品主张冲突。single 模式下可以顺手把它的 `multi_agent` 关掉。
4. **跨执行器 fan-out 留到以后**。真要做，把 `DelegationService` 接成模型工具，而不是引入第三套编排。

## 五、验收与风险

### 5.1 验收

- single：工具 schema 里没有 `agent`；一个十轮任务不产生 `subagent.delegated`；token 与改造前的单 agent 持平。
- team：三个 `explore` 并行返回；报告通过 canonical schema；证据落 `taskRoot/.hearth/agents/`；父 run 的 run-evidence 能列出所有子代理的操作。
- 切换：关掉开关后，同一会话下一轮不再出现 `agent`；历史任务板、计划、子代理记录仍可读。
- 回归：现有 493 个测试文件、约 4800 个用例保持全绿。

### 5.2 风险与未决

- **行为变化**。今天所有 Native 任务都能派子代理，改成默认 single 会影响老会话。需要一次性提示，或给已有会话保留 team 的迁移策略。
- **成本**。团队模式 token 明显更高，且 Hearth 不做预算闸门；只能靠 UI 提示和用户自律。
- **只读队友也花钱**。v1 的价值是延迟和覆盖，不是省钱；默认关是必要的。
- **DSH 版本**。team 包与 SDK 版本不一致，实验包还在 rc；挂载前要确认 sdk profile 的 bundle 是否已含 continuable subagent 和 durable session。
- **DSH 用量**。SDK 只返回父会话 usage，子会话的 token 是否能拿到尚未验证。
- **Codex 可见性**。第三方资料描述了 `[features] multi_agent` 和 `[agents]` 配置，但 Hearth 的 SDK 类型面没有子代理事件，需要在 0.166.0 上实测。
- **合并**。`general-purpose` 一旦开放，worktree 合并就是硬前提；这一天到来之前，团队模式必须保持只读。

## 六、下一步

如果只做一件事，做 P1：开关 + 工具面 + policy。它不改主循环，三天内能看到"单/多"的真实差异，也能立刻止住单任务里无意的多 agent 开销。

如果做两件事，加 P2：只读团队 + 结构化回执。这是能力提升的主体。

P3 是让团队模式"可信"的前提，不做的话，团队模式只是一个更贵的单 agent。
