# 执行器工具与提示词边界调研

本文回答三个问题。Hearth 自带工具是否只对 Native 生效，提示词系统是否只影响 Native，以及任务级浏览器与直接使用 Playwright 的差别。结论基于 2026-11-25 的工作树源码。

## 结论摘要

Hearth 的浏览器、Web 搜索、技能、后台任务、子代理、目标控制和任务管理扩展工具通过 `extraNativeTools` 进入 Native。Codex 与 DSH 不读取这个字段，继续使用各自运行时的工具循环。

Hearth 生成的任务 prompt 会交给所有执行器。Native 还使用 Hearth 自己的完整系统提示词、执行契约、编码 harness、记忆和项目说明装配。Codex 与 DSH 使用各自运行时的系统提示词、计划模式和项目说明加载机制。

Hearth 资料库是明确的跨执行器共享能力。Native 使用原生资料库工具，Codex 与 DSH 使用同一个标准 MCP 服务。设置页配置的普通 MCP 当前只注入 Native。

浏览器工具是任务级平行能力。它基于 Playwright 引擎和官方 Playwright Extension，增加任务会话、用户接管、控制 epoch、截图证据、配方、输入脱敏和在任务卡中的恢复入口。Codex 与 DSH 仍可以通过自己的 Shell 运行 Playwright 脚本，但不会自动进入这条产品链路。

## 第一问，工具作用范围

### Native

Native 会接收 Hearth 构造的全部 `extraNativeTools`。当前装配包括：

- 个人资料读取和本体展开。
- 目标控制。
- 背景任务和任务管理。
- Web 搜索。
- 浏览器二十个工具。
- 资料库原生工具。
- 技能。
- 用户配置的 MCP 工具。
- 子代理生命周期工具。

装配位置见 [scheduler.ts](https://github.com/hearthproject/hearth-os/blob/main/apps/server/src/scheduler.ts)。Native 适配器将这些工具加入权限并传入 `extraTools`，见 [executor-adapter.ts](https://github.com/hearthproject/hearth-os/blob/main/apps/server/src/executor-adapter.ts) 和 [native-executor.ts](https://github.com/hearthproject/hearth-os/blob/main/apps/server/src/native-executor.ts)。

### Codex

Codex 接收工作目录、共享任务 prompt、网络权限、沙箱模式、审批策略、恢复 thread、资料库 MCP 和上下文事件。Codex 适配器不使用 `extraNativeTools`。

Codex 的文件修改、命令执行、计划、审批、子代理和会话 thread 来自 Codex SDK 与 CLI 运行时。Hearth 集成在 [executor.ts](https://github.com/hearthproject/hearth-os/blob/main/packages/codex-executor/src/executor.ts) 中关闭了 Codex 的内置 Web 搜索。

### DSH

DSH 接收共享任务 prompt、工作目录、权限、模型设置、恢复 session、资料库 MCP 和进度事件。DSH 适配器同样不使用 `extraNativeTools`。

DSH 的文件系统、PowerShell、Bash、Web、技能、任务、目标、计划模式和子代理工具来自标准预设和插件。相关接入位置见 [deepseek-executor](https://github.com/hearthproject/hearth-os/tree/main/packages/deepseek-executor) 和 [executor-adapter.ts](https://github.com/hearthproject/hearth-os/blob/main/apps/server/src/executor-adapter.ts)。

### 工具边界

| 能力 | Native | Codex | DSH |
|---|---|---|---|
| `extraNativeTools` | 接收并执行 | 不注入 | 不注入 |
| `browser_*` | 接收 | 不接收 | 不接收 |
| Web 搜索扩展工具 | 按任务意图注入 | 使用运行时自身能力，内置搜索关闭 | 使用 DSH 预设能力 |
| 资料库原生工具 | 使用 | 不注入 | 不注入 |
| 资料库 MCP | 同一服务 | 使用 | 使用 |
| 设置页普通 MCP | 当前注入 | 当前不注入 | 当前不注入 |
| Shell 中运行 Playwright 脚本 | 可以 | 可以 | 可以 |
| Hearth 浏览器任务会话 | 自动使用 | 不自动使用 | 不自动使用 |

## 第二问，提示词作用范围

### 共享任务 prompt

Hearth 在调度器里生成任务 prompt，包含任务标题、目标、输入文件、输出目录、网络范围、运行时依赖、验收要求、审批要求和完成约束。当前执行器统一接收这个 `prompt`。

生成逻辑位于 [workspace.ts](https://github.com/hearthproject/hearth-os/blob/main/apps/server/src/workspace.ts) 的 `buildTaskPrompt`，执行调用位于 [scheduler.ts](https://github.com/hearthproject/hearth-os/blob/main/apps/server/src/scheduler.ts)。

因此三个执行器都会受到 Hearth 对任务目标、路径、输出和验收的约束。

### Native system prompt

Native 使用 Hearth 自建的完整 system prompt。主要来源如下：

- [native-executor.ts](https://github.com/hearthproject/hearth-os/blob/main/apps/server/src/native-executor.ts) 装配执行器、任务画像和上下文。
- [prompts.ts](https://github.com/hearthproject/hearth-os/blob/main/packages/agent-runtime/src/prompts.ts) 提供运行契约和提示词模块。
- [harness/prompt.ts](https://github.com/hearthproject/hearth-os/blob/main/packages/agent-runtime/src/harness/prompt.ts) 提供编码 harness 和环境信息。
- Hearth 的目标、记忆、项目档案、工作风格、任务 prompt registry 和浏览器工具规则只进入 Native。

### Codex system prompt

Codex 使用 SDK 和 CLI 自带的 system prompt、工具说明和审批循环。Hearth 只提供任务输入、工作目录、权限、网络、MCP、恢复 thread 和事件转发。

Codex 对 `AGENTS.md` 等项目说明的发现由 Codex 运行时处理。Hearth 不把 Native 的项目说明装配结果重复注入 Codex。

### DSH system prompt

DSH 使用标准预设中的 persona、指令加载、计划模式、上下文压缩、技能、任务、目标、子代理和 Web 工具。配置来自 `@deepseek-ai/dsh-web-app/presets/standard.patch.yml`。

项目说明由 `@deepseek-ai/dsh-agent-instructions` 加载。Hearth 传递任务 prompt 和执行参数，DSH 决定如何把预设、项目说明和任务组合进自己的 session。

### 提示词边界

| 提示词层 | Native | Codex | DSH |
|---|---|---|---|
| Hearth 任务 prompt | 接收 | 接收 | 接收 |
| Hearth 非 Native 输出补充要求 | 不接收 | 接收 | 接收 |
| Hearth Native system prompt | 使用 | 不使用 | 不使用 |
| Hearth 记忆、目标、档案注入 | 使用 | 不使用 | 不使用 |
| Hearth 编码 harness | 使用 | 使用 Codex 自己的 harness | 使用 DSH 预设 |
| 项目说明发现 | Native harness | Codex SDK/CLI | DSH agent-instructions |
| 计划模式提示词 | Native prompt | Codex plan mode | DSH plan preset |
| 浏览器工具规则 | 随 `extraNativeTools` 进入 Native | 无 Hearth 浏览器工具说明 | 无 Hearth 浏览器工具说明 |

## 浏览器工具与 Playwright

| 能力 | Hearth 浏览器工具 | 直接 Playwright 或脚本 |
|---|---|---|
| 浏览器引擎 | Playwright | Playwright |
| 连接日常 Chrome | 官方 Playwright Extension | 调用方自行配置 Extension |
| 受管 Chrome fallback | 自动 | 调用方自行实现 |
| 任务级会话保存 | 有 | 调用方自行实现 |
| 跨运行标签页恢复 | 有 | 调用方自行实现 |
| 用户接管 | 有控制状态、类型和归还动作 | 调用方自行实现 |
| 控制 epoch | 有，旧元素引用失效 | 调用方自行实现 |
| 多 frame 快照 | 有 | Playwright API 提供底层能力 |
| 开放 Shadow DOM 扫描 | 有 | 调用方编写扫描逻辑 |
| Canvas 坐标交互 | 有 | Playwright API 提供底层能力 |
| 输入脱敏 | journal、checkpoint、progress、审批和错误统一处理 | 调用方自行处理 |
| 截图证据 | 有任务级证据目录 | 调用方自行管理 |
| 任务运行卡接管按钮 | 有 | 无 Hearth 任务 UI |
| 完成断言 | 只记录证据 | 调用方自行定义 |

Playwright 提供页面协议和自动化 API。Hearth 提供任务级协作状态、证据和恢复。两者是上下层关系。

## 浏览器设置和会话

独立浏览器设置页已删除。浏览器状态按任务显示在运行卡中，接口包括：

| API | 用途 |
|---|---|
| `GET /api/tasks/:id/browser` | 读取任务浏览器状态 |
| `POST /api/tasks/:id/browser/takeover` | 用户接管 |
| `POST /api/tasks/:id/browser/release` | 归还 Agent |
| `POST /api/tasks/:id/browser/connect` | 重新连接 Extension |
| `POST /api/tasks/:id/browser/close` | 关闭当前任务浏览器 |

旧域名白名单、高风险域名、固定任务并发、固定标签数和空闲回收设置不再存在。并发和标签数量由活动会话、模型调用和机器资源决定。

## 设置页普通 MCP

调度器在 `executorId === "native"` 条件下创建设置页普通 MCP 工具。Codex 与 DSH 当前只接收 `hearth` 资料库 MCP。

用户配置的普通 MCP 要进入 Codex 与 DSH，需要在调度器中增加统一装配，并处理三个运行时的 MCP 配置格式、工具命名、审批和恢复差异。

## Linger 调研

参考材料：

- [Desktop and Browser](https://github.com/simplexai-labs/linger/blob/main/docs/desktop-and-browser.md)
- [Architecture](https://github.com/simplexai-labs/linger/blob/main/docs/architecture.md)
- [user_chrome_session.go](https://github.com/simplexai-labs/linger/blob/main/apps/computer/local-daemon/internal/linger/localtools/user_chrome_session.go)
- [browser_connection.go](https://github.com/simplexai-labs/linger/blob/main/apps/computer/local-daemon/internal/linger/localtools/browser_connection.go)
- [cua.go](https://github.com/simplexai-labs/linger/blob/main/apps/computer/local-daemon/internal/linger/localtools/cua.go)

Hearth 采用的思路包括日常 Chrome 登录态、官方 Playwright Extension、受控子进程 token、每任务独立连接、用户接管时不抢回前台、复杂界面使用坐标和截图、输入结果未知时不盲目重放。

Hearth 没有采用 Linger 的固定空闲回收、单一 Chrome seat、任务串行限制、高风险域名策略和云端多租户结构。Hearth 选择任务级独立 Extension 连接，资源主要由会话和机器决定。

## 实际效果

浏览器能力可以实际完成以下协作流程：

- 使用日常 Chrome 登录态读取页面和继续任务。
- Agent 填写普通表单、选择项、上传工作区文件、下载结果。
- 用户接管的登录、验证码、支付最终确认和复杂前端操作。
- 用户归还后重新观察页面，并通过同一任务继续执行。
- 跨 run 和 Hearth 重启恢复标签页和控制状态。
- 多 frame、开放 Shadow DOM、Canvas 和截图式界面的组合操作。
- 输入值在运行记录和恢复链路中的统一脱敏。

以下能力仍需要现场验证或存在产品边界：

- 真实 Chrome Extension 首次配对依赖本机 Chrome、扩展安装和配对页面。
- 仓库内自动测试使用 mock Extension 验证协议和状态，不能证明某台机器的扩展商店和配对页面一定可用。
- 网站风控、验证码策略、DOM 改版和网站条款会影响自动化成功率。
- 自动破解验证码和完全无人值守支付不在能力范围内。
- 直接让 Codex 或 DSH 在 Shell 中运行 Playwright 脚本时，Hearth 浏览器卡和接管状态不会自动生效。
