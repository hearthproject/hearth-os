## 安全是产品能力

Hearth 的安全不是“加一个审批弹窗”，而是贯穿来源、上下文、权限、执行、副作用和恢复的系统能力。模型不是可信执行环境，网页不是可信指令，文档不是可信代码，Connector 返回的数据也不是自动可信。

### 信任边界

```text
不可信外部内容
  → Gateway 归一化
  → Policy / 数据标记
  → 最小上下文
  → Executor
  → Sandbox
  → Effect Dispatcher
  → 外部系统
```

每一层都假设下一层可能被污染。外部内容可以影响任务内容，但不能扩大权限、修改 Policy 或直接触发高风险副作用。

### 威胁模型

| 威胁 | 场景 | 防线 |
|---|---|---|
| 提示词注入 | 网页/邮件要求泄露文件或忽略规则 | 数据指令分离、工具白名单、不可信标记 |
| 凭据窃取 | 模型被诱导读取 token | Broker、最小注入、日志脱敏 |
| 数据外泄 | 恶意文档诱导上传 | egress 白名单、DLP、只读挂载 |
| 重复副作用 | 超时后重试导致重复发信 | 幂等键、outbox、对账 |
| 恶意附件 | 宏、zip bomb、路径穿越 | 沙箱解析、宏禁用、资源限制 |
| 供应链 | 依赖/技能被篡改 | 锁版本、签名、SBOM、审阅 |
| 沙箱逃逸 | 恶意代码跳出容器 | 强隔离、非 root、无宿主 socket |
| 记忆投毒 | 不可信来源写入长期偏好 | quarantine、双来源、用户确认 |
| 设备丢失 | 手机或电脑被他人使用 | 撤销、过期、生物识别、加密 |
| 过度自动化 | Agent 在无监督下扩大范围 | Mandate、预算、kill switch |

### Capability 模型

Capability 不是“某个 Agent 有某个工具”，而是对具体资源、动作、范围和期限的许可：

```ts
type Capability = {
  action: string;
  resource: string;
  scope?: Record<string, string>;
  constraints?: Record<string, unknown>;
  expiresAt: string;
  revokedAt?: string;
  issuedBy: string;
  mandateId: string;
};
```

原则：最小权限、短期有效、任务结束回收、按设备/账户/资源/动作限定、执行器不能自签或扩大、所有使用可审计、撤销立即生效。

### 风险分级

| 等级 | 示例 | 默认处理 |
|---|---|---|
| R0 只读 | 查看文件、读邮件、搜索 | 可自动 |
| R1 低风险写入 | 草稿、临时文件、工作区修改 | 在 Mandate 内自动 |
| R2 外部可见 | 发送邮件、评论、分享 | 首次或每次审批 |
| R3 不可逆 | 删除、付款、权限变更、公开发布 | 强审批 + 回执 + 补偿 |
| R4 禁止 | 绕过安全控制、泄露秘密、未经授权转账 | 系统拒绝 |

### 凭据与秘密

- 长期秘密只存在 Broker/密钥库；
- 模型上下文永远不包含 refresh token、私钥、cookie；
- 短期 token 只在调用外部 API 时注入；
- 日志、异常、截图和 Artifact 做敏感信息扫描；
- 开发、测试和生产使用不同凭据；
- 本地存储和备份加密；
- 支持按连接、设备和账户撤销；
- 用户可查看“谁在什么时候用了什么权限”。

### Sandbox、网络与提示词注入

- 默认最小挂载和最短生命周期；
- 默认拒绝出站，按任务开白名单；
- 外部页面和文档标记为不可信；
- 不可信内容不能直接决定工具调用；
- 高风险动作必须经过 Effect Dispatcher 和审批；
- 下载物、宏和附件进入隔离区；
- 沙箱失败视为安全事件，不做“再试一次”掩盖。

### 隐私与本地优先

- 默认本地存储；
- 只上传任务需要的最小上下文；
- 敏感数据可指定本地模型或人工处理；
- 记忆、日志和 Artifact 有敏感级别；
- 删除和遗忘要传播；
- 备份加密；
- 数据导出和迁移可用；
- 不把用户数据用于未经同意的训练或共享。

### 供应链与扩展

- 依赖锁版本、校验、SBOM；
- 技能/插件签名或来源验证；
- 第三方 Connector 最小权限；
- 插件不能绕过 Policy；
- 高风险扩展需人工审阅；
- 升级前跑安全与契约测试。

### 多设备安全

- 设备配对使用短期码和公钥；
- 手机不持有长期主凭据；
- 审批绑定 nonce、参数和过期时间；
- 设备丢失可远程撤销；
- 离线缓存只读，不产生外部副作用；
- 跨设备只同步必要投影和产物引用；
- 记忆删除不能在另一设备复活。

### 事故响应与 kill switch

- 全局停止开关；
- 按设备、连接器、技能、任务和账户的局部停止；
- 停止后保留审计和恢复入口；
- 密钥轮换；
- 事故后清理受影响凭据和缓存；
- 输出可读的事故报告；
- 不把“重启服务”当成事故处理。

### 备份、恢复与删除

- 加密备份；
- 恢复后验证事件、产物、记忆和权限；
- 删除传播到投影、索引、缓存和设备；
- 保留最小审计所需信息，但不保留不应保留的敏感正文；
- 用户可导出自己的数据；
- 迁移后重新验证，不假设复制成功。

### 安全测试

- 提示词注入与工具越权；
- 秘密泄漏；
- 路径穿越、宏、zip bomb；
- 沙箱逃逸；
- 网络出口绕过；
- 审批重放；
- 设备撤销；
- 重复副作用；
- 供应链篡改；
- 记忆投毒；
- 数据和备份删除。

## 评估体系

Demo 不是能力。Hearth 只相信可重复、可验证、带失败样本的证据。

### 评估金字塔

| 层级 | 评什么 | 频率 |
|---|---|---|
| Unit/Tool | 解析器、连接器、策略、验证器 | 每次提交 |
| Task-level | 单任务端到端成功 | 每次发布 |
| Trajectory Replay | 历史轨迹重放、换路由和失败恢复 | 持续 |
| Shadow | 真实输入、无外部副作用 | 持续 |
| Live Pilot | 真实用户、真实副作用、受控范围 | 阶段推进前 |
| Long-run | 多设备驻留、设备切换、记忆演化 | 阶段验收 |

### 任务集

初始建立 40–60 个真实任务，覆盖八类任务族：邮件、日历、文档、调研、代码、网页、桌面、跨应用流程。

要求：

- 每条任务有明确输入、验收标准和验证器；
- 包含正常、边界、失败和恶意输入；
- 真实脱敏数据优先，合成数据单独标记；
- 保留 holdout 集，不能反复调参；
- 失败样本不能被删除；
- 新增能力时增加对应任务，而不是只增加 demo；
- MVP 的窄任务族也必须有独立任务集，不能只靠一条演示脚本。

### 核心指标

| 指标 | 定义 | 初始目标 |
|---|---|---|
| Verified Task Success | 通过验证器的任务比例 | Stage 1 ≥ 70% |
| Human Minutes / Verified Task | 每有效完成的人工分钟 | 相对基线下降 ≥ 30% |
| Interruptions / Verified Task | 每任务打断次数 | ≤ 1.0 |
| Recovery Rate | 崩溃/断网/重启后恢复比例 | ≥ 95% |
| Duplicate Side Effects | 故障注入下重复副作用 | 0 / 200 |
| Unsafe Action Rate | 未授权高风险动作 | 0 |
| Token / Verified Success | 每有效完成 Token | 持续下降 |
| Cost / Verified Success | 每有效完成综合成本 | 可解释且可控 |
| Memory Precision | 召回记忆确实相关且正确 | ≥ 90% |
| Skill Regression | 晋升技能导致旧任务退化 | 0 严重回归 |

目标值是早期工程门槛，不是营销承诺，必须用真实数据更新。

### 基线比较

至少比较：

1. 全人工；
2. 直接使用 Codex；
3. Hearth 的当前版本；
4. Hearth 的替代路由或技能版本。

比较成功率、人工分钟、打断、Token、延迟、成本和失败恢复，而不是只比较输出文本。

### 验证器

- 代码：测试、类型检查、diff、CI；
- 文档：结构、引用、格式、用户验收；
- 邮件：收件人、事实、语气、发送审批、Receipt；
- 网页：DOM/可访问性状态、截图、最终状态；
- 桌面：可访问性树、截图、目标状态；
- 研究：来源和引用；
- 数据：schema、行数、抽样、对账、复现脚本；
- 副作用：幂等键、Receipt、对账。

### 轨迹重放与故障注入

历史轨迹应能重放、换路由、替换模型/执行器并比较结果。故障注入至少覆盖：进程崩溃、网络中断、超时、重复投递、磁盘满、provider 限流/认证过期、设备离线、外部结果不确定、审批过期、记忆/缓存失效。

### 安全与红队评估

红队必须尝试让系统越权、泄露秘密、重复副作用、绕过审批、污染记忆、扩大技能权限和利用设备。评估结果要进入发布门槛，而不是放在附录。

### 统计与评估纪律

- 预先定义指标和样本；
- 不用平均值掩盖某个任务族崩溃；
- 保留失败和拒绝样本；
- 评估集不能用于技能训练；
- 区分统计显著和产品有意义；
- 记录模型、执行器、提示、工具和版本；
- 变更后重新跑基线，避免“只跟旧版本比”。

### 阶段发布门槛

| 阶段 | 必须证明 |
|---|---|
| Stage 0 | 可点击端到端原型、12 个可验收任务、核心协议和威胁模型 |
| Stage 1 | MVP 可在浏览器每天使用；可恢复、可审批、无重复副作用、Codex 任务可验收 |
| Stage 2 | 邮件/日历/文档/网页真实任务可完成，Token 可控 |
| Stage 3 | GUI 可接管，失败可恢复，无越权 |
| Stage 4 | 主动任务不造成通知疲劳，审批和安全可审计 |
| Stage 5 | 记忆可纠正/遗忘，技能可评估/回滚 |
| Stage 6 | 多设备一致、离线恢复、迁移和撤销可靠 |

### 评估反模式

- 只看 demo 和截图；
- 只测成功路径；
- 只统计模型输出，不验证副作用；
- 用合成任务代替真实任务；
- 把 Token 降低当成唯一目标；
- 评估集被技能训练污染；
- 失败样本被删除；
- 用平均值掩盖某个任务族崩溃；
- 自评通过；
- 没有安全回归测试；
- 用“以后补评估”推进阶段。

## 结论

安全与评估不是 Stage 6 的收尾工作。Stage 0 就要有威胁模型和任务集，Stage 1 就要有 MVP 的真实任务验收、恢复和副作用演练；后续每扩一个执行器，安全与评测面同步扩大。
