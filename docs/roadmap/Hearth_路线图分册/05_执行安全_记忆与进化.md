## Execution Gateway 与 Sandbox

Execution Gateway 是执行器与实际资源之间的安全层，负责：

- Workspace 生命周期、挂载和文件权限；
- Sandbox Provider 选择、快照和回收；
- 网络出口策略；
- Credential Broker；
- Effect Dispatcher；
- 配额、审计、取消和恢复。

它不决定业务意图，也不替代 Policy。

### Workspace 类型

| 类型 | 用途 | 特性 |
|---|---|---|
| Read-only | 研究、审查、读取证据 | 不可写，可缓存 |
| Ephemeral | 一次性执行 | 结束即销毁 |
| Copy-on-write | 修改文件但保留原件 | 快照、diff、可回滚 |
| Persistent Project | 长期项目工作区 | 版本化、配额、定期清理 |
| Remote Workspace | 设备或远程执行 | lease、加密传输、离线恢复 |

默认从最小权限和最短生命周期开始。任务结束后，临时权限、挂载和网络规则必须回收。

### 隔离级别

| 级别 | 典型实现 | 适用场景 |
|---|---|---|
| Process | 受限进程、资源限制 | 可信脚本、轻量工具 |
| Container | Docker/OCI | 一般代码、测试、文档转换 |
| MicroVM | Firecracker 等 | 不受信任代码、外部文件、高风险研究 |
| Virtual Desktop | VM + 桌面 | GUI 应用、不可信桌面软件 |
| Remote Device | 用户设备 agentd | 必须在特定设备执行的任务 |

Container 适合运营隔离，但不是对恶意代码的绝对安全边界。不受信任代码、宏、浏览器下载物和高风险文件应使用更强隔离。

### Sandbox Provider 接口

```ts
interface SandboxProvider {
  create(spec: SandboxSpec): Promise<SandboxHandle>;
  resume(snapshot: SnapshotRef): Promise<SandboxHandle>;
  snapshot(handle: SandboxHandle): Promise<SnapshotRef>;
  exec(handle: SandboxHandle, cmd: CommandSpec): Promise<CommandResult>;
  mount(handle: SandboxHandle, mount: MountSpec): Promise<void>;
  expose(handle: SandboxHandle, port: PortSpec): Promise<Endpoint>;
  destroy(handle: SandboxHandle): Promise<void>;
}
```

Hearth 依赖接口，不把业务逻辑写死在 Docker、Firecracker 或某个云厂商 API 上。

### 网络出口

- 默认拒绝出站；
- 按任务开启域名和端口白名单；
- 通过代理记录请求，阻断元数据地址和本地管理接口；
- 研究任务使用只读网络或浏览器代理；
- 写操作不直接走模型生成的任意 URL；
- 下载内容进入隔离区，扫描、解析后再使用；
- 绕过 egress 的尝试视为安全事件。

### Credential Broker

```text
用户 OAuth / API Key
  → 加密存储
  → 用户授权 scope
  → Run 申请短期能力
  → Broker 校验 Mandate / Approval
  → 发放短期 token 或代执行
  → 记录使用、过期并撤销
```

原则：

- 模型永远看不到 refresh token、私钥、cookie 和完整 secret；
- Connector 调用外部 API 时才注入凭据；
- 凭据按账户、资源、动作、设备和时间限定；
- 所有使用有审计；
- 任务结束立即回收；
- 用户可随时撤销全部连接；
- 日志、错误和模型上下文自动脱敏。

### Effect Dispatcher

外部副作用不能由执行器直接完成，而应通过类型化 Effect：

```text
Effect Intent
  → 参数验证
  → Preview
  → Policy / Mandate 检查
  → Approval
  → outbox
  → 幂等执行
  → Receipt / 对账
```

Effect 应声明目标系统和资源、幂等键、是否可逆、失败补偿、审批级别、回执字段、超时和对账方式。

### 安全威胁矩阵

| 威胁 | 防线 |
|---|---|
| 提示词注入 | 外部内容不可信、能力隔离、审批、工具白名单 |
| 越权访问文件/网络 | Workspace 最小挂载、egress 白名单、Sandbox |
| 秘密泄露 | Broker、短期凭据、日志脱敏、上下文过滤 |
| 重复外部副作用 | 幂等键、outbox、Receipt、对账 |
| 恶意文档/下载 | 隔离区、扫描、解析沙箱、禁止宏执行 |
| 供应链攻击 | 锁定版本、依赖审计、签名/校验、最小权限 |
| 设备丢失 | 撤销、密钥轮换、本地擦除、短期会话 |

## Memory OS

记忆不是聊天记录，也不是越多越好。它是“受约束的判断缓存”，必须可解释、可纠正、可遗忘。

### 五类记忆

| 类型 | 内容 | 生命周期 | 用途 |
|---|---|---|---|
| Working Memory | 当前目标、约束、步骤和临时观察 | 任务结束清理 | Task Pack、当前计划 |
| Episodic Memory | 过去任务、结果、失败、人工纠偏 | 中期，可摘要 | “上次类似任务怎么做” |
| Semantic Memory | 人物、项目、组织、事实、关系 | 长期，需来源和有效期 | 项目背景、联系人、决策 |
| User Model | 偏好、沟通风格、边界、习惯、价值排序 | 长期，高度可编辑 | 减少重复说明 |
| Procedural Memory | 技能、工作流、工具配方、验证器 | 版本化，可回滚 | 重复任务复用、Evolution |

Skill 包含权限、版本、评估和回滚元数据；Memory 只保存“曾经有效的经验”。

### 记忆记录

每条记忆至少包含：

- id、类型、subject、statement；
- scope（用户、项目、人物、设备）；
- sourceRefs 和 sourceTrust；
- confidence、sensitivity；
- createdAt、lastUsedAt、expiresAt；
- supersedes、conflictsWith；
- status：quarantined / active / superseded / forgotten；
- forgetPolicy。

关键不是字段多，而是每条记忆都能回答：从哪里来、有多可信、谁能看、何时过期、与哪条冲突、用户如何纠正或删除。

### 写入与检索

记忆写入不是“模型说值得记就记”。应先进入候选区，检查来源、敏感度、重复、冲突和用户授权；高敏感内容默认不自动写入。

检索按任务需要、scope、来源可信度、时效、敏感度和 Token 预算筛选；不能把全部记忆塞入上下文，也不能让不同项目/账户互相污染。

### 记忆预算

- 总记忆量预算；
- 单条长度预算；
- 注入上下文预算；
- 召回频率和衰减；
- 过期和归档。

记忆预算与 Token Governor 联动，避免“记忆越多越智能”的假象。

### 冲突、更新与置信度

- 新事实不能静默覆盖旧事实；
- 保留来源和时间；
- 冲突时标记或请求用户确认；
- 低置信度记忆不能单独触发高风险动作；
- 用户明确纠正优先；
- 过期事实可降权或遗忘。

### 遗忘

遗忘必须传播到索引、缓存、设备副本和派生摘要。用户应能确认：

- 忘了什么；
- 为什么忘；
- 哪些设备和索引已更新；
- 是否仍存在于备份；
- 如何验证。

### 记忆投毒与提示词注入

网页、邮件、文档和外部工具输出都是不可信来源。它们可以成为候选记忆，但不能直接获得高可信度，更不能通过记忆扩大权限。高敏感或外部不可信内容应隔离、降权或拒绝写入。

### 多设备同步与 UI

- 同步记忆必须携带版本、来源和 tombstone；
- 删除不能在另一台设备“复活”；
- 敏感记忆按设备范围过滤；
- 记忆浏览器显示“记住了什么、为什么召回、来自哪里”；
- 用户可纠正、删除、导出；
- “为什么召回”不能只给模型解释，要有来源和规则证据。

### 记忆指标

- 召回准确率；
- 错误记忆导致的返工；
- 用户纠正率；
- 遗忘合规率；
- 注入 Token 和延迟；
- 敏感信息泄漏尝试被阻断率。

## Evolution OS

自进化不是让 Agent 改自己，而是从轨迹中形成候选能力，经过验证后有限晋升。

### 输入信号

- 成功轨迹；
- 失败和重试；
- 人工纠偏、拒绝和接管；
- 工具/模型变化；
- 用户偏好变化；
- 评估结果和成本。

### 技能模型

技能可以是提示模板、确定性工作流、文档管道、Connector 配方、代码适配器和验证/补偿步骤，但必须有 manifest：

```ts
type SkillManifest = {
  id: string;
  version: string;
  trigger: string;
  preconditions: string[];
  inputs: SchemaRef[];
  steps: SkillStep[];
  tools: string[];
  capabilities: string[];
  budgets: BudgetSpec;
  validators: ValidatorRef[];
  fallback: FallbackSpec;
  provenance: string[];
  evalSuite: string;
  status: "draft" | "shadow" | "canary" | "active" | "retired";
};
```

技能不能自带新权限，只能申请父任务和用户 Mandate 的交集。

### 从轨迹到技能

```text
轨迹采集
  → 重复/失败聚类
  → 候选技能描述
  → 生成实现
  → 静态检查与权限审计
  → 离线回放评估
  → Shadow（无外部副作用）
  → Canary（小范围真实使用）
  → Promote / Reject / Rollback
  → 持续监控
```

### 晋升门槛

- 真实任务集的 Verified Success 不低于旧流程；
- 安全测试零越权；
- 没有扩大 capability；
- Token、时间或人工分钟有明确改善；
- 失败可恢复、可解释、可回滚；
- 评估集没有严重污染；
- 用户审阅技能说明和权限；
- 上线后监控无异常副作用。

“模型觉得更好”或一次演示不能作为晋升证据。

### 权限与自修改边界

- Agent 可提出技能、参数、提示、验证器和流程候选；
- Agent 不能修改自己的 Mandate、Policy、Approval 规则和 Permission；
- Agent 不能直接改写核心 Runtime、事件格式和安全边界；
- 核心代码变更必须走人工审阅 PR；
- 技能上线必须绑定版本、评估集和回滚目标；
- 技能不能创建新凭据或后台任务；
- 任何权限变化需要用户明确授权。

### 反模式

- 无评估直接启用；
- 用一次成功代表长期能力；
- 技能不断扩权；
- 评估集被训练/挑选污染；
- 失败样本被删；
- 只降 Token 不降人工分钟；
- 没有回滚；
- 让 Agent 自己修改安全检查。

## 与 Stage 的关系

- **Stage 1**：只做执行隔离、基础凭据边界、outbox/Receipt 和演练审批；不做完整 Memory/Evolution。
- **Stage 2**：Memory v0（来源、基本遗忘）和 Context Compiler。
- **Stage 5**：完整 Memory OS 五类记忆、遗忘传播、技能候选和 Evolution 晋升门。
- **Stage 6**：多设备记忆同步、tombstone、设备撤销和迁移验证。

安全、记忆和进化不能等到最后补；它们从 Stage 1 就以最小形式存在，并在后续阶段逐步完整。
