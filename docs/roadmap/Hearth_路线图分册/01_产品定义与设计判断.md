# 01 产品定义与设计判断

> 对应主文档：第 0–3 章  
> 建议前置：无  
> 下一篇：[总体架构与领域协议](02_总体架构与领域协议.md)  
> 读完后应能回答：Hearth 为谁做、解决什么问题、为什么不是 Codex 套壳，以及哪些底线不能妥协。

## 一句话定位

> **Hearth 是一个拥有个人上下文、持久执行、真实工具和多设备入口的通用个人 Agent OS；它把人从重复的数字劳动中解放出来，而不是制造另一个需要看管的聊天窗口。**

它是单用户、自托管、长期驻留、低打扰、低 Token 的个人 Agent OS。产品名是 Hearth，仓库建议为 `hearth-os`，命令行为 `hearth`，常驻服务为 `hearthd`，包命名空间为 `@hearth/*`。

## 它是什么，不是什么

Hearth 不是：

- 另一个 Coding Agent；
- 一个只会转发提示词的 Codex 套壳；
- 一个把所有权限交给模型的黑盒自动化；
- 一个只在聊天框里回答问题的助手；
- 一个企业多租户 Agent 平台；
- 一个需要用户每天维护提示词、插件和工作流的工具。

Hearth 是：

- **Control Plane**：决定做什么、是否允许、何时打扰、如何恢复；
- **Durable Harness**：把意图变成可恢复、可审计、可回执的执行；
- **并列 Executor 集合**：Native、Codex、Connector、Browser、GUI、Document/Data、Human；
- **Memory OS**：让人物、项目、偏好、承诺和经验可被安全召回；
- **Evolution OS**：让重复成功沉淀成技能，但变化必须经过评估和回滚；
- **Experience Plane**：用任务卡、审批和产物承载交互，而不是无穷聊天记录。

## 五个不可妥协的判断

1. **价值在控制面、记忆和验证，不在“再实现一个模型”。**
2. **Codex 是强大的并列 Executor，不是产品本体，也不是唯一执行大脑。**
3. **Token 消耗是架构指标；能不用模型的地方，坚决不用模型。**
4. **前端必须简单到用户不需要学习 Agent 架构；复杂逻辑留在后端。**
5. **自进化只能产生候选技能和候选策略，不能绕过权限、评估和人类审查。**

本版追加一条交付判断：

6. **先做可每天使用的最小产品，再逐步长成完整 OS；前端从第一个增量开始存在。**

## 首选用户

| 项目 | 假设 |
|---|---|
| 用户 | 1 个主要用户，可能有 1–3 个可信协作者 |
| 设备 | 一台主力电脑、一台常驻机器、一部手机 |
| 工作 | 研究、写作、文档、邮件、日程、代码、Issue、PR、数据和网页操作混合 |
| 技术能力 | 能运行本地服务，但不希望每天维护 Agent 配置 |
| 隐私要求 | 个人文件和凭据不能默认上传到不可信第三方 |
| 使用方式 | 主动任务、定时任务、通知触发和手动发起并存 |

第一版不追求“所有人都能用”，而追求“一个真实用户愿意每天用”。

## 八类任务覆盖

| 任务族 | 典型工作 | 首选执行方式 |
|---|---|---|
| 沟通与协作 | 邮件、IM、会议纪要、跟进、日程协调 | Connector + Native/Codex + 审批 |
| 文档与内容 | docx、xlsx、pptx、PDF、Markdown、报告、翻译、改写 | Document/Data Engine、Native、Codex |
| 研究与信息整理 | 搜索、阅读、对比、引用、摘要、资料库 | Native + Browser + Codex |
| 代码与研发 | 仓库修改、测试、Issue、PR、代码审查 | Codex + 测试/CI 工具 |
| 数据与表格 | 清洗、对账、统计、图表、导入导出 | Document/Data Engine + Python sidecar |
| 网页与 SaaS | 登录、表单、下载、上传、后台操作 | Browser Executor |
| 桌面应用 | 没有 API 的软件、系统设置、跨应用流程 | GUI Executor |
| 个人事务 | 表单、预约、账单、提醒、设备操作 | Connector、Browser、GUI，高风险审批 |

一个任务可由多个执行器协作；“调研竞品并写进周报”可能同时使用 Browser、Native、Document Engine 和 Codex。

## 自主级别

| 级别 | 行为 | 默认使用 |
|---|---|---|
| A0 建议 | 只生成建议、草稿或计划 | 新场景、高风险、未验证能力 |
| A1 受控执行 | 自动完成低风险步骤，中风险首次审批 | Stage 1–2 默认 |
| A2 授权执行 | 在 Mandate 内自动完成已授权动作，高风险仍需审批 | Stage 4 以后 |
| A3 受监督自主 | 长周期运行，但保留审批、预算、kill switch 和回执 | 长期目标 |

自主性必须按任务族、来源、时间段、设备、风险和金额独立配置，不能用一个“全自动开关”覆盖所有场景。

## “完成”的定义

自然语言“已完成”不是完成证据。不同任务需要不同验证器：

| 任务 | 完成证据 |
|---|---|
| 代码/Issue/PR | 测试、类型检查、diff、CI 或人工审查 |
| 文档 | 结构检查、引用检查、格式检查、用户验收 |
| 邮件草稿 | 收件人、事实、语气检查；发送前审批 |
| 邮件发送 | Approval、Broker 执行记录、provider message id 或明确的不确定状态 |
| 网页操作 | DOM/可访问性状态、截图、最终状态和回执 |
| 桌面操作 | 可访问性树、截图、目标状态和人工确认 |
| 研究 | 来源可追溯，关键断言有引用 |
| 日程 | 时间、时区、参与者、冲突检查和日历回执 |
| 数据 | schema、行数、抽样、对账和可复现脚本 |

## 明确不承诺

- 物理世界机器人操作；
- 代替用户承担法律、医疗、金融等专业责任；
- 未审批的付款、签约、删除、公开发布或权限变更；
- 对任意软件 100% 无人值守；
- 企业 IAM、多租户、组织审计和计费；
- 第一天覆盖全部八类任务；
- 与底层模型厂商比模型能力；
- 通过无限自主循环制造“像人”的假象。

## 体验承诺

- 用户一眼知道 Agent 正在做什么；
- 需要人时只出现一个明确动作；
- 不需要理解 Worker、Harness、Token 等内部术语；
- 手机可以完成查看、审批、接管和发起；
- 任何失败都能看到原因和恢复选项；
- 通知是可预期的；
- 从第一个可运行增量开始，用户就能通过真实界面完成任务，而不是只能在 CLI、日志或测试里看到能力。

## 核心设计判断

### Codex 是并列执行器，不是产品中心

Codex 擅长长链路 workspace 工作、代码、测试、Issue/PR、调研、文档、表格和多步骤 Shell；不适合作为长期记忆、权限中心、凭据中心、常驻事件监听器或实时桌面操作器。

路由原则是：

> **哪个执行器能以最低 Token、最高可靠性、最小权限完成并通过验证，就选哪个。**

### 自研与集成的边界

Hearth 自研：

- 控制面、Durable Harness、Event Log 协议；
- Policy、Mandate、Capability、Approval；
- Context Compiler、Token Governor；
- Memory OS、Evolution OS；
- Execution Gateway 控制逻辑、Credential Broker；
- 任务卡、审批、产物和手机入口；
- 验证器与评估体系；
- Native Runtime 的薄执行层。

Hearth 集成：

- 模型 API 或本地模型；
- Codex；
- Playwright；
- 文档解析/转换库；
- 官方邮件、日历、云盘 API/MCP；
- 容器/微虚拟机/Sandbox 内核；
- OpenTelemetry。

Hearth 不重写模型推理引擎、容器/虚拟化内核、完整第三方 Agent 框架或文档解析器。

### 前端不是后置包装层

用户打开 Hearth 只需知道三件事：它在做什么、是否需要我、下一步点哪里。

- 首页不是无限聊天流，而是任务卡；
- 每个状态只有一个主动作；
- 审批不藏在多层设置里；
- 手机可以完成高风险动作确认；
- 技术术语不进入主界面；
- 任何异常都有可执行恢复路径；
- 只存在于 CLI、日志、数据库或测试中的能力，不计入阶段完成。

### 一个逻辑 Agent，多设备执行

```text
一个逻辑 Hearth
  ├─ 一个主 Gateway / Control Plane
  ├─ 一个 Event Log / 单写者
  ├─ 多台设备上的 agentd
  ├─ 手机作为查看、审批、接管、发起入口
  └─ 每个设备注册自己的能力
```

设备只提供执行能力和入口，不复制身份、事实源和授权。

### 学习 OpenClaw 与 Hermes，但不复制它们

OpenClaw 值得学习 Gateway、渠道、设备节点、常驻、自主分级和注意力入口；Hermes 值得学习记忆预算、记忆约束、技能沉淀、子任务生命周期和进化闭环。

不 fork、不作为运行时依赖、不让参考项目变成产品底座。Hearth 只吸收模式，并通过自己的 Event Log、Policy、Memory 和 Evolution 协议实现。

## 七条架构不变量

1. Event Log 是唯一事实源。
2. 每个 State Root 只有一个写权威。
3. 所有外部副作用必须有幂等键、审批或明确豁免、以及 Receipt。
4. 执行器不能直接读取长期原始凭据。
5. 每个任务必须有预算、截止时间和取消路径。
6. 记忆必须有 provenance、敏感度、冲突和遗忘策略。
7. 任何自进化都必须经过评估、canary 和回滚。

再加一条交付不变量：

8. **每个增量都必须是可用纵向切片：用户结果、界面、持久状态、真实执行、验证、恢复和度量同时出现。**

## 参考系统的位置

| 参考 | 学习什么 | 不做什么 |
|---|---|---|
| OpenClaw | Gateway、渠道、设备、注意力、常驻 | 不 fork、不复制渠道规模 |
| Hermes | 记忆预算、技能、生命周期、进化 | 不做无界自修改 |
| DeerFlow | Harness/App 分层、Run 生命周期 | 不引入重型框架耦合 |
| Pi / Maka | session tree、steering、compaction | 不复制完整框架 |
| OpenSandbox / OpenBot | 隔离、快照、takeover、receipt | 不复制完整产品 |
| OpenMuse / OpenDots | durable job、checkpoint、lease | 不照搬任务模型 |
| Codex | 工作区执行、代码、研究、文档 | 不当权限中心或记忆中心 |

## 本章结论

Hearth 的护城河不是“拥有一个更强的模型”，而是知道什么时候不该调用模型、该给执行器什么最小上下文、哪些动作需要谁的授权、如何证明任务真的完成、失败后如何恢复、什么该记住、什么该遗忘。

但这一切必须先以一个真实可用的最小产品出现，而不是等架构全部完成后才让用户看到。
