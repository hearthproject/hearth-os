## Personal Gateway 与多入口

Personal Gateway 是 Hearth 与外部世界之间的唯一入口。它负责：

- 识别用户、设备和渠道；
- 接收文字、语音、文件、图片、网页、邮件、日历和定时事件；
- 统一转换为 `Event`；
- 去重、排序、限流和来源标记；
- 判断哪些事件进入注意力收件箱；
- 维护设备注册、在线状态和配对关系；
- 为手机提供安全 API 和推送，而不是暴露本地端口。

Gateway 不做长任务推理，也不直接执行业务动作。

### 输入渠道

| 渠道 | 典型输入 | 处理方式 |
|---|---|---|
| CLI | 命令、脚本、开发调试 | 直达 Gateway，可结构化输出 |
| Web/PWA | 文本、文件、拖拽、分享 | 任务卡和审批中心 |
| 手机 | 文本、语音、分享、拍照、通知 | 审批、查看、接管、发起 |
| IM | 消息、文件、转发 | Channel Adapter 归一化 |
| Email | 邮件与附件 | 只读同步、草稿、待审批发送 |
| Calendar | 日程与邀请 | 只读、冲突检查、待审批写入 |
| Device | 文件、屏幕、摄像头、传感器 | 设备能力与授权 |
| Cron/Watch | 定时器、文件变化、网页变化 | Trigger 评估 |
| API/MCP | 外部服务事件 | Connector 归一化 |

Stage 0 只设计渠道模型和 UI 状态；Stage 1 只接 Web 与 CLI；Stage 2 再接第一个真实 Connector。不能一开始就铺所有渠道。

### 事件归一化与去重

所有渠道事件至少包含：

- 来源类型与来源 id；
- 可信级别；
- 用户/设备身份；
- 原始时间；
- 内容引用或脱敏摘要；
- 会话/线程关联；
- 幂等键；
- 是否允许触发主动任务。

默认策略：

- 同一来源同一事件只处理一次；
- 重复通知合并；
- 低价值事件只记录，不推理；
- 不可信来源不能创建高风险 Mandate；
- 外部内容不能覆盖系统 Policy。

### 注意力收件箱

Attention Inbox 不是消息列表，而是“需要人处理的最小集合”：

- 需要审批的动作；
- 需要补充信息的任务；
- 失败且无法自动恢复的任务；
- 需要接管的浏览器或桌面；
- 已完成的产物；
- 可延后查看的摘要。

默认不进入收件箱：低置信度但无副作用的观察、被规则过滤的重复事件、纯状态变化、不需要人决策的失败重试。

排序依据：

```text
priority = risk × blockedness × deadline × userImpact × reversibilityPenalty
```

用户关闭某渠道后，任何其他渠道都不能绕过。

### 设备注册与能力目录

设备注册时上报：

- 设备 id 与公钥；
- 操作系统和版本；
- 在线状态与心跳；
- 可用能力：文件、终端、浏览器、屏幕、摄像头、麦克风、通知、剪贴板；
- 可访问的本地数据范围；
- 安全边界和 Sandbox 支持；
- 用户授予的 capability；
- 设备 lease 与过期时间。

设备能力不是永久授权。任务结束后，临时能力应自动回收。

### 手机接入

手机是 Hearth 的远程入口，不是默认执行权威。Stage 4 的第一版只支持：

1. 查看任务、状态和产物；
2. 审批高风险动作；
3. 接管异常任务；
4. 发起新任务；
5. 接收高信号通知。

安全要求：

- 通过安全隧道或推送服务接入；
- 不直接暴露 Agent 端口；
- 设备配对使用短期码和公钥；
- 审批绑定 nonce、动作参数和过期时间；
- 通知只包含脱敏摘要；
- 设备丢失可撤销全部 token 和 lease。

## Control Plane 与自主性

Control Plane 决定：

- 事件是否值得处理；
- 是否创建 Task；
- 是否需要用户审批；
- 应用哪个 Executor；
- 花多少 Token、时间和金钱；
- 何时通知、何时静默；
- 失败后重试、换路还是转人工。

它不直接调用工具，不直接持有凭据，也不直接写外部服务。

### Trigger

Trigger 是规则、订阅和条件的组合：cron、文件变化、网页变化、邮件到达、日历临近、GitHub Issue/PR、设备上线/离线、任务依赖完成、用户显式订阅和失败重试。

规则命中的可以直接创建 Ticket；只有需要语义判断时才调用小模型。Trigger 不是“让大模型一直观察一切”。

### Policy 与 Mandate

Policy 是长期规则，Mandate 是一次或一段时间的授权实例。

Mandate 至少包含：

- 允许的动作类型；
- 资源范围；
- 联系人/域名/仓库/文件夹范围；
- 风险等级；
- 预算；
- 有效期；
- 是否允许自动执行；
- 是否允许转发或委托；
- 撤销方式。

模型可以提出建议，但不能修改 Mandate、Approval 或自身 capability。

### 调度与 Watchdog

调度器负责优先级、并发上限、设备/Executor 匹配、预算、截止时间、依赖等待和公平性。

Watchdog 独立于 Agent 运行，负责：

- 卡死检测；
- 死循环检测；
- 预算超支；
- 设备失联；
- 凭据失效；
- 外部平台异常；
- 自动降级或转人工。

Watchdog 不是另一个模型，而是一组确定性监督机制。

### 自主性的正确边界

自主性不是“模型想做什么就做什么”，而是：

- 在明确 Mandate 内自主；
- 在预算内自主；
- 在可恢复/可回滚范围内自主；
- 在低风险场景中自主；
- 高风险动作始终保留人类确认。

### 注意力预算

每个任务都有注意力预算，而不只是 Token 预算：

- 最多打断次数；
- 聚合窗口；
- 静默时段；
- 默认动作；
- 升级条件；
- 用户关闭渠道后的行为。

规则：

- 能自动验证的不要求人确认；
- 能安全等待的不即时打扰；
- 能批量审批的不逐条打断；
- 每次打断必须有一个明确动作；
- 同一任务打断超过 2 次且无法下降，退回“只建议不执行”。

### 主动循环

```text
Source Event
  → Trigger / Rule
  → Small classifier
  → Task / Thread
  → Policy + Mandate
  → Budget
  → Executor
  → Verification
  → Notification / Receipt
```

主动模式与建议模式必须可独立开关，并且有对照数据。Stage 4 之前不开放真实主动循环。

## Durable Harness

Harness 是“把一次意图变成可恢复执行”的中间层：

- 承接 Control Plane 的决策；
- 构建任务图；
- 选择执行器；
- 执行预算和 lease；
- 处理取消、重试、恢复；
- 把结果转成 Artifact、Receipt 和 Eval。

它不是模型，也不是 Sandbox。

### Run 生命周期

```text
created
  → authorized
  → queued
  → assigned
  → running
  → verifying
  → completed

异常分支：
  → paused
  → waiting_approval
  → waiting_input
  → retry_wait
  → failed
  → cancelled
  → needs_human
```

每个状态迁移必须：

- 产生事件；
- 有明确触发者；
- 有幂等条件；
- 可以从事件重放；
- 不允许原地覆盖历史。

### 任务图

支持顺序依赖、并行分支、汇合、失败传播、补偿任务、人工审批节点、跨天等待、长任务检查点和子任务预算继承。

第一阶段不引入重型工作流引擎，使用显式状态机、SQLite、outbox、定时器和 lease，加上清晰的中间产物。

### Lease 与单写者

- 每个 Ticket 同一时刻最多一个有效 Assignment；
- Executor 或设备必须持有 lease 才能推进；
- lease 过期后可重新分配；
- 重新分配必须带 fencing token，拒绝旧执行者继续写入；
- 同一 State Root 只有一个写权威；
- 设备本地状态只是缓存；
- 设备离线时任务排队，重新上线按 cursor、lease 和检查点继续；
- 设备丢失必须撤销 lease、capability 和密钥。

### 恢复策略

| 故障 | 恢复方式 |
|---|---|
| 进程崩溃 | 从 Event Log 和检查点恢复 |
| 网络中断 | 保留 outbox；恢复后按幂等键重投 |
| Executor 超时 | 保存 workspace 快照；重试或换 Executor |
| 设备离线 | 进入设备队列；不丢任务 |
| 外部结果不确定 | 标记 uncertain；先对账，不盲目重试 |
| 记忆冲突 | 保留来源；不静默覆盖 |

恢复后必须重新验证，不信任旧的自然语言“完成”。

### 路由

```text
Ticket
  → 能力匹配
  → 风险与权限检查
  → Token / 成本 / 延迟估计
  → 选择 Executor 或 Human
  → 执行
  → 验证失败？
      ├─ 同 Executor 重试
      ├─ 换更合适的 Executor
      ├─ 降级为更小范围
      └─ 人工接管
```

路由不应只由模型决定。规则、历史成功率、成本、权限和设备状态都参与。

### 边界规则

1. Control Plane 不直接执行工具。
2. Harness 不直接读取原始凭据。
3. Executor 不决定“是否允许”。
4. Execution Gateway 不决定业务意图。
5. UI 不能绕过 Policy 写数据库或触发工具。
6. 所有外部副作用经过 outbox、幂等键和 Receipt。
7. 所有 schema 变更带 migration 和兼容测试。

## 与 MVP 的关系

MVP 不需要完整实现 Gateway、Trigger、设备目录和所有恢复策略，但必须具备最小真实链路：

- Web 输入进入 Gateway → Event；
- Control Plane 创建 Task/Ticket；
- Harness 持久化 Run 和状态；
- Codex 执行并产生事件；
- 验证器决定完成；
- Web 从投影展示任务卡和恢复入口。

没有这条链路，就不是 MVP，只是前端演示或后端库。
