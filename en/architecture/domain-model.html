DOMAIN MODEL

Domain Model and Protocol ​

Core entities, relationships, events, executor protocol, approvals, and receipts. This section defines the system's source-of-truth contract, not the details of any single implementation.

Core Entities ​

EntityDefinitionKey Invariants
SourceUsers, email, calendars, IM, GitHub, web pages, files, cron, devicesHas identity, trust level, and rate limits
EventImmutable facts: messages, observations, tool calls, results, approvals, errorsAppend-only, replayable, with schema version
ThreadContext container around an ongoing topicCan be associated with multiple Tickets but does not hold execution authority
IntentA goal expressed by the user or inferred by the systemNot executed directly; must be converted into a Task/Ticket
TaskA user-visible work item with acceptance criteriaHas a deadline, status, and completion evidence
TicketThe smallest authorized unit of workSingle owner, budget, scope, and expiration time
MandateA versioned instance of an authorization policyScope, strength, validity period, revocable
PolicyA set of personal rulesVersioned; changes can trigger revalidation
AssignmentBinding between a Ticket and an ExecutorAt most one active executor at any given time
RunA single actual execution attemptInputs, budget, checkpoints, terminal state
ExecutorExecution capabilityCapability declaration, isolation boundary, cancellable
CapabilityPermission for resources, actions, scope, and durationLeast privilege, expirable, revocable
ApprovalA human authorization decisionBound to the actual action, parameters, scope, and expiration time
ArtifactDocuments, code, reports, screenshots, data, schedulesContent-addressed, provenance-traceable
ReceiptReceipt for external side effectsIdempotency key, time, result, revocation information
MemoryLong-term facts, preferences, experiences, or Skill indexprovenance, confidence, sensitivity, forgetting policy
SkillReusable procedural capabilityVersioned, permission declaration, evaluatable, rollbackable
DeviceTrusted device nodeIdentity, capability allowlist, pairing status
BudgetTime, Token, cost, disk, and command budgetsHard limit; exhaustion must pause or hand off to a human
EvalEvaluation of a task, Run, Skill, or routingResults cannot be cherry-picked by the operator

Minimal Event Structure ​

ts
type Event = {
  id: string;
  type: string;
  schemaVersion: number;
  occurredAt: string;
  actor: "user" | "agent" | "executor" | "system" | "device" | "external";
  subject:
    | { kind: "thread"; id: string }
    | { kind: "task"; id: string }
    | { kind: "ticket"; id: string }
    | { kind: "run"; id: string }
    | { kind: "device"; id: string };
  causationId?: string;
  correlationId: string;
  payload: unknown;
  hashPrev?: string;
};

Event Log records only facts, not "what the model thinks should be." Projections can be rebuilt, model context can be recomputed, but history cannot be overwritten.

Executor Protocol ​

ts
type ExecutorCapability =
  | "files"
  | "shell"
  | "code"
  | "research"
  | "documents"
  | "email"
  | "calendar"
  | "browser"
  | "gui"
  | "http"
  | "devices"
  | "human";

interface Executor {
  id: string;
  capabilities: ExecutorCapability[];
  execute(ticket: Ticket, context: ExecutorContext): AsyncIterable<ExecutorEvent>;
  cancel(runId: string): Promise<void>;
  resume?(checkpoint: Checkpoint): Promise<void>;
  health?(): Promise<ExecutorHealth>;
}

The unified output includes: a standardized event stream, Artifact references, a structured final result, a verification result, external action Receipts, failure classification, and recoverability.

The Executor is not responsible for interpreting long-term preferences, deciding whether to send/delete/merge/pay, expanding its own capability, directly reading long-term raw credentials, or creating new Tasks without a budget.

Approval and Receipts ​

All external side effects follow this sequence:

  1. Generate an effect intent;
  2. Write to the outbox;
  3. Commit the transaction;
  4. Dispatcher reads pending execution items;
  5. Check Approval / Mandate / capability;
  6. Call the external service with an idempotency key;
  7. Record a Receipt;
  8. Mark as complete or move to the dead-letter queue.

Rules:

  • Persist first, then execute;
  • The same idempotency key must not produce a second external side effect;
  • Retries reuse the same idempotency key;
  • External actions that cannot be idempotent must be approved and escalated to manual handling;
  • After crash recovery, items can be safely redelivered;
  • When an external service returns an uncertain result, reconcile first; do not retry blindly;
  • Dead-letter items must be inspectable, repairable, and manually replayable.
