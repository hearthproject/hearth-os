D3.2 · GUI observation and human takeover ​

Let users see and take control before the system acts; observation and takeover are prerequisites for any GUI automation.

STAGE 3 · D3.2 · 1 vertical increment · 4 work packages

User-visible outcomeUsers can see the target window in Hearth, pause automation, operate manually, then hand back or terminate.
Completion gateTakeover works without input contention; hand-back leaves explicit task state; window bounds are correct; users know their required action; no high-risk action auto-runs.

What this increment solves ​

Users can see the target window in Hearth, pause automation, operate manually, then hand back or terminate.

Stage 3 follows observation, takeover, low-risk action, and high-risk action; desktop automation that cannot be observed or taken over is not product-ready.

Before you start ​

  • Stage 1–2 recovery, approval, idempotency, receipts, and browser isolation are stable.
  • A dedicated desktop device can pair and has explicit allowed windows, applications, and file scopes.
  • GUI tasks run in an isolated desktop and users can pause and take over at any time.
  • D3.1 deliverables have passed review; do not enter this increment otherwise.

Four implementation work packages ​

Every work package must produce runnable code, a reproducible check, or a concrete UI result; interfaces alone or pages alone do not count as complete.

01 · Minimal observation capture ​

Capture target-window bounds, visible screenshot, accessibility tree, and necessary focus information without recording the full private desktop. Crop by task scope and automatically redact password fields, notifications, and sensitive titles. Observation frames carry time, window ID, and bounds so stale pixels never pose as current state.

02 · Observe-only mode and input lock ​

Provide observe-only mode with an explicit guarantee of zero keyboard or mouse input. While observing, the control channel permits only frame reads and cancellation; policy rejects and logs any input request so looking around cannot become unauthorized operation.

03 · Live takeover and contention handling ​

When the user takes over, pause automatic input immediately, withdraw pending actions, and give focus to the user. The takeover view shows window, objective, current step, and completed actions. While the user operates, the system only observes and records, never clicks in the background or steals focus.

04 · Hand-back, redaction, and timeout ​

Before hand-back, record focus, window, URL, completed steps, and next step; afterward recapture state and recheck preconditions. Hand-back timeout, disconnection, or window closure enters Needs attention with screenshots and audit. Acceptance covers contention, disconnects, sensitive-region redaction, and termination.

Engineering map ​

Primary directories and modules ​

  • apps/agentd — pairing, capability declaration, health checks, and revocation
  • packages/devices — device identity, sessions, capability catalog, and online state
  • packages/desktop-observation — window bounds, screenshots, accessibility tree, and redaction
  • packages/desktop-control — allowlists, locators, input actions, and pre/postconditions
  • packages/desktop-verification — screenshot comparison, focus checks, and half-complete detection
  • packages/approval — desktop Effect Preview, second confirmation, and compensation guidance
  • apps/web — device page, observation view, live takeover, and recovery

Shared verification commands ​

bash
pnpm test:device: pairing, capability escalation, offline, revocation, and session expiry
pnpm test:desktop: observation, takeover, focus changes, half-complete, and compensation
pnpm test:desktop-fault: window drift, vanished elements, input contention, and crashes
pnpm eval:computer: at least eight real desktop tasks and failure samples

Acceptance rehearsal ​

  1. Start hearthd from a clean data directory, open the D3.2 page, and confirm it relies on no browser cache or hand-seeded data.
  2. Complete the four work packages in order: Minimal observation capture; Observe-only mode and input lock; Live takeover and contention handling; Hand-back, redaction, and timeout. Preserve the matching test output, screenshot, or artifact version after each package.
  3. Reproduce the failure case "Window or element mismatch". The page must show "The task pauses with the current screenshot and the element that needs confirmation.", then recover with "Relocate, request takeover, or adjust the allowlist; never click coordinates blindly."; no duplicate effect or unregistered state is allowed.
  4. Restart the service and reopen the task. Runtime state, approvals, artifacts, and recovery entry points must all come from durable projections rather than the current page.
  5. Run the shared verification commands above and export the evidence. The completion gate is: Takeover works without input contention; hand-back leaves explicit task state; window bounds are correct; users know their required action; no high-risk action auto-runs.

Deliverables ​

  • Observation view and window bounds
  • Live takeover/hand-back demo
  • Screenshot redaction
  • Takeover audit events

Completion decision ​

  • [ ] Takeover works without input contention; hand-back leaves explicit task state; window bounds are correct; users know their required action; no high-risk action auto-runs.
  • [ ] Deliverables match the contracts and task-card projection with no unregistered field or state.
  • [ ] At least one failure path has an actionable recovery, and key actions leave audit events.
  • [ ] The demo needs no manual database edit, terminal-only stitching, or permanent mock.

Out of scope ​

  • Do not automate when observation, verification, or takeover is unavailable.
  • Do not read password vaults, change system security settings, or operate unauthorized windows.
  • Do not treat one successful coordinate click as general GUI capability.
