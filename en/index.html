WHY HEARTH

The hard part of an agent is not answering. It is taking responsibility.

Hearth puts task state, authorization, execution, evidence, and recovery on one auditable path. It is not trying to build a more conversational model; it is making personal digital work durable, governable, and verifiable.

  • Task cards first, not an endless chat log
  • External effects require approval, idempotency, and receipts
  • Every stage must ship a usable vertical slice
DESIGN CONTRACT

Six non-negotiable design choices

These choices keep Hearth from becoming a Codex wrapper, a pile of automation scripts, or an unrecoverable black box.

01Tasks, not chatUsers see task cards, approvals, and artifacts. They never need to understand workers, harnesses, or token internals.↗02Durable execution kernelAn event log, leases, checkpoints, and recovery policies keep long-running work alive across crashes, sleep, and network loss.↗03Interchangeable executorsCodex, Native, Connector, Browser, GUI, and Human are routed by capability, risk, and token cost.↗04Receipts for side effectsEvery external action passes through an outbox, idempotency key, and receipt. Failures can be reconciled, reversed, and replayed.↗05Governed memory and evolutionMemory has provenance, sensitivity, and forgetting rules. Skills must pass evaluation, canary, and rollback.↗06Local-first, growing by stagesFrom a local MVP to a multi-device Agent OS, every stage has UI, state, verification, and recovery.↗
PUBLIC CONTRACT

One auditable execution chain

Every fact enters the Event Log. Every external effect passes through an outbox, idempotency key, and receipt. Every UI state is a projection, never the source of truth.
