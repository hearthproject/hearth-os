阶段二至六交付状态 ​

核对日期：2026-11-08。本文只记录当前代码和真实运行能证明的事实，不以页面存在代替闭环。

阶段结论 ​

  • 阶段二：部分完成。 本地文件、知识库、公开网页、文档表格提取、任务来源引用，以及“草稿 → 审批 → 本地发件箱写入 → 回执”的闭环已可用；IMAP 只读同步和 SMTP 发送已形成代码闭环，但需要用户配置真实账户并完成人工验收。日历账户和真实邮件服务商的退信/垃圾邮件语义仍未验收，因此不能宣称阶段二整体验收完成。
  • 阶段三：部分完成。 同机 Windows 设备已能配对、逐项审批能力、开始观察、暂停、继续、接管、交还、终止，并在明确目标应用后执行低风险点击、输入、按键和 UIAutomation 动作。敏感区域遮挡、隔离桌面、高风险动作、快照与补偿仍未实现，因此不能宣称阶段三整体验收完成。
  • 阶段四：部分完成。 主动建议、主动收件箱、接受/忽略/稍后提醒/转任务、注意力预算、暂停入口、应用内通知和飞书长连接审批已形成代码闭环。手机 PWA、手机配对、系统级推送和远程接管未实现，因此不能把阶段四称为完整交付。
  • 阶段五：部分完成。 记忆候选、召回、纠正、冲突、遗忘传播、导出，以及候选方法的生成、试跑证据、评估、晋升、拒绝和回退已形成代码闭环。真实长期记忆使用、方法采用前后的生产对照和完整 5.4 验收尚未完成。
  • 阶段六：部分完成。 增量事件同步、同步对端认证、冲突处理、任务租约与 epoch fencing、设备撤销与令牌轮换、kill switch、加密数据库备份恢复、健康检查、维护和脱敏诊断已形成代码闭环。真实双设备切换、设备丢失演练、完整迁移、数周连续运行和 v1.0 发布验收尚未完成。

体验补齐（2026-11-08） ​

本轮补齐的是用户可感知的入口和最后一公里，不改变原有任务、审批和恢复边界：

  • 首次运行： 全新实例进入 /welcome 四步向导，完成服务商选择、连接测试、聊天模型保存、原生执行器绑定、记忆/主动偏好；向导失败时 fail-open，不阻塞其他路由。
  • 记忆与主动： 主导航重新暴露“需要你”和“记忆”；记忆默认由向导开启“任务经历”候选，直答聊天会召回已确认记忆并显示参考条数；任务成功、失败和可恢复终态都会尝试捕获经历。
  • 主动提醒： 主动服务启动后扫描一次，之后每 5 分钟扫描，并响应任务/审批/效果/来源事件；页面内 toast 和可选桌面通知只负责“让人看到”，页面关闭后不承诺推送。
  • 飞书： 企业自建应用长连接、open_id 白名单、文本/图片/文件消息、任务状态转发、审批摘要和 /approve、/reject 文本命令已形成代码闭环。飞书卡片按钮回调不支持长连接，首版不做卡片按钮。
  • 邮件： SMTP 发送复用效果账本，审批预览写明真实发送和不可撤回；IMAP 只读同步最近邮件到来源，不标记已读。邮件工作台提供账户、收件箱和写信；首版不支持附件选择。
  • 尚未验收： 真实飞书租户、真实 SMTP/IMAP 账户、退信与垃圾邮件语义、页面关闭后的推送、邮件附件 UI，以及真实用户长期使用。

Agent 运行时闭环 ​

  • 已实现： 原生执行器 native 与工程执行器 codex 并列，执行器身份写入运行记录和产物清单；普通任务默认走原生执行器，明确的代码/工程任务走 Codex，失败后不静默切换。
  • 已实现： 四协议模型接入（OpenAI Chat、OpenAI Responses、Anthropic Messages、Gemini），统一流式文本与工具调用；服务商可在设置中选择或自定义。
  • 已实现： @hearth/agent-runtime 单 Agent 工具循环，包含读取、搜索、写入、编辑、补丁、命令、联网、询问用户和完成工具；任务级读写目录、网络域名和工具白名单。
  • 已实现： 轮次、工具次数、Token 和时长预算；每个模型回合与工具步骤写检查点；等待用户补充时可带着回答恢复；缺失产物时带上一轮 Agent 上下文补交，最多两轮。
  • 已实现： 需要联网或工程工作区权限的任务先在聊天中生成提案，用户确认后才创建任务；普通通用任务直接派出。
  • 界面结果： 任务页显示执行器、阶段、Token、耗时和结果；详情页默认只展示用户需要的总结与声明产物，中间 JSON、命令日志和检查点收进折叠区域。

以上是代码与自动测试能证明的闭环，不代表已在真实用户环境中完成长期运行验收。

Windows 助手目前采用“先聚焦服务端批准的目标应用，再截图或输入”的方式，不适合后台无焦点操作。对于由 ApplicationFrameHost 承载窗口的 UWP 应用，助手会读取窗口的 UIA 子树，只有解析出与批准应用对应的子进程时才允许聚焦和观察；例如 CalculatorApp 会映射为批准名 calculator。无法唯一归属或无法读取 UWP 子进程时直接拒绝，不把整个宿主窗口静默当成目标。真实 UIA invoke 已在计算器中验证：调用“二”返回 InvokePattern，读数由 7 变为 72。同一条链路也已在隔离配对设备上完成“观察 → UIA 动作 → 自动观察”，命令结果和截图回传均成功。

4.2 主动收件箱已实现代码闭环独立收件箱按优先级展示建议；支持接受、忽略、稍后提醒和转成普通任务；接受与转任务分离；应用内 toast、可选桌面通知和飞书长连接可分发“需要你”的审批/建议；忽略后同一事件不换说法继续推送页面关闭后没有系统级推送；手机收件箱和远程接管仍未实现

4.4 注意力预算与主动服务验收部分完成每日上限 0–50、安静时段、冷却时间、聚合窗口、临时暂停和恢复；预算快照显示今日已用、限额、是否安静/暂停及下次允许时间；最近 7 天记录送达、接受、忽略、转任务和完成任务数；“需要你”页面集中显示待处理审批尚未用 5–10 个真实主动任务验收“平均每个任务打断不超过一次”；没有推送送达统计，也没有长期用户感受记录

阶段四的关键边界是“建议不等于执行”。accept 只改变建议状态；只有 convert 会创建一个新的排队任务，之后仍按普通任务的执行器、审批和效果账本规则运行。高风险动作不会因为来自主动建议而绕过审批。

6.3 备份、恢复与升级部分完成生成 *.hearth-backup 加密归档；口令经 scrypt（N=32768、r=8、p=1）派生，AES-256-GCM 加密，口令至少 12 字符；归档包含 SQLite 快照、必要设置/审计/事件元数据和加密后的本机 master.key；恢复先写临时 SQLite，检查 user_version、schema 和 integrity_check，重建投影，再事务复制，失败回滚；保留当前实例 instanceId、createdAt 和全局停止状态，清除旧租约、配对和桌面会话临时记录；旧 /api/backup 返回 410 并要求使用加密备份不包含产物正文、任务工作区、来源正文、发件箱附件、截图/桌面临时文件和外部服务数据，因此不是完整可迁移备份；没有应用版本升级流水线或升级失败回退发布流程；schema 不兼容会拒绝恢复，但没有真实跨版本 fixture 演练
6.4 长期运行与 v1.0 验收部分完成健康快照包含运行时长、内存、磁盘、schema、任务计数、调度器、审批、kill switch 和最近一次维护；维护会清理过期审批、恢复中断任务、删除过期租约/桌面命令/截图/配对和临时文件，不删除任务、记忆或产物；服务启动后每 6 小时自动维护，也可手动触发；维护失败会记录失败并把健康状态标为 degraded；诊断导出包含健康、维护、计数和事件类型，不含路径、密钥或环境秘密；运维页展示健康、维护和备份边界没有数周连续运行测试、资源漂移数据、真实 v1.0 安装/升级/迁移/退出验收，也没有完整的全任务类型回归矩阵

阶段六的备份边界需要在界面上继续显示：数据库可恢复不等于产物文件可迁移。恢复完成后，任务可能重新出现，但产物正文、任务工作区或外部附件仍需要单独备份和核对。

借鉴与取舍 ​

  • OpenClaw： 配对与能力审批分离；命令按设备声明并逐项授权；观察帧是动作的唯一依据；用户接管会取消待执行输入、推进控制代次；不支持的动作直接拒绝。Hearth 已采用这些边界。
  • Hermes： 强调显式能力清单、执行前目标复核和会话隔离。Hearth 已采用应用白名单、目标应用复核和控制代次；尚未采用后台无焦点输入，因为当前 Windows 执行层无法可靠证明输入仍落在批准窗口内。
  • OpenClaw 的主动服务思路： 建议与执行分离、建议动作仍回到普通审批链。Hearth 已采用；没有把主动建议做成自动执行器。
  • Hermes 的健康检查思路： 把驱动、权限、运行状态和最近维护结果显式暴露。Hearth 已用健康快照、维护记录和脱敏诊断采用该边界。
  • DeerFlow： 任务拆解、方法候选和评估分层只作为设计参考。Hearth 没有集成 DeerFlow，也没有引入其多 Agent 运行时。
  • LoopX： 只借鉴小闭环提交、状态证据和验收边界作为交付方法；没有把 LoopX 作为运行依赖。
