阶段二至六交付状态 ​

核对日期：2026-11-12。本文只记录当前代码和真实运行能证明的事实，不以页面存在代替闭环。

阶段结论 ​

  • 阶段二：部分完成。 本地文件、知识库、公开网页、文档表格提取、任务来源引用，以及“草稿 → 审批 → 本地发件箱写入 → 回执”的闭环已可用；IMAP 只读同步和 SMTP 发送已形成代码闭环，但需要用户配置真实账户并完成人工验收。日历账户和真实邮件服务商的退信/垃圾邮件语义仍未验收，因此不能宣称阶段二整体验收完成。
  • 阶段三：部分完成。 同机 Windows 设备已能配对、逐项审批能力、开始观察、暂停、继续、接管、交还、终止，并在明确目标应用后执行低风险点击、输入、按键和 UIAutomation 动作。敏感区域遮挡、隔离桌面、高风险动作、快照与补偿仍未实现，因此不能宣称阶段三整体验收完成。
  • 阶段四：部分完成。 主动建议、主动收件箱、接受/忽略/稍后提醒/转任务、注意力预算、暂停入口、应用内通知和飞书长连接审批已形成代码闭环；Web 端已有可安装 PWA 壳、离线应用壳和移动底部导航。手机配对、系统级推送、远程接管及 iOS/Android 真机验收仍未完成，因此不能把阶段四称为完整交付。
  • 阶段五：部分完成。 记忆候选、召回、纠正、冲突、遗忘传播、导出，候选方法的生成、试跑证据、评估、晋升、拒绝和回退，以及 5.12 的持久委派、可审阅 Handoff、沙箱和渠道边界已形成代码闭环；5.11–5.13 共加入 30 个本地可重复场景，其中 10 个为 Personal Agent 专项场景，并保留 P0 故障注入回归。真实长期记忆使用、方法采用前后的生产对照、完整 5.4 验收、真实多执行器压力与真实渠道/设备场景尚未完成。
  • 阶段六：部分完成。 增量事件同步、同步对端认证、冲突处理、任务租约与 epoch fencing、设备撤销与令牌轮换、kill switch、加密数据库备份恢复、健康检查、维护和脱敏诊断已形成代码闭环；连接运行时已分离 transport、subscription、dataFreshness 和 executionOwnership，并提供 generation 隔离、离线 outbox、设备能力扩权审批和远程动作 uncertain 对账。真实双设备切换、真实远程节点断网恢复、设备丢失演练、完整迁移、数周连续运行和 v1.0 发布验收尚未完成。

体验补齐（2026-11-08） ​

本轮补齐的是用户可感知的入口和最后一公里，不改变原有任务、审批和恢复边界：

  • 首次运行： 全新实例进入 /welcome 四步向导，完成服务商选择、连接测试、聊天模型保存、原生执行器绑定、记忆/主动偏好；向导失败时 fail-open，不阻塞其他路由。
  • 记忆与主动： 主导航重新暴露“需要你”和“记忆”；记忆默认由向导开启“任务经历”候选，直答聊天会召回已确认记忆并显示参考条数；任务成功、失败和可恢复终态都会尝试捕获经历。
  • 主动提醒： 主动服务启动后扫描一次，之后每 5 分钟扫描，并响应任务/审批/效果/来源事件；页面内 toast 和可选桌面通知只负责“让人看到”，页面关闭后不承诺推送。
  • 飞书： 企业自建应用长连接、open_id 白名单、文本/图片/文件消息、任务状态转发、审批摘要和 /approve、/reject 文本命令已形成代码闭环。飞书卡片按钮回调不支持长连接，首版不做卡片按钮。
  • 邮件： SMTP 发送复用效果账本，审批预览写明真实发送和不可撤回；IMAP 只读同步最近邮件到来源，不标记已读。邮件工作台提供账户、收件箱和写信；首版不支持附件选择。
  • 尚未验收： 真实飞书租户、真实 SMTP/IMAP 账户、退信与垃圾邮件语义、页面关闭后的推送、邮件附件 UI，以及真实用户长期使用。

与 T3 Code 的能力差距收窄（2026-11-09） ​

本轮优先补齐与 Hearth 任务所有权、审批账本和日常使用直接相关的入口，不把 Hearth 改造成 IDE：

  • 交互粒度： 任务运行中可以追加“轮后继续”或“中止当前轮并带补充重跑”。queue 不打断当前轮；steer 会中止当前轮、保留任务与产物，再用补充信息重跑，不是向正在生成的 token 流中实时注入。
  • 工具审批： @hearth/agent-runtime 在执行敏感工具前调用调度器审批桥；写文件、改文件、应用补丁、运行命令、联网读取和桌面截图在必要审批下进入 waiting_approval，批准后继续，拒绝后以工具错误回给模型并继续任务。DeepSeek Harness 的 SDK approval/request 也进入同一审批记录，分别映射为 allowed-once、rejected 和 cancelled。原生执行器的完全权限不打断，但写入 approval.auto_approved 审计事件；DeepSeek Harness 在完全权限下收到审批请求时也自动放行并写审计。外部 effect 仍走原有参数指纹、效果账本和回执，两层审批不合并。
  • Git 工作台： 任务详情展示工作区与相对基线的文件 diff、增删行数、提交、文件源码预览、PR 与 CI 检查状态；即使工作区有未提交改动，也能独立查看分支相对基线的改动。
  • 快速入口与移动壳： 增加 Ctrl/Command + K 页面与任务跳转、PWA Manifest、应用图标、离线应用壳和移动底部导航。
  • 任务整理： 任务列表支持置顶、归档和恢复；归档任务默认从“全部”“进行中”“已完成”“需要处理”中隐藏，可在“已归档”筛选中找回，置顶任务优先显示。整理状态写入独立的 pinnedAt/archivedAt 字段，不改变任务状态、审批、租约或执行结果。

该轮仍明确留空（后续状态见“通用执行内核升级”）： Codex、Hermes、Qoder、WorkBuddy、Kimi 等外部执行器还没有把 provider 原生逐次审批事件统一接回 Hearth；当时没有任意 project/worktree 管理、隐藏 ref 文件回滚、PR 评审决定/自动合并/revert、subagent、MCP 服务端或 provider 原生 skills/commands。2026-11-11 已补齐本地项目 Worktree、有界子代理、本地 stdio MCP 和按需技能；隐藏 ref 文件回滚、PR 评审决定/自动合并/revert、远程 MCP 和 provider 原生 skills/commands 仍未实现。PWA 仍未完成 iOS/Android 真机安装、系统推送、手机配对和远程接管验收。

Agent 运行时闭环 ​

  • 已实现： 原生执行器 native 与工程执行器 codex 并列，执行器身份写入运行记录和产物清单；普通任务默认走原生执行器，GitHub 代码/工程任务走 Codex，用户显式选择本地项目后由 native 在隔离 Worktree 中执行，失败后不静默切换。
  • 已实现： 四协议模型接入（OpenAI Chat、OpenAI Responses、Anthropic Messages、Gemini），统一流式文本与工具调用；模型档案可配置上下文窗口和最大输出 Token，服务商可在设置中选择或自定义。
  • 已实现： @hearth/agent-runtime 通用执行内核，包含读取、文档、glob/grep、写入、原子编辑、补丁、命令、联网搜索、技能、委派、本地 MCP、询问用户和完成工具；任务级读写目录、网络域名和工具白名单。
  • 已实现： 轮次、工具次数、Token 和时长预算；每个模型回合与工具步骤写检查点；Token 感知压缩、瞬态重试、重复工具调用检测；等待用户补充时可带着回答恢复；缺失产物时带上一轮 Agent 上下文补交，最多两轮。
  • 已实现： 需要联网或工程工作区权限的任务先在聊天中生成提案，用户确认后才创建任务；普通通用任务直接派出。
  • 界面结果： 任务页显示执行器、阶段、Token、耗时和结果；详情页默认只展示用户需要的总结与声明产物，中间 JSON、命令日志和检查点收进折叠区域。

以上是代码与自动测试能证明的闭环，不代表已在真实用户环境中完成长期运行验收。

通用执行内核升级（2026-11-11） ​

本轮把 native 从精简编码循环升级为通用执行内核，共完成 16 个计划项：前 15 项是代码与测试交付，最后一项是本文档与能力矩阵。以下只证明代码与自动测试闭环，不构成与 Pi、DeerFlow 或 OpenCode 的共享基准，也不能据此宣称数值上更强。

  • 文件与命令： 新增 glob/grep、文档读取、XLSX/CSV/DOCX 生成；edit_file 可预览差异，补丁先校验全部目标再原子写入，支持 move 和真实删除；Shell 完整输出写入任务内 .hearth/shell 日志，只回填尾部，超时会杀死整个进程树。
  • 上下文与稳定性： 模型窗口默认 128K、最大输出默认 8K；按窗口预留 max(16K, 15%) 并保留约 20K 近期 Token，只在完整回合边界压缩，绝不拆散工具调用与结果，摘要失败退回安全截断；压缩后写检查点。纯文本不再算完成，连续未调用 finish_task 会失败；429/5xx/网络错误最多重试两次，相同工具参数循环会被提示并停止重复执行。
  • 技能与委派： 提示词只注入技能索引，load_skill 校验内容哈希、任务权限和审计后返回正文，read_skill_resource 限制在技能包内。delegate_task 使用新上下文，只允许只读或隔离写，单层串行、每父任务最多两个、禁止 MCP 和自动合并，子代理用量计入父任务。
  • 项目与 Worktree： 新增本地 Git 项目注册、路径与 Git 根校验、分支校验和设置页项目列表；项目任务使用 hearth/<task-id> 独立 Worktree，恢复时复用，成功或失败都保留，只有用户手动清理且工作区干净时才删除。GitHub 任务继续走 Codex。
  • 本地 MCP： 仅支持 stdio，服务器命令、参数和加密环境值由设置页管理；启动探测、工具发现、超时和崩溃隔离形成闭环。工具统一命名为 mcp__<serverId>__<toolName>，调用前用 ajv 校验 JSON Schema，结果限长，输出、错误和 stderr 均脱敏，并检测跨服务器及内置工具名称冲突。
  • MCP 审批与边界： 每次 MCP 调用进入现有逐次工具审批，绑定服务器、工具名和参数摘要；只有完全权限模式自动放行并记录审计。系统不自动重试 MCP 调用，也不承诺 exactly-once。搜索默认关闭，仅支持 Tavily 与 SearXNG；公共网络能力仍受 DNS、重定向和私网地址拦截，每次抓取仍审批。

这轮仍没有远程 MCP、OAuth、浏览器自动化搜索、图片/扫描件视觉理解、PPTX、LSP、格式化器、Shell 后台会话或自动 cherry-pick。工具数量增加不等于执行质量已经经过真实用户验收。

Windows 助手目前采用“先聚焦服务端批准的目标应用，再截图或输入”的方式，不适合后台无焦点操作。对于由 ApplicationFrameHost 承载窗口的 UWP 应用，助手会读取窗口的 UIA 子树，只有解析出与批准应用对应的子进程时才允许聚焦和观察；例如 CalculatorApp 会映射为批准名 calculator。无法唯一归属或无法读取 UWP 子进程时直接拒绝，不把整个宿主窗口静默当成目标。真实 UIA invoke 已在计算器中验证：调用“二”返回 InvokePattern，读数由 7 变为 72。同一条链路也已在隔离配对设备上完成“观察 → UIA 动作 → 自动观察”，命令结果和截图回传均成功。

Personal Agent 升级（2026-11-10） ​

本轮以 codex/eval-agent 的实际代码为基线，把任务系统扩展为可持续的个人 Agent 层，没有重写执行面，也没有引入常驻 LLM Router：

  • 个人状态层： 10 类实体、别名、关系和状态、决定、承诺、提及与证据引用进入 SQLite schema v28。实体和状态使用 confirmed / observed / inferred / stale 四档置信度；同一字段出现来源冲突时生成冲突注意力事项，不静默覆盖。
  • 写回与遗忘： 聊天确认、任务完成、审批决定和来源入库都会尝试写回本体；用户纠正生成新的确认状态和用户决定。遗忘按证据引用传播到实体、别名、关系、状态、决定、承诺、记忆和 Context Pack，并保留可审计墓碑。
  • 上下文连续性： Context Broker 生成 must_know / relevant / recallable / omitted 四 lane 上下文包，注入项带稳定 ref、来源、置信度、有效期和原因；支持 token 预算、敏感度、taint、trust、expand_ref 以及委派子包继承父包边界。
  • 指代与歧义： Mention Resolver 将“昨天那个”“小艾”等表述解析到实体或决定；多个候选时要求澄清，不可逆外部动作在歧义未解决前直接阻断。
  • 注意力治理： Attention Governor 统一任务、审批、承诺、对账、来源、冲突和主动建议候选；预算、安静时段、冷却、去重和影子模式仍按原有治理边界运行。每条投递可解释，Inbox 以“现在需要你决定什么”为主列表，并记录接受、忽略、稍后和错误反馈。
  • 任务图与异步执行： Task DAG 默认最大深度 3、每个父任务最多 5 个子任务、最多 3 个并行；支持 all、any、n_of_m 汇聚、循环拒绝和取消失败传播。后台工具支持启动、输出、停止和审批；预备动作只允许只读或可丢弃预览，外部副作用必须绑定同一任务的审批和动作摘要。
  • 运行可观测性： 线程订阅把执行器事件回流到任务，忽略自身订阅事件以避免递归；Watchdog 支持重复失败、超时和影子模式；Intake Router 对入站内容做 ignore / chat / task / attention 确定性分流并记录决策。
  • 原生执行器： 除 expand_ref 外，新增五个只读本体查询工具；工具名通过权限合并进入原生运行时，但仍不扩大写目录、网络或审批权限。
  • 控制面： /personal 展示实体、状态、别名、承诺和决定，支持用户纠正、查看证据和按证据遗忘；/runtime 展示预备动作、后台工具、线程订阅、Watchdog 和 Intake 决策。
  • PA 专项场景： 新增 mention-ambiguous、cross-session-continue、stale-state-deadline、source-conflict-owner、attention-budget-30、forget-propagation-ontology、prompt-injection-ontology、four-week-continuity、task-dag-fan-in、async-tool-interrupt，并纳入统一场景包。

这一层的边界是：场景可以证明机制和故障边界，不能证明真实长期价值。生产阈值、真实用户注意力收益和实体解析总体准确率仍需用真实数据和 dogfooding 基线校准。

借鉴与取舍 ​

  • OpenClaw： 配对与能力审批分离；命令按设备声明并逐项授权；观察帧是动作的唯一依据；用户接管会取消待执行输入、推进控制代次；不支持的动作直接拒绝。Hearth 已采用这些边界。
  • Hermes： 强调显式能力清单、执行前目标复核和会话隔离。Hearth 已采用应用白名单、目标应用复核和控制代次；尚未采用后台无焦点输入，因为当前 Windows 执行层无法可靠证明输入仍落在批准窗口内。
  • OpenClaw 的主动服务思路： 建议与执行分离、建议动作仍回到普通审批链。Hearth 已采用；没有把主动建议做成自动执行器。
  • Hermes 的健康检查思路： 把驱动、权限、运行状态和最近维护结果显式暴露。Hearth 已用健康快照、维护记录和脱敏诊断采用该边界。
  • DeerFlow： 任务拆解、方法候选、评估分层、长任务中间件、沙箱和子代理边界作为设计参考。Hearth 没有集成 DeerFlow，也没有引入其多 Agent 运行时；当前 native 在长时编排、沙箱、子代理、技能、记忆和延迟工具上的覆盖仍弱于 DeerFlow。
  • OpenCode： 只学习公开执行面形态，不复制代码或运行时。Hearth 已补齐 glob/grep、原子编辑、Shell、办公产物、搜索、按需技能、有界子代理、本地 stdio MCP、压缩和项目 Worktree，但 LSP、格式化器、远程 MCP、浏览器自动化、视觉理解、自动合并和更完整的 Worktree 体验仍未支持。
  • MCP 审批： 采用本地 stdio、独立启动探测和逐次审批绑定，不引入远程传输或 exactly-once 承诺。服务器环境值经 SecretBox 加密，且不继承 Hearth 模型密钥或任意父进程密钥。
  • LoopX： 只借鉴小闭环提交、状态证据和验收边界作为交付方法；没有把 LoopX 作为运行依赖。
  • T3 Code / OpenClaw 的连接运行时： 采用 owner connection、generation fencing、传输/订阅/新鲜度分离、离线 outbox 和重连不自动重放 mutation 的边界；没有复制其协议、会话存储或客户端实现。

2026-11-12 在当前分支运行 npm test，100 个测试文件、725 个测试全部通过；npm run typecheck、npm run build 和 npm run docs:build 通过。测试覆盖服务层、API、模型协议、原生工具循环、glob/grep、原子补丁、Shell 进程树超时、办公文件读写、上下文压缩、瞬态重试、循环检测、强制完成、技能加载、项目与 Worktree、子代理边界、MCP 管理/调用/审批、搜索适配、预算、权限、检查点、提案确认、记忆/技能治理、主动提醒、调度、连接运行时、持久委派、交接产物、沙箱分类、渠道幂等、个人本体、Context Broker、任务图和只读本体工具，但不替代真实用户、真实设备和长期运行验收。

本轮没有建立与 Pi、DeerFlow 或 OpenCode 的共享外部能力基准，也没有执行可支撑“超过它们”的量化评测。目前能成立的是公开能力、代码成熟度和边界差异，不是总体性能排名。
