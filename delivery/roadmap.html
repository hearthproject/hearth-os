分阶段产品路线图 ​

Stage 0–6 的能力门槛：每个阶段交付什么、何时算完成、什么条件不满足就不能进入下一阶段。

本篇怎么读 ​

  • Stage 是能力层级，不是日期或工期。
  • MVP 位于 Stage 1 的早期出口，不是 Stage 6 的产物。
  • 每个阶段都必须同时有用户可见界面、持久状态、验证证据和恢复路径。
  • 阶段退出条件全部满足才算完成；可以停留、试用和回退，但不能跳步。

分阶段产品路线图：从原型到 Personal Agent OS ​

推进原则 ​

  • 以能力门槛推进，不以日历承诺推进；
  • 每个阶段都能独立交付价值；
  • Stage 1 内部必须尽早出现可每天使用的 MVP，而不是等 Stage 6 才形成产品；
  • 每个阶段都必须同时交付用户可见界面、持久状态、验证证据和恢复路径；
  • 前端与后端按纵向切片同步推进，不允许“先做完后端再补界面”；
  • 先证明可靠，再扩大覆盖；
  • Codex 是第一个外部执行器，但不是唯一能力来源；
  • 不在早期自研通用 Sandbox、模型推理引擎或完整 Agent 框架；
  • 每个阶段都同时有产品门槛和学习门槛；
  • 任何自动化能力进入真实副作用前，必须先通过安全与恢复测试。

阶段总览 ​

阶段用户拿到的产品形态核心能力仍明确不做主要风险
Stage 0可点击的端到端产品原型产品楔子、任务集、协议、交互、评测和安全基线真实执行、真实副作用目标漂移、原型与实现脱节
Stage 1本地可用的个人任务工作台；早期出现 MVP可恢复内核、Codex、Web 任务卡、审批、产物、恢复真实邮箱自动发送、GUI、主动循环、多设备状态恢复、重复副作用、集成不稳
Stage 2能处理日常内容工作的 Personal Operator邮件/日历/文档/网页/数据真实任务，Context Compiler，Memory v0桌面 GUI、完整主动性、自进化权限、平台限制、上下文成本
Stage 3能操作桌面的 Computer Operatoragentd、GUI、接管、桌面隔离与高风险审批多设备长期同步、无评估进化脆弱性、验证、不可逆操作
Stage 4低打扰的 Proactive Personal AgentTrigger、主动循环、注意力预算、手机 PWA、设备配对完整多设备执行、技能自动晋升通知疲劳、越权、移动安全
Stage 5会积累个人上下文并安全改进方法的 AgentMemory OS、Evolution OS、技能评估/晋升/回滚企业多租户、公开市场记忆污染、技能漂移、评估偏差

阶段之间不是按日期切换的瀑布，而是能力依赖关系。每个阶段都可以停留、试用和回退；产品在任一阶段都应保持当前范围内的完整可用性。

MVP 的位置： MVP 是 Stage 1 的早期产品出口，位于完整 Stage 1 门槛之前。它不包含邮件、日历、GUI、主动性、完整记忆和多设备，但必须包含真实执行、持久任务状态、Web 任务卡、产物、审批演练和失败恢复。具体定义见 25.3。

Stage 0：定义、原型与基线 ​

开发模块：Stage 0 · 定义与原型

目标： 在进入真实实现前，把产品、交互、协议和验收钉住。Stage 0 不是纯文档阶段，必须产出一个可点击的端到端产品原型。

交付：

  • 一页产品定义与非目标；
  • 首选用户和 20–30 个真实任务清单；
  • 八类任务覆盖矩阵；
  • 第一个产品楔子：优先选择一个高频、低外部风险的任务族做 MVP；
  • 可点击的 Web 原型：今日、任务卡、新任务、需要你、产物、失败/恢复和审批状态；
  • 每个 UI 状态对应的投影字段和主动作；
  • Event、Task、Run、Executor、Approval、Receipt 的 schema v0；
  • 威胁模型和风险分级；
  • 评测任务集与验证器 v0；
  • Build vs Integrate ADR；
  • 仓库、CI、编码规范和版本策略。

退出条件：

  • 能用一句话说明 Hearth 不是什么；
  • 每个核心实体有不变量；
  • 至少 12 个任务有可执行验收；
  • 高风险动作有明确审批路径；
  • 用户可以在原型中连续完成“创建任务 → 看到状态 → 审批 → 查看产物 → 查看恢复路径”；
  • 原型中的每个状态都能映射到真实数据契约，而不是只能演示的动画；
  • 已决定 Stage 1 不自研 Sandbox 内核。

Stage 1：Durable Personal Kernel 与 MVP ​

开发模块：Stage 1 · 持久内核与 MVP

目标： 证明一个个人 Agent 可以本地常驻、可中断、可恢复、可审批、可审计地完成真实任务，并尽早形成一个每天可用的最小产品。

MVP 完成线： Stage 1 不等待所有内核细节完成后才展示产品。先在一个窄任务族上完成真实纵向切片，达到 25.3 的 MVP 门槛；随后继续补齐副作用安全、第二任务族和故障注入，完成整个 Stage 1。

范围：

  • hearthd 单进程常驻服务；
  • SQLite WAL Event Log、投影和 migration；
  • Task / Ticket / Run / Assignment / Lease；
  • outbox、幂等键、Receipt；
  • Codex Executor：代码、测试、Issue/PR、调研、文档和多文件工作区；
  • workspace 生命周期、只读证据、文件 diff；
  • Policy、Mandate、Approval v0；
  • Web 作为主入口：任务创建、任务卡、详情/时间线、审批、产物、失败与恢复；
  • CLI 作为自动化和诊断入口，不替代产品界面；手机 PWA 留到 Stage 4；
  • Artifact 和验证器 v0；
  • 基础 Token 记录与预算；
  • 崩溃恢复和故障注入测试。

首批真实任务：

  1. 从 Issue 到代码修改、测试和 PR 草稿；
  2. 三份资料来源整理成对比表和报告；
  3. 读取一组文档，生成周报草稿和引用清单；
  4. 文件整理与可复现转换；
  5. 需要审批的外部副作用（使用测试 Effect 或本地测试服务）。

退出条件：

  • MVP 已能在浏览器中每天使用一个窄任务族；
  • kill -9 后能恢复到可继续状态；
  • 200 次故障注入下重复外部副作用为 0；
  • Codex 任务有结构化产物和验证；
  • 没有任务仅凭自然语言“完成”；
  • 任务卡能清楚显示状态、产物和下一步；
  • 创建、取消、重试、审批、查看产物和恢复都能通过 Web 完成；
  • 至少 10 个真实任务通过人工验收；
  • Token 和人工分钟有基线。

学习门槛：

  • 理解事件日志、单写者、lease、fencing token 和恢复；
  • 理解 Codex 的能力边界和工作区隔离；
  • 理解审批、outbox 和 Receipt 的区别；
  • 形成第一份失败分类和路由数据。

Stage 2：Personal Operator ​

开发模块：Stage 2 · Personal Operator

目标： 从“会做文件任务”扩展到“能做大多数日常数字内容工作”。

范围：

  • Email Connector：只读同步、线程、联系人、附件、草稿、待审批发送；
  • Calendar Connector：只读、冲突检查、待审批写入；
  • Docs/Drive Connector：读取、版本、导出、待审批分享；
  • Browser Executor：研究、下载、无 API 表单；
  • Document/Data Executor：PDF、Office、表格、OCR、转换、对账；
  • Context Compiler 和 Token Governor v1；
  • Memory v0：Episodic + Semantic，带来源、预算和基本遗忘；
  • 任务模板和第一批可复用流程；
  • 更完整的通知与产物中心。

退出条件：

  • 邮件“读—理解—起草—审批—发送—回执”闭环可用；
  • 日历冲突检查与待审批写入可用；
  • 文档转换结果可验证；
  • 网页研究有来源和引用；
  • 常见任务的人工分钟显著下降；
  • 没有跨账户、跨项目数据串扰；
  • 失败时能恢复或明确转人工。

Stage 3：Computer Operator ​

开发模块：Stage 3 · Computer Operator

目标： 覆盖没有 API 的桌面软件和跨应用流程。

范围：

  • 设备 agentd 与桌面能力注册；
  • GUI Executor：可访问性树、截图、键鼠、文件选择；
  • 隔离虚拟桌面；
  • 浏览器/桌面实时接管；
  • 高风险桌面动作审批；
  • 桌面任务验证与恢复；
  • 应用白名单、窗口范围和系统安全边界。

退出条件：

  • 至少 5 个真实桌面任务可以完成并验证；
  • 接管流程可用，用户能暂停、操作和交还；
  • GUI 失败不会留下半完成的高风险状态；
  • 桌面操作没有读取密码库或越权系统设置；
  • Token 和人工分钟在可接受范围。

Stage 4：Proactive Personal Agent ​

开发模块：Stage 4 · 主动个人 Agent

目标： 让 Hearth 在有限授权内主动工作，同时保持低打扰。

范围：

  • 邮件、日历、文件、网页和任务依赖 Trigger；
  • 主动循环和后台批处理；
  • 注意力预算、静默时段、聚合通知；
  • 手机 PWA：查看、审批、接管、发起、通知；
  • 设备配对、安全隧道、推送脱敏；
  • A1/A2 自主级别；
  • 任务卡和“需要你”收件箱成熟；
  • 主动模式的开关和对照评估。

退出条件：

  • 主动任务真实有用，不制造通知疲劳；
  • 每任务打断次数 ≤ 1；
  • 高风险动作仍需审批；
  • 手机可完成关键审批和接管；
  • 用户能随时暂停、撤销和降级主动模式；
  • 无后台无限循环和预算透支。

Stage 5：Memory OS 与 Evolution OS ​

开发模块：Stage 5 · 记忆与进化

目标： 让系统真正积累个人上下文，并能安全地改进方法。

范围：

  • 五类记忆完整落地；
  • 记忆写入、冲突、检索、预算、遗忘、同步；
  • 记忆浏览器和“为什么召回”视图；
  • 轨迹挖掘、技能候选、版本和评估集；
  • Shadow → Canary → Promote → Rollback；
  • 技能权限约束；
  • 核心 Runtime 人工 PR 修改；
  • 至少一个完整技能晋升案例。

退出条件：

  • 记忆可纠正、可遗忘、可导出；
  • 记忆注入准确率达标；
  • 技能晋升有对照评估；
  • 没有权限扩大或安全回归；
  • 回滚可用；
  • 用户能理解系统为什么这样做。

Stage 6：Personal Agent OS ​

开发模块：Stage 6 · 多设备与长期运行

目标： 多设备、长期驻留、可迁移、可自托管。

范围：

  • 多设备 agentd；
  • 事件同步、cursor、lease、fencing；
  • 设备能力路由和离线队列；
  • 设备丢失撤销；
  • 远程执行和加密传输；
  • 备份、恢复、迁移和升级；
  • 长期运行监控；
  • 资源调度和配额；
  • 可选远程 Sandbox。

退出条件：

  • 一个逻辑 Agent、多个设备一致；
  • 设备切换不丢任务、不重复副作用；
  • 离线恢复率达标；
  • 迁移后事件、记忆和技能可验证；
  • 设备撤销立即可靠；
  • 长期运行无内存泄漏和状态漂移。

明确推迟 ​

Stage 0–1 的 MVP 不做：

  • 自研容器/虚拟机/内核；
  • 自研基础模型或推理引擎；
  • 自建公开 Agent 市场；
  • 企业 IAM、多租户、计费；
  • 完整桌面 Office 替代品；
  • 无边界的自动付款、签约和公开发布；
  • 一开始接入所有渠道；
  • 无评估的自进化；
  • 多设备复杂同步；
  • 原生 iOS/Android 应用；
  • 只有 CLI 或 API、没有浏览器产品路径的“伪 MVP”；
  • 为了赶底层进度而把前端整体推迟到后续阶段。
