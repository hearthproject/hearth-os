工程实施 ​

设计说明定义产品边界，工程实施定义怎样把这些边界落在可运行、可验证、可恢复的系统里。这里的技术选择是默认方案，不是不能替换的信仰；但任务正确性、权限和恢复不能为了开发方便而让步。

工程原则与运行形态 ​

  • 模块化单体优先。 早期不引入微服务，把控制、任务、执行、记忆和入口放在同一个可部署系统里，用接口和测试保持边界。
  • 纵向切片交付。 每个阶段同时包含界面、持久状态、真实执行、验证和恢复；只有后台或只有日志的能力不算完成。
  • 事实先写入。 任务状态、审批、产物和回执先落本地记录，界面、通知和统计都从记录重建。
  • 单一事实源。 消息、工具结算、检查点与 run 边界统一写入 SQLite events；checkpoint 文件只是物化视图，损坏时按 event_seq 回放重建。
  • 每个状态只有一个写权威。 单进程、单写者、单 SQLite 连接；HostKernel 用数据目录租约阻止第二个宿主写入。
  • 执行可以恢复。 长任务保存检查点和执行记录；工具调用走 prepare → dispatch → settle 操作账本，未结算操作在下一进程拒绝自动重放。
  • 外部动作先审批。 发送、写入、删除、发布和付款都经过预览、授权、幂等和回执，执行器不能直接绕开。
  • 适配器隔离。 Codex、连接器、浏览器、桌面操作和 Windows AppContainer 沙箱都通过统一能力边界接入。
  • 本地优先并可迁移。 个人数据默认留在本地，云服务可以替换，用户能够导出、备份和恢复。
  • 版本与回退。 数据结构、执行器、方法和配置都有版本，升级失败可以回到上一个稳定版本。
  • 可观察但不侵入。 每个任务有轨迹、成本和失败分类；终态 run 输出 run-evidence.json，详细记录留在本地审计视图。

TypeScript 是语言，Node.js 是运行时。前者约束开发期类型，后者提供文件、网络、进程和定时能力；外部输入和持久化数据仍然需要运行时校验。主语言选择不改变隔离、审批、恢复和权限这些真正的安全边界。

早期只有一个常驻服务写入主数据库。命令行、Web、手机和各个执行器通过任务队列或受控接口连接，不直接写主数据库。执行器可以替换，任务状态、授权范围和回执留在主系统。文档提取在服务端进程内完成；浏览器工作进程和设备代理按需作为受控能力接入，不成为第二套业务协议。

本地数据目录应当让用户能看懂、备份和迁移。主记录保存任务和事件，产物单独存储并按内容校验，工作区按任务创建和清理，配置保存规则与连接，凭据只保存加密内容或短期引用，日志和备份单独保留。敏感目录使用最小权限，备份加密，多设备同步只发送必要的状态和产物引用。

数据、测试与发布 ​

仓库按“入口、核心能力、执行器、测试和评估”组织，而不是按页面或团队随意堆放。

区域负责什么
apps/serverFastify 单进程控制面：HostKernel、调度、审批、效果、上下文、记忆、浏览器、渠道与运维
apps/web聊天、资料库、Context、邮件、定时任务、连接与设置
apps/nativeWindows 沙箱/PTY/租约 helper（C#）
apps/desktop-tauriTauri 2 外壳、托盘、内置 Node 与打包资源

packages/eventlogSQLite 单一事件日志、schema 迁移与投影
packages/agent-runtime通用 Agent 内核、编码 harness、T1/T2 操作合同
packages/codex-executor / deepseek-executor两个外部执行器适配器
docs中英双语文档站；架构 18 篇、设计 21 篇、交付、评测与日志

任务、运行和执行尝试必须分开。任务表达用户要的结果，运行表达某一次真实尝试；工作单元同一时间只允许一个有效执行者，重新分配时要防止旧执行者用迟到结果覆盖新状态，重新分配也不能重复产生外部动作。

事实记录只追加，不原地改写。每条记录带版本、关联关系和触发原因，任务状态、审批、产物和成本都是投影。记录升级必须兼容旧数据，重放不能产生外部副作用。大内容放在产物中，记录只保存引用。

测试和评估是两件事。测试是确定性的通过或失败门槛，每次提交都要运行；评估是带统计性质的质量测量，需要真实任务集、基线和多次比较。两者都重要，但不能混成一个只看平均分的检查。

测试至少覆盖九类：单元逻辑、执行器与连接器契约、真实存储集成、浏览器纵向路径、故障注入、记录重放、安全拒绝路径、性能和长稳，以及真实任务评估。当前 main 上有 140 个测试文件、946 个用例；另有一套 18 个崩溃点的长跑矩阵。

每个小阶段都要同时提交实现、浏览器验收路径、失败路径和回归测试。每个 bug 修复带回归测试；每条记录版本带迁移和旧数据兼容测试；每个外部动作带幂等和重复投递测试；每个新权限带拒绝路径测试；每个执行器或连接器带超时、取消和失败分类测试。

持续集成建议分三层：提交和合并前跑单元、契约、集成和模拟执行，目标在十分钟内完成；每天运行故障注入、安全、性能、真实外部服务冒烟和长稳测试；发布前跑全量测试、迁移、安装、备份恢复和阶段出口验收。当前仓库把 typecheck、test、test:longrun、test:sandbox、test:e2e、docs:build 等拆成独立脚本；统一的三层聚合入口和远端分支保护仍需在仓库设置里补齐。

发布必须版本化数据结构、执行器协议和用户可见配置。升级前自动备份，升级后验证旧记录、产物、记忆和授权仍然可读；失败可以回退。执行器版本、方法版本和配置都要锁定，真实用户数据、凭据和本机路径不能进入测试仓库。
