风险与 Kill Criteria ​

什么情况下暂停、回退或停止项目，比“继续做”更难也更重要的决策。

风险与 Kill Criteria ​

主要风险 ​

风险早期信号缓解
范围膨胀每阶段都在新增执行器，核心闭环未稳定以任务集和阶段门槛控制范围
可靠性不足崩溃后任务丢失、重复发送单写者、outbox、lease、故障注入
安全事件越权、秘密泄露、提示词注入成功沙箱、Broker、审批、红队

维护负担每周大量时间修依赖和渠道不自研底层、减少连接器、自动升级测试

记忆错误反复引用过期或错误事实来源、置信度、冲突、遗忘、用户纠正

产品像套壳去掉 Codex 后没有独立价值控制面、记忆、审批、恢复、评测
平台限制浏览器登录、验证码、API 变更人工接管、官方 API 优先、降级

时间投入不可持续维护超过可支配时间缩小范围、延迟非核心能力、自动化测试

全局暂停条件 ​

出现以下情况时，暂停新增功能，优先修复：

  • 高风险动作发生越权；
  • 发生秘密或敏感数据泄露；
  • 故障注入出现重复外部副作用；
  • 崩溃恢复率低于 95%；
  • 用户无法撤销设备、连接或技能；
  • 关键记忆无法遗忘；
  • 任务状态与事实源不一致；
  • 外部副作用无法对账。

阶段 Kill Criteria ​

Stage 0：

  • 无法定义 12 个可验收任务；
  • 无法说明 Hearth 与单 Codex 的区别；
  • 没有威胁模型；
  • 原型无法让用户在不看说明的情况下完成主路径；
  • 原型状态无法映射到真实投影或数据契约；
  • 试图在第一阶段同时做所有执行器。

Stage 1：

  • 达到 MVP 门槛后仍无法完成 10 个真实任务；
  • 重复副作用无法消除；
  • 恢复依赖人工重建状态；
  • 任务状态只能靠聊天记录推断；
  • Token 成本完全不可见；
  • 后端可用但 Web 任务卡无法完成创建、查看、审批、恢复和取回产物；
  • 只有 CLI 或日志能演示，不能算 MVP 成立。

Stage 2：

  • 邮件/日历闭环需要用户频繁重建上下文；
  • 连接器权限无法最小化；
  • 文档处理结果无法验证；
  • 常见任务人工分钟没有下降；
  • 不同账户/项目数据串扰。

Stage 3：

  • GUI 任务成功率低且无法接管；
  • 无法证明操作没有越权；
  • 桌面环境无法恢复；
  • 每次 GUI 任务都需要大量人工介入。

Stage 4：

  • 主动任务制造通知疲劳；
  • 用户无法预测何时会被打扰；
  • 手机审批可被重放或越权；
  • 后台任务无法停止或预算失控。

Stage 5：

  • 记忆错误导致持续返工；
  • 遗忘无法传播到设备和索引；
  • 技能评估可被挑选样本操纵；
  • 技能扩大权限或安全回归；
  • 回滚不可用。

Stage 6：

  • 多设备重复执行或状态分裂；
  • 设备丢失无法及时撤销；
  • 迁移后事实、记忆或产物不一致；
  • 长期运行维护成本超过产品收益。

项目级 Kill Criteria ​

在以下情况下，应考虑缩小产品，而不是继续加功能：

  • 完成 Stage 2 后仍没有稳定的 10 个真实日常任务；
  • 人工分钟没有实质下降，用户只是在“看 Agent 工作”；
  • 维护成本持续超过可支配时间且没有下降趋势；
  • 仅靠换模型就能替代 Hearth 的绝大部分价值；
  • 安全边界无法达到可接受水平；
  • 用户不愿意把真实邮件、文件或日程交给它；
  • 自进化持续产生不可解释的漂移；
  • 多设备复杂度吞掉单设备体验。

不应被 Kill 的东西 ​

  • Event Log 和可恢复性；
  • 审批、幂等和 Receipt；
  • 评测与失败样本；
  • 记忆遗忘和用户纠正；
  • 任务卡与低打扰体验；
  • 手动接管；
  • 安全边界和 kill switch。

这些是产品的地基，不是可以在“赶进度”时删除的功能。
