自研与集成 ​

Hearth 自己做“任务如何被授权、执行、验证、恢复和记住”，直接使用“完成任务所需的模型、浏览器、文档解析、隔离环境和外部接口”。边界清楚，产品才不会变成一堆互相对不上的集成。

自研与集成边界 ​

自研描述的是责任归属，不是开发顺序。Hearth 不会先把后台全部做完，最后再补界面；任务卡、审批、产物和接管从第一阶段就是产品的一部分。下面这些能力必须由 Hearth 自己掌握，因为它们决定任务是否可信。

  • 任务控制：判断一个请求要不要处理，何时创建任务，选择哪种执行方式，什么时候停下来等用户。
  • 持久执行：保存目标、工作单元、执行记录、检查点、预算和恢复路径，保证长任务跨重启和断网继续。
  • 事实记录：先写事实，再从记录重建界面、通知和统计；每个状态只有一个写权威。
  • 授权与审批：把规则、单次授权、设备能力和外部动作绑定在明确范围内。
  • 外部副作用控制：动作先预览，再授权，执行后留下可核对的回执；不确定时先对账，不直接重试。
  • 运行环境与安全：工作区、隔离级别、网络出口、短期凭据、隐私和全局停止入口。
  • 记忆与能力进化：记忆有来源、敏感度和遗忘规则；方法变化经过评估、灰度、晋升和回退。
  • 验证与成本：用真实任务、独立验证器、人工分钟、恢复能力和成本判断是否完成。
  • 入口与体验：任务卡、审批、产物、接管、通知和手机入口是产品本身，不是后台的展示层。

这里的“自研”不意味着从零写数据库、浏览器或模型运行时。Hearth 自研协议、策略、验证和恢复，底层可以使用成熟组件。模型服务、Codex、浏览器自动化、隔离内核、文档解析、外部系统连接和通用开发工具链都直接集成；重复实现它们不会形成产品差异，只会增加维护负担。

Hearth 做的是适配层：锁定版本、准备最小工作区、注入短期权限、限制网络、设置超时和取消、解析结构化结果、独立验证，并在失败时降级到其他执行器或人工。适配层不是简单转发；它决定外部能力能否被任务系统安全使用。

Codex 适合作为第一个外部执行器。它擅长代码、长文档、复杂研究和多文件工作，但 Hearth 只能使用其公开、稳定、当前版本允许的能力。Codex 不持有任务数据库、长期凭据、记忆中心或外部写入权限；它接收一段最小上下文，在隔离工作区中完成工作，返回产物、结构化结果和失败分类，邮件、日历、付款和发布等动作必须回到 Hearth 的审批与回执通道。

接入要求Hearth 的处理
版本变化锁定版本，升级前跑契约测试
工作区一次执行一个临时工作区，任务结束回收
权限只挂载必要目录，不传入长期密钥和无关凭据
网络默认关闭或白名单，只开放任务需要的出口
结果要求结构化输出，由 Hearth 自己验证
失败区分模型、工具、验证、权限和环境失败，再决定重试、降级或接管

Hearth 与“Codex 套壳”的分界线也在这里：套壳把 Codex 当产品；Hearth 把 Codex 当作可替换、可限权、可验证的执行引擎。

与其他个人助手项目的区别 ​

OpenClaw 已经是可运行的个人助手产品，在渠道、会话、常驻服务、设备节点和生态上明显领先当前的 Hearth。Hearth 刚进入第一阶段 MVP 实现，不能声称自己已经更强，也不能把两者天然说成上下层关系。

更准确的区别是负责的对象不同。OpenClaw 主要对会话、渠道、个人助手体验和常驻运行负责；Hearth 想对任务契约、授权范围、外部副作用、完成证据和失败恢复负责。如果未来把 OpenClaw 作为渠道或运行入口接入，Hearth 仍然必须自己掌握任务、授权、预算、验收和回执，才有资格成为任务控制层。

Hearth 从 OpenClaw、Hermes 等项目学习渠道组织、记忆约束、检查点、人工接管和低成本体验，但不 fork 它们的产品底座，也不把它们作为当前运行时依赖。当前路线只把 Codex 作为第一个外部执行器，其余项目主要提供设计参考。

是否真的更强，只能靠可验证的差异证明：同样的任务，Hearth 不重复产生外部副作用，能独立证明完成，能在注入攻击下守住权限，并且 Token、延迟和人工注意力没有变差。功能更多不算证据，演示成功也不算证据。
