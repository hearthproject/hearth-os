WHY HEARTH

Agent 的难点不是“会回答”，而是“能负责”。

Hearth 把任务状态、授权、执行、证据和恢复放在同一条可审计链路上。它不试图制造一个更会聊天的模型，而是让个人数字劳动变得持久、可控、可验证。

  • 任务卡优先，而不是无限聊天记录
  • 外部副作用必须经过审批、幂等与回执
  • 每个阶段都必须交付可用的纵向切片
DESIGN CONTRACT

六个不可妥协的设计选择

这些选择决定了 Hearth 不是 Codex 套壳、不是自动化脚本集合，也不是一个无法恢复的黑盒。

01任务，而不是聊天用户面对任务卡、审批和产物，不需要理解 Worker、Harness 或 Token 的内部结构。↗02持久执行内核Event Log、lease、检查点与恢复策略让长任务跨越崩溃、休眠和网络中断继续工作。↗03并列执行器Codex、Native、Connector、Browser、GUI 与 Human 按能力、风险和 Token 成本路由。↗04副作用有回执所有外部动作经过 outbox、幂等键与 Receipt；失败可对账、可撤销、可重放。↗05记忆与进化受控记忆有来源、敏感度和遗忘策略；技能必须经过评估、canary 和回滚。↗06本地优先，逐步长大从本地 MVP 到多设备 Agent OS，每一阶段都同时有界面、状态、验证和恢复。↗
