Hearth 总体设计 ​

Hearth 是一个单用户、自托管、长期运行的个人 Agent OS。它把用户意图变成持久、可审计、可恢复的任务，让模型、工具和外部系统围绕同一条任务链路协作。

产品定位与目标 ​

Hearth 服务一个主要用户，允许少量可信协作者参与审批和查看结果。个人文件、凭据、记忆和设备默认由用户自己掌握，云端模型、远程隔离环境和同步服务都可以按需接入，而不是默认把全部数据交出去。

产品以任务为中心，而不是以聊天记录为中心。用户需要看到的是：系统正在做什么、为什么需要自己介入、最后交付了什么、失败后从哪里恢复。模型、工具和执行环境可以更换，但任务状态、授权范围、完成证据和外部操作回执必须留下来。

首个产品范围不从“所有个人工作”开始，而是选择一个高频、外部风险低、结果容易验证的任务族，完整走通从输入到交付的链路。首条链路稳定后，再逐步增加信息来源、外部写入、桌面操作、主动服务、记忆和多设备能力。

明确不做： 企业多租户、公开 Agent 市场、未经审批的高风险自动化、以模型参数规模为核心的竞赛，以及要求用户每天维护提示词、插件和工作流的工具。

判断一项工作是否完成，不能只看模型是否说“好了”。任务需要有用户可见的结果、可复核的证据、明确的未完成事项，以及外部写入对应的审批和回执。

总体设计与任务链路 ​

Hearth 把一次工作拆成同一条链路：入口接收请求，控制层判断是否值得处理，任务层保存目标和状态，执行器完成具体工作，审批与回执层守住外部副作用，验证层决定完成还是转人工。

环节负责什么不负责什么
入口与交互接收消息、文件、网页和定时事件，展示任务、审批、产物和接管入口不直接决定任务是否执行，也不直接修改状态
控制与授权判断忽略、观察、建议还是创建任务，检查范围、风险和自主级别不执行工具，不持有长期原始凭据
任务与持久执行保存目标、工作单元、执行尝试、预算、检查点和恢复路径不决定业务权限，也不直接完成外部写入
执行器与路由根据能力、风险、成本和设备选择合适的执行方式不自行扩大权限，不绕过审批
审批与外部副作用预览、授权、幂等执行、回执、对账和人工接管不判断任务本身是否值得做
运行环境与安全隔离工作区、网络、凭据和敏感数据，控制资源与设备边界不替代产品层面的风险判断
记忆与能力进化保存可纠正的背景和可复用方法，评估后再小范围启用不成为事实源，不允许无边界自改
评估与成本用真实任务、验证器、基线和成本指标判断能力是否真的提升不用演示或单次成功代替验收

所有事实先被记录下来，界面、通知和统计都从记录重建。系统早期采用单进程、单写者和本地数据库，不为尚未出现的规模提前拆成微服务。任务可以跨越重启、休眠和网络中断继续存在；每个工作单元同一时间只有一个有效执行者，旧执行结果不能覆盖新状态。

外部操作不是“让模型调用一个工具”就结束了。系统先生成可预览的动作，确认权限和审批，再通过可重复核对的方式执行，最后留下回执。出现不确定结果时先对账，不盲目重试；无法确认或风险过高时暂停并交给用户。

技术选型 ​

技术选型服从系统约束，而不是语言偏好。Hearth 需要长期运行、跨入口共享协议、方便扩展工具，并且让单人团队能维护完整链路。

层次选择理由
主语言TypeScript控制、任务、命令行、网页和适配器共享同一套概念与校验规则，减少前后端协议漂移
服务运行时Node.js 22+适合大量输入输出、进程编排和事件推送；第一阶段保持单进程
本地存储SQLite WAL单用户、本地优先、单写者场景足够，部署简单，迁移和备份容易
Web 界面React、Vite、PWA适合任务卡、审批、产物和实时状态；PWA 降低手机入口成本
实时更新Server-Sent Events比双向长连接更简单，适合服务端把状态变化推送到界面
文档与数据Python sidecar文档解析、表格、批处理和评测依赖成熟生态，按需独立运行
原生边界Rust 按需引入只用于隔离监督、设备代理、加密等确实需要单二进制或更强内存边界的部分

TypeScript 是语言，Node.js 是运行时，两者不是同一层，也不是二选一。TypeScript 提供开发期的类型约束，Node.js 提供文件、网络、进程和定时能力；外部输入和持久化数据仍然需要运行时校验。

选择 TypeScript 的主要原因是协议共享和集成效率。任务、审批、产物、回执和执行事件会同时出现在服务端、命令行、网页和测试中，同一套类型与校验可以显著减少漂移。Hearth 的主要负载是编排和等待，不是持续的大规模计算，因此 Node.js 在单用户规模下足够。

不选 Rust 作为主语言，不是因为 Rust 不好，而是当前瓶颈是产品边界、协议一致性、恢复和权限判断，不是执行速度。Rust 更适合隔离监督、设备侧代理和加密边界；未来只有在单二进制、强隔离或设备资源成为硬约束时，才扩大它的范围。Go 暂不作为主栈，Python 只承担文档、数据和评测能力，避免形成多套业务协议。

前端采用 React、Vite 和 PWA，不采用以服务端渲染为核心的第二套运行时。任务状态来自本地服务端投影，浏览器只负责呈现和发出命令，避免出现第二个事实源。第一阶段不引入微服务，也不为了“看起来完整”提前拆网络边界。

模块地图与关键边界 ​

下面九个模块是并列阅读的设计取舍说明。它们共同覆盖从用户入口到长期运行的全部产品判断，不按代码目录组织。

模块先解决什么
入口与交互让用户知道系统在做什么、什么时候需要自己、结果在哪里
任务与持久执行让工作跨重启、休眠和失败继续，并且可以验证和恢复
控制面与授权判断什么时候观察、建议、执行或停下，并把权限收在明确范围内
执行器与路由用不同专长完成不同工作，而不是把所有事情交给一个万能模型
审批、接管与外部副作用让发送、写入、删除、发布等动作可预览、可授权、可对账
运行环境与安全用隔离、最小权限和凭据代理限制真实世界的影响
记忆与能力进化积累背景和方法，但保持可纠正、可遗忘、可回退
评估与成本用真实任务证明可靠性和成本，而不是用演示证明能力
多设备与长期运行让同一套任务、授权和数据在多设备上长期保持一致

Hearth 不改动的底线包括：所有界面状态都来自可重建的记录；每个状态只有一个写权威；外部动作必须有审批或明确豁免，以及可核对的回执；执行器看不到长期原始凭据；每个任务都有预算、截止时间和取消路径；记忆有来源、敏感度和遗忘规则；方法变化必须经过评估、灰度、晋升和回退。
