# 面试工具包：高级后端工程师（AI 平台）

- **适用岗位：** 云帆数据｜高级后端工程师（AI 平台）｜P5
- **版本与日期：** v1.0；生成于 2026-11-05（Asia/Shanghai）
- **用途：** 为筛选、技术面试、系统设计和团队面提供统一的能力证据记录方式。
- **能力维度：** D1 长任务编排与恢复；D2 输出校验与数据写入安全；D3 供应商故障与降级；D4 数据安全与密钥治理；D5 测试与可观测性；D6 成本与工程取舍。
- **输入依据：** 仅使用《T13 输入：云帆数据招聘需求访谈记录》中的岗位要求与面试重点；未引入外部题库或联网内容。

> 本工具包中的问题、评分锚点和追问是用于收集能力证据的面试设计，不代表输入中已规定的公司评分制度。输入未提供各维度权重、录用分数线或决策规则，**均待招聘团队确认**。

## 使用规则

1. **先要证据，再给分数。** 记录候选人说过的具体机制、取舍、失败案例和结果；工具名、模型名或“做过”本身不构成高分证据。
2. **允许真实案例或假设场景。** 候选人可以使用脱敏的真实经历，也可以基于问题中的假设场景作答；不能要求其披露前雇主机密、客户数据或受限内部材料。
3. **同一主问题用于同岗位候选人。** 追问可以随回答变化，但不得加入与岗位无关的个人问题。
4. **一次只评一个维度。** 如果回答涉及多个维度，先记录交叉证据，再回到当前维度评分，避免重复计分。
5. **1–4 分为证据等级，不是人格评价。** 所有维度不因候选人的表达风格、口音、工具偏好或任职公司名称加减分。
6. **覆盖而不是堆题。** 建议整套流程至少覆盖 D1–D6 各一次；各轮如何分配由招聘团队确认。若某轮时间不足，记录“未覆盖”，不要用猜测补分。

## 统一评分口径

每个维度使用下列四级锚点。维度内的具体锚点优先于这段通用说明。

| 分数 | 证据等级 | 判定要点 |
|---|---|---|
| **4** | 强证据 | 能完整说明目标、约束、方案、失败路径、验证方法和取舍；能指出边界条件与残余风险，并有可复述的实际或高质量模拟结果 |
| **3** | 达到要求 | 能给出可落地的核心方案，覆盖主要故障路径；部分细节或取舍需要追问，但没有关键缺口 |
| **2** | 部分达到 | 知道常见术语或基本做法，但方案停留在单点措施、缺少状态/失败/验证闭环，或无法说明为什么这样做 |
| **1** | 证据不足 | 未给出可执行方法，或直接依赖未经验证的假设；无法说明关键风险，回答与本岗位场景不匹配 |

> 录用阈值：**未知/待确认**。总分可用于汇总证据，不应在未确认公司规则前自行设定淘汰线。

## D1｜长任务编排与恢复

**能力定义：** 面向耗时较长、跨多个步骤或外部依赖的后端任务，设计可持久化、可重试、可恢复、可取消且不会产生不可控重复副作用的执行链路。

**岗位依据：** 访谈将“做过异步任务或长任务”列为必须项，并把“如何设计可恢复的长任务”列为面试重点。

### 主问题（可向候选人宣读）

> 请描述你设计过的一个耗时较长、包含多个步骤或第三方调用的后端任务；如果没有可直接分享的案例，也可以按假设场景回答。假设任务执行到一半时进程重启，某个外部调用已经成功，但本地还没记录结果。你会怎样设计任务状态、幂等、重试和恢复？用户取消任务后，又该如何收尾？

### 1–4 分锚点

| 分数 | 具体锚点 |
|---|---|
| **4** | 设计持久化任务状态与阶段边界；使用幂等键、去重或等效机制处理重复执行；明确“外部副作用已发生但状态未落库”的窗口及补偿/对账方式；支持断点恢复、受控重试、取消和人工介入；区分可重试与不可重试错误；说明部分产物如何隔离、如何观测和清理；能讨论一致性与实现复杂度取舍 |
| **3** | 有持久化状态、重试和幂等设计，能识别进程崩溃与重复执行的常见风险；有基本的取消或人工重试路径；但对某个关键窗口、补偿机制或状态一致性说明不完整，经追问后能补齐核心逻辑 |
| **2** | 主要依赖队列、自动重试或内存状态；知道“要做幂等”，但不能说明幂等键如何生成、状态如何持久化，或没有处理外部成功后本地失败、取消后收尾等关键情况 |
| **1** | 只回答“加队列”“多试几次”或“记录下来”，没有任务模型、恢复机制或失败路径；无法说明重复执行和进程重启会造成什么后果 |

### 追问（至少使用 2 个）

1. **崩溃窗口：** “外部调用成功后、状态写入前进程崩溃，你如何发现并修复这条不一致记录？补偿、对账和人工处理分别放在什么位置？”
2. **错误分类：** “哪些错误允许重试，哪些必须立即终止？重试次数、退避和总时限如何设定，怎样避免把下游故障放大？”
3. **取消与人工介入：** “取消请求到达时任务可能正处于不可中断步骤，你怎样定义取消语义、回收资源并让操作者可追踪？”
4. **验证与观测：** “你会用什么状态、指标或审计记录证明恢复逻辑有效？怎样演练一次真实崩溃？”

### 记录提示

- 任务状态存在哪里、由谁推进、如何防止并发重复推进。
- 外部副作用是否有幂等键、去重表、补偿或对账机制。
- 是否说清“至少一次执行”与业务不重复之间的处理方式。

## D2｜输出校验与数据写入安全

**能力定义：** 对 LLM 的结构化或半结构化输出建立分层校验、隔离和受控写入机制，防止错误、幻觉、越权或不可信内容污染业务数据或直接修改生产数据。

**岗位依据：** 访谈强调“重点是结果校验”“不能让模型直接改生产数据”，并将“如何防止模型输出污染数据”列为面试重点。

### 主问题（可向候选人宣读）

> 假设 LLM 的输出会用于更新客户的敏感业务数据。模型可能返回格式正确的 JSON，但其中的业务含义是错的；也可能受到输入文档中不可信内容的影响。请设计一条从模型输出到业务落库的校验链，说明哪些情况必须拒绝、哪些可以进入人工确认，以及怎样保证模型不能直接修改生产数据。

### 1–4 分锚点

| 分数 | 具体锚点 |
|---|---|
| **4** | 采用分层防线：结构校验、类型/范围校验、业务语义校验、权限与对象归属校验、不可信内容隔离；高风险或低置信结果进入隔离区或人工审批，而不是直接写生产；写入通过受控服务/事务执行，具备审计、版本或回滚能力；覆盖“合法 JSON 但语义错误”、越权目标、重复写入和模型输出被注入等场景；说明误拒与漏放的取舍及验证方式 |
| **3** | 能提出结构校验加业务规则校验，并把高风险写入放在缓冲、审批或独立受控流程之后；能识别模型不应拥有生产写权限；但对越权、语义错误、回滚或提示注入中的至少一项说明不充分 |
| **2** | 只做 JSON Schema、正则或“让模型再检查一遍”；依赖模型自我验证作为主要防线；没有说明写入权限边界、人工确认、审计或错误回滚 |
| **1** | 直接信任模型输出并写库；把“提示词写清楚”当作唯一防护；无法说明错误输出、越权写入或不可信输入会怎样被阻止 |

### 追问（至少使用 2 个）

1. **语义正确性：** “Schema 校验通过但业务含义错误时，你用什么确定性规则或交叉来源发现它？规则由谁维护、如何防止规则本身过期？”
2. **写入边界：** “模型、校验服务、审批服务和数据库之间如何划分权限？系统如何证明模型不能直接拿到生产写权限？”
3. **隔离与回滚：** “哪些结果进入待审区，哪些直接拒绝？审批后写入失败或写错时，如何审计、回滚并通知相关人员？”
4. **不可信输入：** “如果待处理文档里包含诱导模型忽略规则的内容，你会在输入、输出还是权限层拦截？为什么？”

### 记录提示

- 校验是否真正独立于模型，而不是“模型自评”。
- 写入权限是否最小化，模型与生产数据之间是否有可审计的受控边界。
- 是否能把“不确定”的结果安全地留在生产数据之外。

## D3｜供应商故障与降级

**能力定义：** 在第三方模型或 API 出现超时、限流、间歇不可用、响应异常或接口变更时，设计受控重试、熔断、替代路径和明确的降级体验，同时控制重复副作用、质量下滑和成本放大。

**岗位依据：** 访谈明确要求“失败降级”，并将“遇到供应商超时怎么降级”列为面试重点。

### 主问题（可向候选人宣读）

> 你的服务依赖一个外部模型或第三方 API。它可能间歇性超时、触发限流、短时不可用，或返回与预期不一致的结果。请设计请求处理链路：什么情况下重试，什么情况下熔断或切换替代路径，什么情况下向用户返回降级结果？如果原始请求是否成功并不确定，你如何避免重复写入或重复计费？

### 1–4 分锚点

| 分数 | 具体锚点 |
|---|---|
| **4** | 为调用设置超时、有限次数的抖动退避重试和熔断；区分网络错误、限流、供应商错误和不可重试的业务错误；对“响应超时但对方可能已成功”设计幂等键、查询对账或安全补偿；具备备用模型/供应商、排队延后或有边界的降级模式，并说明质量、数据边界和成本影响；有恢复探测、告警和演练方式；不会无条件重试或静默返回错误结果 |
| **3** | 有超时、有限重试和至少一种降级或切换方案；能说明何时停止重试以及如何告知用户；但未充分处理重复副作用、供应商切换后的质量差异或恢复判定中的一项 |
| **2** | 只会增加重试或返回通用错误；没有熔断、替代路径或明确的降级语义；对超时后是否已成功、重复计费或故障恢复缺乏考虑 |
| **1** | 认为“供应商通常会恢复”，没有超时、重试边界或降级设计；或采用无限重试、忽略错误返回成功等高风险做法 |

### 追问（至少使用 2 个）

1. **切换依据：** “什么信号触发切换？备用路径与主路径的能力、数据边界和输出质量是否等价，怎样验证而不是假设？”
2. **不确定结果：** “请求超时但供应商可能已经执行成功，你如何确认状态？如果供应商没有查询接口，采用什么幂等或对账策略？”
3. **全部失败：** “所有路径都不可用时，用户会看到什么？哪些任务可以排队恢复，哪些必须明确失败，为什么？”
4. **恢复与演练：** “熔断后如何探测恢复？怎样在不污染生产的前提下演练一次供应商长时间故障？”

### 记录提示

- 是否明确超时、重试总预算和停止条件。
- 是否处理了“对方可能成功”的不确定性，而不只是重发。
- 降级是否诚实、可恢复，并且不会让低质量结果冒充成功结果。

## D4｜数据安全与密钥治理

**能力定义：** 围绕敏感业务数据的采集、传输、模型调用、日志、缓存、存储和删除建立端到端保护；密钥和凭据与业务代码分离，访问遵循最小权限，并对外部供应商的数据处理边界保持可验证。

**岗位依据：** 访谈指出客户会处理敏感业务数据，不能把密钥放到业务代码里；面试重点包括数据安全与供应商处理边界。

### 主问题（可向候选人宣读）

> 客户的敏感业务数据需要经过你的后端调用外部模型。请从请求进入系统开始，说明数据分级、最小化、租户隔离、凭据管理、日志和存储策略。你如何保证密钥不进入业务代码？如果日志、提示词或模型供应商侧的留存策略并不明确，你会怎样处理？

### 1–4 分锚点

| 分数 | 具体锚点 |
|---|---|
| **4** | 能识别数据分级和最小化原则；明确租户/对象级隔离与最小权限；密钥由专用密钥管理或安全身份机制注入，支持轮换、审计和不落业务仓库；传输与存储加密、日志脱敏、敏感字段不进入常规日志/追踪；对供应商的数据使用、留存、地域和删除边界要求可验证的合同或技术控制，不明确时采取阻断、脱敏或选择受控路径；说明审计、删除和泄露响应 |
| **3** | 覆盖密钥外置、最小权限、日志脱敏和至少一项供应商数据边界控制；能说明敏感数据不应无审查地发送给外部服务；但在轮换、租户隔离、留存核验或删除闭环上有缺口，经追问能补足主要风险 |
| **2** | 只提到环境变量、传输加密或“不要打日志”；没有访问控制、租户隔离、轮换或供应商留存处理；把“供应商承诺安全”当作充分证据 |
| **1** | 将密钥写入代码/仓库或普通配置；记录完整敏感载荷；无法说明数据边界、访问控制或供应商侧留存风险 |

### 追问（至少使用 2 个）

1. **密钥生命周期：** “应用如何取得密钥，如何避免进入镜像、日志和异常栈？轮换时怎样避免停机，如何追踪谁在何时使用了哪个凭据？”
2. **最小化与隔离：** “哪些字段绝不能离开你的边界？你如何在代码或网关层强制执行，而不是依赖调用方自觉？多租户场景如何防止串数据？”
3. **供应商边界：** “供应商是否用请求数据训练、保存多久、存放在哪里，你如何确认？如果合同或技术文档不明确，你的上线决策是什么？”
4. **日志与删除：** “提示词、模型响应、调试追踪和备份分别保存什么、保存多久？客户要求删除时，如何覆盖缓存、日志、备份和下游供应商？”

### 记录提示

- 密钥是否真正脱离业务代码和版本库，是否具备轮换与审计能力。
- 数据最小化、租户隔离、日志脱敏是否是技术强制，而非口头约定。
- 面对供应商未知的留存条款，是否选择暂停、脱敏或替代，而不是假设安全。

## D5｜测试与可观测性

**能力定义：** 为非确定性的模型输出、多步骤异步任务和外部依赖建立分层测试、评测、监控、追踪、告警与故障复现能力，使系统能够证明“结果是否正确、任务是否推进、故障发生在哪里”。

**岗位依据：** 访谈将“可观测性”列为岗位核心，并要求面试重点考察“怎么做测试和观测”。

### 主问题（可向候选人宣读）

> 一个包含 LLM、异步任务和第三方 API 的链路即将上线。输出不是完全确定性的，任务也可能跨多次重试。请说明你的测试策略和上线观测方案：怎样测试正确性、失败路径和恢复？你会看哪些指标、日志和追踪？出现一次“任务卡住但没有报错”的客户投诉时，你如何定位根因？

### 1–4 分锚点

| 分数 | 具体锚点 |
|---|---|
| **4** | 测试分层清晰：单元/契约/集成/端到端、故障注入与恢复演练并用；对非确定性输出使用经过版本化的评测集、可确定的规则断言、阈值和人工抽检，而非依赖单次字符串相等；覆盖超时、重试、熔断、重复执行、取消和坏输出；观测覆盖请求/任务关联 ID、阶段状态、延迟、错误分类、重试、校验拒绝、成本与供应商健康；有可执行的告警、仪表盘和隐私安全的故障复现方式 |
| **3** | 有单元/集成测试、基础评测集或规则校验，并能提出任务状态、错误率、延迟和调用成本等关键指标；能沿追踪或日志定位多数故障；但对非确定性、故障注入或告警有效性中的一项说明不足 |
| **2** | 主要依赖手工测试、固定样例或不稳定的全等断言；只监控服务存活或通用错误率；没有任务状态、阶段追踪或失败复现方法 |
| **1** | 认为非确定性系统无法测试，或只靠用户反馈发现问题；没有测试策略、指标或可追溯证据 |

### 追问（至少使用 2 个）

1. **非确定性测试：** “同一输入可能得到不同文本，你如何定义通过标准？评测集如何代表真实流量，更新时如何防止指标游戏化？”
2. **任务可观测：** “一次请求跨过队列、多个步骤和外部 API，你如何把日志、指标和追踪串起来？‘卡住但无报错’时先看什么？”
3. **失败演练：** “你如何测试崩溃恢复、重复消息、供应商超时和坏输出？这些测试是否会在每次发布前自动运行？”
4. **隐私与告警：** “观测数据如何避免泄露敏感内容？哪些告警真正可行动，怎样避免告警疲劳？”

### 记录提示

- 是否区分“模型质量评测”和“系统工程测试”，两者是否都有闭环。
- 是否能追踪一个任务从接收到恢复的全生命周期。
- 指标和告警是否指向可行动的原因，并兼顾敏感数据保护。

## D6｜成本与工程取舍

**能力定义：** 在输出质量、响应延迟、可靠性和调用成本之间做出有依据、可观测、可回退的工程取舍；能够建立预算边界、成本归因和持续优化机制，而不是只追求最低单价或最高质量。

**岗位依据：** 访谈将“成本控制”列为核心目标，并将“成本取舍”纳入面试考察；加分项包含账单成本分析。

### 主问题（可向候选人宣读）

> 假设产品要在质量、延迟、可靠性和模型调用成本之间取舍。请说明你会如何建立基线、选择方案并设置预算保护。遇到重试、降级、缓存或模型路由时，你怎样判断一项优化是真收益，而不是把成本或风险转移到别处？如果业务要求提高质量但成本已接近预算，你会怎样决策？

### 1–4 分锚点

| 分数 | 具体锚点 |
|---|---|
| **4** | 建立质量、延迟、成功率和单位业务成本的可比基线；将成本归因到租户/功能/任务并设置预算与异常保护；评估模型路由、缓存、批处理、输出长度控制、重试预算等方案时同时检查质量与可靠性副作用；有灰度、回退和成本回归告警；面对预算冲突能明确升级决策、分层服务或调整需求，而不是静默牺牲正确性 |
| **3** | 能提出至少两类成本控制手段，并说明用质量和延迟指标验证效果；有基本预算或成本监控；但对成本归因、异常保护、回退或跨指标副作用中的一项考虑不足 |
| **2** | 只提到换更便宜的模型、缩短提示词或少调用；缺少质量基线、成本归因和回归验证；容易以降低可靠性或结果正确性换取表面成本下降 |
| **1** | 无法说明如何衡量成本，或认为“成本越低越好”；没有预算边界、质量约束或决策责任人 |

### 追问（至少使用 2 个）

1. **基线与归因：** “你用什么单位比较不同任务和租户的成本？怎样区分模型调用、重试、存储和人工审核成本？”
2. **优化副作用：** “缓存、模型路由或减少上下文后，如何确认质量没有静默下降？发现下降时如何回退？”
3. **预算冲突：** “预算已接近上限但业务要求提升质量，谁做取舍？你会提供哪些选项和证据，怎样保证高风险数据仍受保护？”
4. **异常与重试：** “一次供应商故障可能带来大量重试和重复计费，你如何设上限、告警并避免成本事故？”

### 记录提示

- 是否把成本与质量、延迟、可靠性一起衡量，而不是孤立优化单价。
- 是否有预算、归因、异常检测和回退机制。
- 面对冲突是否能提出透明、可审计的决策，而不是静默降低正确性或安全性。
