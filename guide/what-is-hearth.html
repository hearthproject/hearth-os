PROJECT INTRODUCTION

Hearth：把数字劳动变成可靠任务 ​

Hearth 是一个单用户、自托管、长期驻留、低打扰、低 Token 的通用个人 Agent OS。它的目标不是制造另一个需要看管的聊天窗口，而是让重复的数字劳动可以被放心地托付、验证和恢复。

一句话定位 ​

Hearth 是一个拥有个人上下文、持久执行、真实工具和多设备入口的通用个人 Agent OS；它把人从重复的数字劳动中解放出来，而不是制造另一个需要看管的聊天窗口。

产品名是 Hearth，仓库为 hearth-os，命令行为 hearth，常驻服务为 hearthd，包命名空间为 @hearth/*。

它解决什么问题 ​

现有 Agent 往往能完成一次演示，却很难长期使用。问题通常不在模型能力，而在模型之外：

  • 任务状态保存在聊天记录里，崩溃或换设备后无法可靠恢复；
  • 外部副作用缺少审批、幂等、回执和对账；
  • 权限、凭据和记忆没有清晰边界；
  • 用户必须理解 Agent 的内部结构，才能判断它是否真的完成；
  • 每次任务都重复读取大量上下文，Token 成本不可控；
  • 前端被当成后置包装层，用户只能面对日志或 CLI。

Hearth 把这些能力放到产品中心：控制面、持久执行、并列执行器、记忆、进化、体验与评估。

它不是什么 ​

  • 不是另一个 Coding Agent；
  • 不是只会转发提示词的 Codex 套壳；
  • 不是把所有权限交给模型的黑盒自动化；
  • 不是企业多租户 Agent 平台；
  • 不是需要用户每天维护提示词、插件和工作流的工具。

Codex 在 Hearth 中是强大的并列执行器，不是产品本体，也不是唯一执行大脑。

一个逻辑 Agent，多设备执行 ​

text
一个逻辑 Hearth
  ├─ 一个主 Gateway / Control Plane
  ├─ 一个 Event Log / 单写者
  ├─ 多台设备上的 agentd
  ├─ 手机作为查看、审批、接管、发起入口
  └─ 每个设备注册自己的能力

设备只提供执行能力和入口，不复制身份、事实源和授权。所有事实进入 Event Log；所有外部副作用经过 outbox、幂等键和 Receipt；所有界面状态都是投影，不是事实源。

核心能力 ​

能力解决的问题
任务控制面决定做什么、是否允许、何时打扰、如何恢复
持久执行内核把意图变成可恢复、可审计、可回执的执行
并列执行器按能力、风险和 Token 成本选择 Codex、Native、Connector、Browser、GUI 或 Human
记忆与进化让人物、项目、偏好、承诺和经验可被安全召回，让重复成功沉淀成受控技能
体验平面用任务卡、审批和产物承载交互，而不是无穷聊天记录
安全与评估用验证器、红队、故障注入和阶段门槛证明“真的能做”
